<Warning>
**Not available on the hosted service, and not available on Kubernetes.** The gateway mounts
`/agent/*` and resolves your key, but no agent-api workload is deployed on either — every route on
this page answers `502 {"detail":"upstream unreachable: ConnectError"}` on
`https://api.cloud.vexa.ai`. Verified 2026-08-18 against the hosted gateway and the production
cluster. Tracked as
[vexa-platform#324](https://github.com/Vexa-ai/vexa-platform/issues/324).

The two streamed routes fail worse than the rest: `POST /agent/chat` and `GET /agent/meeting/stream`
open `200 text/event-stream` and close with **zero bytes** — no `error` frame, no `done` — so a
client reads a successful empty stream rather than an outage. Same issue.

This page documents the surface as built and as it runs on self-hosted Docker Compose. Do not build
a hosted integration against it until the tracking issue closes.
</Warning>

The agent API is Vexa's **control plane**. It turns triggers into [dispatches](/core/agents) and streams
their output; it does no execution itself — it validates and hands off to the [runtime](/core/runtime).
Endpoints are fronted by the gateway, which carries authentication and per-route scopes; the service
itself is internal.

<Note>
**Identity is server-derived.** Public clients reach these routes through the gateway under the
canonical prefix **`/agent/*`**. The gateway resolves your
`X-API-Key` → user and injects `X-User-Id`; agent-api derives the workspace/chat/quota **`subject`** from
that header (P20). A `subject` in a request body or query string is **ignored** — never trust the client
for identity. The gateway signs the identity it stamps (`X-Vexa-Identity`, gateway-identity.v1) and agent-api
refuses an `X-User-Id` that is not signed, so call these routes **through the gateway** —
`$API_BASE/agent/...` with `X-API-Key`. The `$AGENT_API/api/...` paths below name the internal routes;
reaching them directly takes the internal tier (`X-Internal-Secret` beside `X-User-Id`), which only
Vexa's own services hold.

The proxy maps `/agent/<path>` onto agent-api's `/api/<path>`, so **only the `/api/*` routes have a
gateway path.** `POST /invocations`, `POST /events`, `GET /health` and `POST /internal/scaffolds` are
reachable on the internal service only.
</Note>

## Health

```bash GET /health
curl "$AGENT_API/health"   # → {"status":"ok","service":"agent-api","checks":{"dispatcher":true},"capabilities":{...}}
```

`503` with `"status":"degraded"` when the dispatcher is not wired. `capabilities` carries the agent
plane's config tri-states and never affects `status` or the status code — an unconfigured capability
degrades a feature, not the process.

## Models

`GET /api/models` → the one model this subject runs, under both keys:

```json
{ "chat_model": "...", "agent_model": "..." }
```

**Removed in 0.12** — `streaming_model` and `meeting_model`. They named the in-product inference
pipeline, which no longer exists: Vexa makes no model calls of its own beside the agent, so there is
one model left and both keys carry it.

### The model catalog and a chat's model

When the deployment declares a [model catalog](/model-catalog), people pick the model each chat runs
on.

`GET /api/models/catalog[?session=<chat>]` returns the models the caller may pick (`models.v1`
ModelList):

```json
{
  "models": [
    { "id": "qwen3-32b", "display_name": "Qwen 3 32B (self-hosted)", "provider": "lab-vllm",
      "adapter": "openai_compatible", "harness": "openai-agent",
      "capabilities": { "tool_calling": true, "streaming": true, "context_tokens": 32768,
                        "reasoning_efforts": ["none", "high"], "default_effort": "none" },
      "access": "everyone", "default": true }
  ],
  "default": "qwen3-32b",
  "selected": null,
  "selected_effort": null
}
```

- **`models`** holds only what this caller may pick, each a real model by its catalog name. An
  `admins` model is absent for everyone else. No entry carries an endpoint or a credential.
- **`default`** is the model the caller runs on before picking: their own `default_model`, else the
  organisation's, else the catalog's default.
- **`selected`** is the named chat's own pick (`null` means the chat follows the default). It is
  present only when `session` is given.
- **`capabilities.reasoning_efforts`** lists the effort levels a chat may pick for that model, and
  is empty when the model has no effort control. **`default_effort`** is the level it runs at until
  the chat picks one.
- **`selected_effort`** is the named chat's own effort pick (`null` means the model's
  `default_effort`). It is present with `selected`.
- **No catalog:** the deployment returns `{"models": [], "default": null}`.

`POST /api/chat/model` with body `{ "session": "<chat>", "model": "<id>", "effort": "<level>" }`
returns `{ "ok": true, "session", "model", "effort", "changed" }`.

- It pins the chat to a model. `"model": ""` puts the chat back on the default.
- `effort` is optional. It is checked against the model the chat will run on (the pick, else the
  default) and stored with it; absent or empty runs the model at its `default_effort`. Changing
  the model without an `effort` clears the effort pick.
- The pick takes effect on the chat's next turn, which starts a fresh agent.
- A pick the next turn could not run is refused and not stored:

  | Status | Reason |
  |---|---|
  | `422` | the model is not in the catalog |
  | `403` | an admins-only model, for anyone else |
  | `422` | an effort level the model does not offer (`effort_unsupported`) |

  Each refusal is `{ "detail", "fault" }`, and `fault` is the [typed fault](#chat-streamed) below.

## Dispatch a unit

`POST /invocations` — the sink every trigger funnels through. Body is a conformant `unit.v1` Invocation
(the same envelope `units.make_dispatch` builds); it is validated and dispatched to the runtime. `400` if
the envelope is non-conformant.

```bash POST /invocations  → 202
curl -X POST "$AGENT_API/invocations" -H "Content-Type: application/json" -d '{
  "identity":{"subject":"u_jane","launcher":"schedule:u_jane"},
  "runner":"claude-code",
  "workspaces":[{"id":"u_jane","mode":"rw"}],
  "trigger":"scheduled",
  "start":{"entrypoint":{"inline":"Summarize overnight activity."}}
}'   # → {"workload_id":"agent-..."}
```

The shape is: `identity.subject` + `identity.launcher`, `runner`, a `workspaces` list (`mode` is
`rw` for trusted triggers — `message`/`scheduled` — else `ro`), the `trigger`, and a `start` that is
either `{"entrypoint":{"inline":"..."}}`, `{"entrypoint":{"path":"..."}}`, or `{"session":{"ref":"..."}}`.
There is **no** top-level `subject`, `workspace_repo`, or `plan` field.

## Chat (streamed)

`POST /api/chat` — body `{ prompt, session?, active? }` (`subject` is server-derived, not sent).
`session` is 1–128 characters from `A-Z a-z 0-9 . _ -`, starting with a letter or digit (empty or
absent means `main`); any other value is a `422`, here and at every other door that takes a session:
`/api/chat/submit`, `/api/chat/reset`, `GET /api/chat/pending?session=`, `GET /api/sessions/{session}/history`,
`DELETE /api/sessions/{session}`, `/api/chat/name`, `/api/chat/name/agent` and `/api/chat/target`. Each
entry of `PUT /api/chat/order`, and the `row` of `POST /api/chat/marks`, is a rail row key, `c:<session>` or
`m:<meeting id>` (or a bare session), the part after the prefix held to the same rule.
Returns **Server-Sent Events**; each `data:` line is one frame:

| frame | fields |
|---|---|
| `message-delta` | `text` |
| `tool-call` | `tool`, `args`, `callId` |
| `tool-result` | `callId`, `ok`, `summary` |
| `sources` | `items`: `[{ url, title? }]` — a page the turn successfully fetched (`WebFetch`), one per frame; a client merges a turn's items by `url` and renders them as the answer's citations. Only `http`/`https` URLs. |
| `commit` | `sha` |
| `rejected` | `violations` |
| `done` | `reply`, `sessionId`, `ok` (+ `detail` when a failure's raw provider text was rewritten, + `fault` when the turn failed typed) |
| `error` | `message` — the turn was refused before dispatch (e.g. no model credential configured); actionable, names what to set (+ `fault` when a dependency refused it) |

A chat whose model cannot run, for example because it was removed from the catalog, is refused
before anything starts. The answer is `{ "detail", "fault" }` with
`fault: { source: "model-provider", kind, provider, model, status: null, detail, remedy }`.

- **`kind`** is one of `unknown_model`, `not_permitted`, `not_configured` (the catalog offers this
  caller nothing), `credential_missing` or `effort_unsupported` (a stored effort level the model no
  longer offers).
- **The record's shape** is the one a failed provider call (`unpaid`, `unauthorized`,
  `rate_limited`, `unavailable`, `refused`) carries on the turn's `done` frame.
- **No substitution:** the turn never runs on another model instead.

```bash POST /api/chat  (SSE)
curl -N -X POST "$API_BASE/agent/chat" -H "Content-Type: application/json" \
  -H "X-API-Key: $VEXA_API_KEY" \
  -d '{"prompt":"Record that Acme renewed."}'
```

### Sources: the pages a turn read

When the agent reads a web page with `WebFetch` to answer, the stream carries a `sources` frame for
that page, so a client can show the answer's citations from data instead of parsing a "Sources" list
out of the reply text:

```json
{ "type": "sources", "items": [{ "url": "https://example.com/report", "title": "Example report" }] }
```

**Limits.**

- Only a fetch that succeeded is a source. A failed fetch and a search result list are not.
- One item per frame. A turn that read three pages sends three frames; merge them by `url`.
- `url` is `http` or `https` only, at most 2,048 characters. `title` is present only when the fetch
  tool's result is JSON carrying a `title`, and is cut to 300 characters.
- The `claude-code` and `openai-agent` harnesses emit it. The `codex` harness does not.

#### How it works

1. The harness sees a `WebFetch` call and keeps its arguments by call id
   (`core/agent/llm/claude_code.py`; `core/agent/llm/openai_agent.py` `_panel_events`).
2. On that call's successful result it calls `_fetched_source(args, content)` in
   `core/agent/llm/tool_events.py`, the one place both harnesses share. The URL comes from the call's
   arguments. When the result is JSON, its `title` is added and its own `url` field, if it is
   `http(s)`, replaces the one asked for.
3. The frame follows that call's `tool-result` frame on the worker's output and reaches the chat SSE
   stream unchanged, like the other panel frames.

The harness is the only writer of the frame; nothing stores it. No sealed contract lists the chat
frames, so the frame is additive: a client that does not know it ignores it. No route and no
configuration.

#### Why it complies

| Rule | How | Gate |
|---|---|---|
| **P2** couple only through contracts | The fetch vocabulary and the frame builder live once in `llm/tool_events.py`; both harnesses import it rather than keep a copy. | `gate:python` (`test_the_openai_runner_derives_the_same_event`); the shared module itself: ungated: reviewed |
| **P16** additive change | A new optional frame type on an unsealed stream; existing frames are unchanged. | ungated: reviewed |
| **P18** fail loud, no false success | Only a successful fetch becomes a source, so a citation always names a page the turn read. | `gate:python` (`test_a_failed_fetch_is_not_a_source`, `test_a_search_is_not_a_source`) |
| **P23** one writer | The harness derives the frame from the tool result; nothing else writes sources. | ungated: reviewed |

**Security.** The frame grants no access: it carries only URLs the person's own turn fetched, on that
person's own stream, through the same agent-api relay as every other frame. The fetch itself is
unchanged (`openai-agent`'s `WebFetch` keeps its outbound-address guard). A non-web scheme is never
passed on as a link, and the title is length-capped data, not markup. Tests in
`core/agent/tests/test_turn_sources.py`: `test_only_http_urls_are_sources` (refuses `javascript:`,
`file:` and a missing URL), `test_a_failed_fetch_is_not_a_source`, `test_a_search_is_not_a_source`,
`test_a_successful_fetch_is_a_source`, `test_the_title_and_final_url_come_from_a_json_result`,
`test_the_openai_runner_derives_the_same_event`.

**Typed faults.** A failure says who failed and how, as
`fault: { source, kind, status, detail, remedy }` on a failed `done`, on an `error` frame, and on the
body of a refused dispatch: `{ detail, fault }` with `503` when the agent runtime is down or full
(`unreachable`, `unavailable`, `quota_exceeded`) and `502` for its other kinds — never `500`. A
`runtime` fault adds `op` (`spawn` · `status` · `list`); a `model-provider` fault adds `provider` and
`model`. `detail` is one safe sentence and `remedy` what to do about it. The shape and the kinds are
`Fault` in the contract [`unit.v1`](https://github.com/Vexa-ai/vexa/tree/main/core/agent/contracts/unit.v1):

| `source` | `kind` |
|---|---|
| `runtime` | `spawn_refused`, `quota_exceeded`, `unauthorized`, `refused`, `not_found`, `unreachable`, `unavailable`, `bad_response` |
| `model-provider` | `unpaid`, `unauthorized`, `rate_limited`, `unavailable`, `refused`, `no_tool_calling`, `unknown_model`, `not_permitted`, `not_configured`, `credential_missing`, `endpoint_refused`, `effort_unsupported` |
| `vexa-tools` | `access_expired` |
| `agent-worker` | `tools_unconfined`, `credential_conflict` |
| `agent-api` | `internal`, `unavailable` |
| `gateway` | `unreachable` |

Chats are kept in the session store, apart from every workspace (ADR-0048; [Shared
chats](/minutes/shared-chats)). These routes read and change the store; no workspace route returns a
chat, and `_system` holds identity and settings only.

`POST /api/chat/reset` `{ session? }` → `{ "ok": true }` · `GET /api/sessions` →
`{ "sessions": [...] }` · `GET /api/sessions/{session}/history` → `{ "turns": [...] }`: a session the
caller has no thread for is a `404`; a thread whose transcript is missing or empty returns
`{ "turns": [] }`.

`DELETE /api/sessions/{session}` → `{ ok, session, files_removed, hidden_meeting }`: deletes one of the
caller's chats — the index entry, the conversation's transcript and continuity pointer, and the caller's
own marks and order entry for it. Workspace pages it wrote stay. When the chat was a meeting's,
`hidden_meeting` is that meeting's row (`m:<id>`), now hidden on the caller's rail; the meeting itself is
not deleted. `404` for a session not in the caller's index, `409` while it still has queued submissions,
`403` for a delegated (agent) caller. See [Manage your chats](/how-to/chat-controls).

`GET /api/chat/marks` → `{ pinned: [row], hidden: [row] }` · `POST /api/chat/marks`
`{ row, pinned?, hidden? }` → the same shape: pins or hides one row of the caller's own rail. Setting a mark
needs a row the caller can see (their own chat, or a meeting they can read) — otherwise `404`; clearing one
does not. A request with neither flag, an unknown field or more than 5000 marks is a `422`.

`GET /api/chat/pending?session=&after=` → `{ pending: [{ entry, id, kind, target, display, at, blocked? }], cursor, taken?, fault? }`:
what the chat submitted that its agent has not taken yet. When a typed fault is stopping the queue,
each row carries it as `blocked` and the top level once more as `fault`; it clears the moment the agent
takes anything. `after` is an output-stream id (`<ms>-<seq>`, anything else is a `422`); with it,
`taken` counts the turns the agent has started since that id. A client whose stream just ended passes
its last event id: a message the agent took the moment the previous turn ended is no longer pending,
and `taken` is what tells the client to attach and watch it.

A streamed `/api/chat` view stays open until every turn that started on it has sent `turn-complete`.
Two turns can share one view (the agent takes the next message while it finishes the previous turn's
write-back); every worker event carries its `turn_id`, so a client can tell them apart.

## Routines

<Warning>
Deprecated, and removed in 0.14.0. A routine is a flow of your own: make one with `POST /flows` or
`flows_submit` ([Routines and agent messages](/flows/routines)). Until 0.14.0 these routes are an
adapter onto your flows, kept for installs that are upgrading. Every answer carries
`Deprecation: true` and `Link: </flows>; rel="successor-version"`. On a deployment without flows
they answer `501` with `routines_need_flows`.
</Warning>

```bash POST /api/routines  → 201
curl -X POST "$API_BASE/agent/routines" -H "Content-Type: application/json" \
  -H "X-API-Key: $VEXA_API_KEY" -d '{
  "name":"Morning brief","cron":"0 8 * * 1-5",
  "prompt":"Brief me from overnight activity."
}'   # → {"routine":{...},"job_id":null,"ran_now":false,"flow":{...}}
```

`POST` writes a schedule flow with the `agent_run` step in your own scope; `run_now` has no effect
(the routine first runs at its first slot, in its own thread). Made with an API key or by an agent,
it is filed as a draft that you turn on from the app. A refusal from flows comes back with its typed
reason (for example `quota_min_interval`).

`GET /api/routines` → `{ "routines": [...] }`: your schedule flows, plus any old routine file that
could not be converted, with its reason ·
`PATCH /api/routines/{name}/enabled` `{ enabled }` pauses or resumes the flow. Resuming
(`{"enabled": true}`) takes your signed-in session; an API key or an agent gets `403`
`person_approval_required` ·
`DELETE /api/routines/{routine_id}` retires it ·
`POST /api/routines/{name}/confirm` → `410` `routine_files_retired`: routine files are no longer
confirmed or read.

## Events

`POST /events` — body is an `event.v1` Event (an integration firing). It maps to a `unit.v1` Invocation
and dispatches. `400` if non-conformant; `422` if the event carries no plan.

```bash POST /events  → 202
curl -X POST "$AGENT_API/events" -H "Content-Type: application/json" -d '{
  "name":"email.received","subject":"u_jane",
  "source":{"uri":"mailbox://u_jane/INBOX/AB12CD"},
  "plan":{"prompt":"Triage this email into tasks."}
}'   # → {"workload_id":"agent-...","trigger":"event"}
```

## Live meetings

- `GET /api/meeting/stream?meeting_id=&session_uid=` (SSE) → the meeting's live transcript feed,
  owner-scoped. Resumable: every event carries an SSE `id:`; on reconnect echo it as `Last-Event-ID`
  to resume gaplessly. Event types: `transcript`, `retract`, `ping`, `meeting-end`.
- `GET /api/meeting/relay-health` → typed transcript-relay health (a stale bot key surfaces as
  `native_resolve:{ok:false,kind:"unauthorized"}` rather than silent dead air).
- `POST /api/meeting/terms/scan` `{ meeting_id, since?, keep? }` → the terms the meeting has named
  since `since`, each with `known` (the page this reader can open, personal workspace first) or `null`, plus
  `cursor` and `emit`. Without `keep` it publishes nothing; `keep` (comma separated, `*` for all) adds
  those terms to the meeting's highlight map, which `GET /api/meeting/terms?meeting_id=` returns.
  The transcript is read from meeting-api as the caller: `403` for a meeting they cannot read,
  `502` when the read fails.

**Removed in 0.12** — `POST /api/meeting/start` and `POST /api/meeting/process` return `404`. They
launched and switched on an in-product "copilot" that turned the live transcript into cleaned notes
and cards on a second lane of this same stream. Vexa runs no model calls of its own beside the agent:
ask about a meeting with `POST /api/chat`, passing
`active: {"kind":"meeting","meeting":{…}}`. See [Follow a live meeting](/how-to/live-copilot).

## Workspace

`GET /api/workspace/tree?hidden=` → `{ "files": ["kg/entities/..."] }` ·
`GET /api/workspace/file?path=` → `{ "path": "...", "content": "..." }` (`404` if absent) ·
`PUT /api/workspace/file` `{ path, content, slug? }` → `{ "path": "...", "written": true }` (commits;
`kg/templates/` is refused `403`, and `_global` needs the [admin account](/minutes/workspaces#the-admin-account)) ·
`POST /api/workspace/remove` `{ path, slug? }` → `{ path, deleted, workspace, commit }` (one page, as a
commit) · `POST /api/workspace/restore` `{ path, slug?, commit? }` → `{ path, restored, workspace,
commit, from_commit }` (puts back a removed page from the removal's parent, as a commit; `409` if a
file is at the path) · `POST /api/workspace/move` `{ path, to, slug?, to_slug? }` → `{ from, to, moved, pointer,
commit, source_commit }` (an omitted `to_slug` is the same workspace) ·
`POST /api/workspace/asset` `{ url, path?, slug? }` → the stored picture's `path` (the server fetches it) ·
`GET /api/workspace/git` → `{ branch, changes, commits }` ·
`GET /api/workspace/git/show?sha=&path=&slug=` → the unified diff of one commit ·
`POST /api/workspace/upload` (multipart `files`, ≤25 MB each) → `{ "files": [{ name, path, original, size, type }] }` (`name` is stored, `original` the uploaded name) ·
`GET /api/sessions/{session}/attachment?path=` → the bytes of a file attached to a message: the caller's own, or one posted in that session to its participants; `404` otherwise ·
`POST /api/workspace/init` → `201` `{ workspace, seeded, already_initialized }` (idempotent) ·
`GET /api/workspace/attached` → `{ active, parked }` ·
`POST /api/workspace/swap` `{ repo?, ref?, token? }` → attach an external git repo as the active
workspace (parks the current one; omit `repo` to swap back to the seed).

(All workspace routes derive `subject` from `X-User-Id` — no `subject` query parameter.)

On the page writes — file, remove, move, asset and entity — an omitted `slug` is where the conversation
is working: an agent worker's identity carries its chat's target workspace, and a caller with none
writes in its own personal workspace. `slug: "personal"` (or `"desk"`) names the personal workspace explicitly.

## Workspace identity and links

A workspace's id lives **in the workspace** — `.vexa/workspace.json`, ten characters of lowercase
base32 — and the server registry is the derived half, rebuildable by walking the root. Links are
written `[[ws:<workspace-id>/<entity-id>]]` with one canonical URL `/w/<workspace-id>/<path>`, so
renaming either the workspace or the page leaves them resolving.

`GET /api/workspaces/by-slug/{slug}` · `GET /api/workspaces/{workspace_id}` →
`{ id, name, kind, slug, access, writable }`, from this reader's point of view. `access` is
`readable` · `not-yours` · `gone`, and neither route 404s or 403s: a workspace you cannot see is an
**answer**, not an error, and a `gone` record still carries its last known name so a dead link renders
as its own title. A `not-yours` answer carries only what you asked with — `{ id: null, slug }` by slug,
`{ id }` by id — with `name` and `kind` null; members, instance admins and the admin account get the
full view. Links resolved through `POST /api/links/resolve` likewise name no workspace when it is
`not-yours`.

`POST /api/workspaces/{workspace_id}/rename` `{ name }` → the same view plus `renamed_from`. A group's
owner and instance admins only — `403` otherwise, including for a personal workspace's own owner; `404` unknown id,
`400` empty name. The rename is audited on the record.

`POST /api/links/resolve` `{ refs: [...], slug? }` →
`{ "results": [{ ref, title, url, access, workspace, writable }] }` — a whole page of refs in one round
trip, capped at 200. A readable ref with no file yet adds `missing: true` and still returns a `url`; a
resolved one adds `path` and `slug`.

`POST /api/desk/touch` `{ workspace, path }` → `202 { "recorded": true|false }`. The touch is filed
under the **caller's own** personal workspace, never a workspace named in the body; a workspace this caller cannot
read answers `recorded: false` rather than confirming it exists. `400` without both fields.

## Entities

`POST /api/workspace/entity` — the one write that makes a knowledge-graph page. Body
`{ kind, name, facts?, source?, summary?, fields?, section?, connections?, open_questions?, dates?, slug? }`;
`kind` is `person` · `company` · `meeting` · `project` · `decision`, and `slug` names the **workspace**
to write into (default: as for the other page writes above). It renders `kg/entities/<kind>/<slug>.md` as a card, writes
the reciprocal `## Connected` chips on the other page, refreshes `kg/INDEX.md`, and commits both by
pathspec.

Returns the upsert result — `path`, `created`, `changed`, `facts_written`, `links_resolved`,
`links_missing`, `links_rewritten`, `back_links`, `filed`, `kind`, `name` — plus `index` (the index
path) and `commit` (the sha, `null` when nothing changed). `403` for `_global`; `422` when the write is
refused, and the refusal sentence is the product — fix the fact rather than retrying.

## Claims

What an agent believes about a person's company is **proposed**, and is company context only once the
person has answered. `POST /api/claims` `{ claims: [{ claim, source?, scope? } | "…"] }` →
`{ ids, state: "proposed", show_them_exactly_this, then }`, and publishes `claim.proposed` once per new
claim (`400` on an empty list). `POST /api/claims/verdicts` `{ verdicts: [{ id, verdict, note? }] }` →
`{ recorded: [{ id, state, usable_as_context }], errors?, workspace_ready? }` — `verdict` is
`confirmed` · `corrected` · `rejected`; an unknown id or verdict is reported in `errors` and the rest
still lands. The first claim the person stands behind writes the personal workspace's `.scaffolded` marker.

## Rough edges

People report friction by telling the chat agent what did not work; the agent files it with the
`report_friction` tool. The terminal has no separate report control. The route below is what the
agent's worker and its harness post to.

`POST /api/friction` — body `{ kind?, severity?, tried?, happened?, would_help?, session?, context? }`;
the context keys `workspace` · `path` · `meeting_id` · `scaffold_id` · `tool` · `error` · `surface` are
also accepted flat. `session`, `tried` and `happened` must be present (`400` otherwise). `kind` is
`missing-tool` · `refusal` · `no-page` · `wrong-workspace` · `unfulfilled` · `error` · `ux` · `other`;
`severity` is `blocker` · `annoyance` · `papercut` · `idea`. Unknown keys are dropped and free text is
clipped and secret-scrubbed. This is the **one route here that files without an identified caller** —
`X-User-Id` is recorded when present and never required.

agent-api stores nothing: it forwards the report to flows' `POST /friction` and returns its answer,
`201 { id, recorded }`. When flows cannot be reached or refuses the report, the answer is
`{ "id": "", "recorded": false }`. When the same subject already filed the same report (same tool,
same refusal reason or same text once ids are removed) in the same UTC hour, flows counts it against
the first report instead of storing a new one, and the answer passes that through:
`{ id, recorded: false, duplicate_of, occurrences, instruction }`, where `instruction` tells the
reporter not to file it again this run. How reports are folded:
[Friction reports](/flows/operations#friction-reports-repeats-are-folded-into-one-row).

## Sharing, membership and invites

Membership is a file in the workspace's **own git repo** — `policy/members.json`, with invite token
hashes beside it in `policy/invites.json` — and the user-row index (`users.data.memberships[]`) is the
derived copy, so a grant survives a database loss and travels with the tree. Roles are `owner` >
`contributor` > `viewer`. On the invite and member routes `workspace_id` is a **query parameter**.

`POST /api/workspace/{slug}/share-enable` → `{ workspace_id, promoted }`, which is what lets any
workspace be shared after creation · `POST /api/workspace/shared/new` `{ name }` →
`201 { workspace_id, role, name }` · `POST /api/workspace/{workspace_id}/unshare` (owner) → `{ slug }`;
the id does not change, so links into it keep resolving and answer `not-yours` to everyone else.

`POST /api/workspace/invites` `{ workspace_id, role?, expires_in_sec?, max_uses?, mode?, allowed_emails? }`
→ `201 { id, token, role, workspace_id, expires_at, max_uses, mode, accept_path }`. `mode` is `open` or
`restricted` (redeemable only by the listed verified emails); the token is returned **once** and only
its sha256 is stored ·
`GET /api/workspace/invites/preview?token=` →
`{ workspace_id, name, purpose, role, mode, expires_at, shared_by, valid, reason }`, granting nothing
and consuming no use (`404` for a token matching nothing) ·
`POST /api/workspace/invites/accept` `{ token }` → the membership, in both stores; idempotent per user,
and the token carries no workspace id — it is resolved by hash ·
`GET /api/workspace/invites?workspace_id=` → `{ invites: [...] }`, hashes never surfaced ·
`DELETE /api/workspace/invites/{invite_id}?workspace_id=` → `{ ok, invite_id }`.

`GET /api/workspace/members?workspace_id=` → `{ members: [...] }` ·
`POST /api/workspace/members/{member_subject}/role?workspace_id=` `{ role }` → the member record
(owner) · `DELETE /api/workspace/members/{member_subject}?workspace_id=` → `{ ok, subject }` (owner) ·
`POST /api/workspace/invite` `{ slug, email, role? }` → the invite, mailed to an address this deployment
does not know or handed back as a link (owner) · `POST /api/workspace/membership`
`{ slug, email, role }` → the member's new role, or `remove` (owner; the last owner is refused `409`) ·
`POST /api/workspace/{workspace_id}/leave` → `{ ok, left }` — any role, but the last owner is refused
`409` and must hand off or unshare · `GET /api/workspace/shared` →
`{ memberships: [...], index_degraded }`, the **union** of both stores, with `index_degraded: true`
when the derived index could not be read.

`POST /api/workspace/shared/{workspace_id}/attach` `{ repo?, ref?, slug?, token? }` →
`{ workspace_id, active, repo, ref, attached, cloned, parked, state }` — contributor or owner
only; the current tree is parked, and `policy/` is carried into the new one so an attach cannot lock
the group out · `GET /api/workspace/shared/{workspace_id}/attached` → the attachment view plus `home`
(`remote`, `url`, `branch`, `ahead`, `behind`) and `credential`, which says what kind of credential
exists and never its value · `POST /api/workspace/shared/{workspace_id}/active` `{ active }` →
`{ workspace_id, active }`, a per-user mount preference; membership is unchanged. Switching ON
needs membership in the roster (`403` otherwise); switching OFF is open to anyone, since it only
edits the caller's own set — it is how a client clears a workspace the caller was removed from.

## Workspace slots and the active set

`GET /api/workspace/active` →
`{ subject, active: [{ slug, repo, ref, role, path, write, primary, name }], index_degraded }` — the
ordered set the next dispatch mounts ·
`POST /api/workspace/activate` `{ repo?, ref?, slug?, token? }` → `{ subject, slug, changed, cloned }`,
additive: nothing else is parked ·
`POST /api/workspace/new` `{ name? }` → `201 { subject, slug, changed, added }` (blank, seeded) ·
`POST /api/workspace/deactivate` `{ slug }` → `{ subject, slug, changed }` — parks it, never destroys ·
`POST /api/workspace/rename` `{ slug, name }` → the slot's display label only; the slug and parked tree
do not move ·
`GET /api/workspace/purpose?slug=` and `POST /api/workspace/purpose` `{ slug?, purpose }` →
`{ purpose }`, stored in the workspace and committed so it travels when shared ·
`POST /api/workspace/{slug}/archive` `{ archived }` → `{ slug, archived }` ·
`DELETE /api/workspace/{slug}` → `{ slug, deleted: true }`, irreversible; the baseline is refused ·
`POST /api/workspace/reset` `{ target }` → `{ target, reset: true }` for `personal` or `_global` (admin
account only) — the slot survives and the content returns to the seed. `_system` is never resettable.

## Git remotes, deploy keys and publish

Credentials are resolved **server-side** — the workspace's own deploy key, or the caller's saved token
— and errors are scrubbed by **shape** before they leave: known token families, credentials wearing a
URL, and any long opaque run, whether or not the caller passed the secret in.

`GET /api/workspace/git-token` → `{ set, masked }` · `POST /api/workspace/git-token` `{ token? }` → the
same shape; an empty token clears it, and the clear value is never returned ·
`GET /api/workspace/{slug}/deploy-key` → `{ slug, public_key, fingerprint, add_as }` (`public_key` is
`null` until one is generated; the private half has no read path at all) ·
`POST /api/workspace/{slug}/deploy-key` `{ repo? }` → the key plus where to add it, idempotent, so a key
already added to a repository is never invalidated.

`GET /api/workspace/git-remote-status?slug=` → `{ has_home, remote, url, branch, tracked, ahead, behind }`
— no network, no token ·
`POST /api/workspace/push` `{ slug?, token? }` → `{ remote, url, branch, head_sha }`, fast-forward only,
never a force push; `400` when no credential resolves, naming the deploy-key route ·
`POST /api/workspace/pull` `{ slug?, token? }` → `{ remote, url, branch, head_sha, updated, behind_before }`;
a divergence is refused rather than merged, rebased or forced, and on a shared workspace a viewer is
refused because a pull rewrites the tree ·
`POST /api/workspace/publish` `{ repo_name?, private?, org?, remote_url?, slug?, token?, host? }` →
`{ repo_url, pushed_ref, head_sha, created }` — `host` is where a new repository is created:
`github.com` (default) or a GitLab host registered in `VEXA_GIT_PROVIDERS`, where `org` is a group path
(nested allowed); any other host is `422` naming it. `409` if the repo already exists, `502` on a push
failure, `400` with no token passed and none saved (a saved token is only used for GitHub).

Repository addresses may be nested (`group/sub/repo`) on any host but `github.com`. A per-call `token`
written `<user>:<token>` (for GitLab, `oauth2:<token>`) is sent with that account name; a bare token is
shaped by the host's provider. See [Repositories on GitLab](/minutes/workspaces#repositories-on-gitlab-or-another-self-hosted-server).

## The company layer

Optional. `_global` starts empty of company data and may stay that way: no request, sign-in, flow or
operator verb waits for it (founder ruling 2026-10-08). Unless `VEXA_GLOBAL_SYSTEM_WORKSPACE_PATH`
names a separate host repo, agent-api keeps `_global` in its own store and creates it empty at boot.

`POST /api/global/ready` `{ author_email?, author_name? }` →
`{ accepted, company, service, commit, files }` — accept a company layer the admin account chose to write.
Admin account only (`403`) and idempotent; it reads the files and commits them itself, authored by the
admin (the caller's own address unless the body names another) — nothing may mark itself accepted. A layer that is not complete answers
`409 { accepted: false, missing_files, reasons, next }`. It gates nothing.

## Scaffolds

`POST /api/scaffolds/hand` `{ preset, meeting? }` → `201 { id, url }`. `preset` is a **name** in
`_global/asks/`, never prompt text; the recipient is the signed-in caller, and there is no `who` field;
`meeting` must be a row this caller can open. `400` unknown preset, `401` no subject, `404` a meeting
that is not theirs, `409` a session carrying no address, `503` when `VEXA_UI_URL` is unset.

`GET /api/scaffolds/{scaffold_id}` → the record as its recipient, with the opening already substituted
server-side: `id`, `kind`, `who`, `meeting`, `native`, `phase`, `workspaces`, `refs`, `opening_preset`,
`opening_label`, `opening_text`, `tabs`, `focus`, `header`, `provenance`, `provenance_line`,
`minted_at`, `redeemed_at`, `redeemed_by`. Marks the record redeemed on first read. `404` for an
unknown id **and** for one that is not yours — the id is a capability, so a `403` would confirm it
exists; `409` when the preset it was minted against has been deleted.

`GET /api/scaffolds?pending=` → `{ scaffolds: [...] }`, indexed by the caller's gateway-injected
address. No address → an empty list, never every scaffold on the instance. (A `mine` parameter is
accepted and has no effect — the listing is always the caller's own.)

`POST /internal/scaffolds` is internal — it is not under `/api/`, so it has no gateway path.

## Admin and config probes

`GET /api/admin/overview` → `{ workloads, meetings }`, each replaced by `workloads_error` /
`meetings_error` when that section fails · `POST /api/admin/probe` → the transcription-pipeline smoke
probe (gateway → meeting-api → runtime → redis carriers → relay); POST because it writes and reads
scratch keys. Both are **internal tier**: the caller sends `X-Internal-Secret` matching
`VEXA_INTERNAL_API_SECRET`, and an unconfigured secret means nobody gets in (`403`), whichever ingress
they arrive on.

`GET /api/models/test` → `{ ok, summary, mode, route, config }`. Tests the route the caller's turns
take now. `route: subject` is the caller's own custom endpoint, when it passes the deployment's
allow-list: it is probed with the caller's own key, model and extra body. `route: deployment` is every
other case, probed with the deployment's credential only. `mode` says how: `custom` makes a real
one-token completion against the endpoint, `subscription` checks the mounted credentials for expiry. A
stored key that is not in effect is never sent, and the summary says that nothing of the caller's was
tested. `config` echoes only `mode`, `model` and `base_url`.

With a [model catalog](/model-catalog), `GET /api/models/test?model=<id>` tests that catalog model
(the caller's default when `model` is absent). The response is
`{ ok, summary, mode: "catalog", model, provider, harness }`.

- It resolves the route a turn on that model would take, through the same provider port.
- It probes that route in its own dialect, at the URL the harness posts to, with exactly that route's
  credential.
- A model the caller cannot use answers `ok: false` with its `fault`.

`GET /api/transcription/test` → `{ ok, summary, source }` (plus per-failure detail). Probes the
effective STT backend with its token and then a real transcribe, so a zero-balance account fails here
rather than on every segment; `source` says whether settings or the deployment env was tested.
It tests the URL and token a bot spawned now would use.
- **Your URL in settings:** your URL is probed with your token, and with none if you set none.
- **No URL of yours:** the deployment's URL is probed with the deployment's token.
- **Never mixed:** a deployment token never goes to your URL, and your token never goes to the
  deployment's URL.

## Repository imports

`POST /api/workspace/import` accepts `repo`, optional `ref` (default `main`) and an
optional one-off `token` from the authenticated UI. It returns HTTP 202 with an
`operation_id` and `status`. Credentials are never included in the persisted operation.

Poll `GET /api/workspace/import/{operation_id}/status`. States are `queued`, `running`,
`completed`, `failed`, and `interrupted`. Only `completed` includes a usable `result`
with the workspace slug, repository and ref. Status is scoped to the caller. Repeating
the same repository/ref recovers the operation; a different import while one is
running returns 409. Status survives an agent-service restart, but an unfinished
operation is marked interrupted rather than automatically replayed.

The MCP equivalents are `workspace_import(repo, ref, credential_workspace?)` and
`workspace_import_status(operation_id)`. They use configured server-side credentials
and expose no token argument. The HTTP routes own their schemas and descriptions.

If a deploy key is already registered for another workspace you own, pass its slug as
`credential_workspace`. The server verifies ownership before using the key and saves
the reference for later Git operations; it does not copy the key or grant access.

### Request a secure connection

The agent domain's Connections tools are served by the gateway's one MCP server
(`core/agent/mcp.tools.v1.json`): `connection_request(provider, label?, new_account?, setup?)`,
`connections_status()`, the reads `gmail_search` · `gmail_read` · `gmail_thread` ·
`calendar_events` · `mail_inbox` · `mail_read`, the drafts `gmail_draft_create` (a reply in a
thread, Cc, Bcc, workspace attachments) · `gmail_draft_update`, the calendar changes
`calendar_event_create` · `calendar_event_update` · `calendar_event_cancel`, the policy
`connection_policy_get` · `connection_policy_set`, `secret_service_call` and `onboarding_research`. Each is one `/api/connections/*` or
`/api/onboarding/research` route with a typed body; a meetings-only installation does
not expose them, and without a credential broker they answer that Connections are not
configured (`onboarding_research` with `action: status` still reports stored progress, because it
reads no account). A worker dispatched without a person in the loop is refused `connection_request`,
`connection_policy_set`, `secret_service_call` and `onboarding_research`; the mail and calendar
tools follow the administrator's `connection_actions_unattended` policy, which refuses all of them
by default ([Connections → the policy](/connections#what-an-agent-may-do-the-policy)). What onboarding research reads, its receipts and its failure
modes are on [Onboarding research and Extend](/how-to/onboarding-research).

A request returns a connection reference and `awaiting_user` or an existing
`ready` status. Minutes opens **Connections** on the right, where the user chooses
**Continue with Google** and grants read-only consent. Agents must never request
passwords, tokens or authorization codes in chat. `ready` means authorization was
stored; it does not establish that email ingestion or Calendar auto-join is active.


## How it works

1. **Presence.** The gateway registers the agent routes from `core/agent/routes.v1.json` only when
   `AGENT_API_URL` is set. Without it (the no-agents profile) every `/agent/*` path is `404`.
2. **Forward.** Public `/agent/<path>` maps onto agent-api's `/api/<path>`. 54 rows are declared:
   literal routes (two of them, `/agent/chat` and `/agent/meeting/stream`, streamed as server-sent
   events) and a `{path:path}` catch-all for each of five methods, all with scopes `bot` + `tx`.
3. **Identity.** The gateway resolves the key, strips client-sent identity headers and signs the
   identity it stamps. agent-api believes `X-User-Id` only with a valid signature.
4. **Workers.** A worker's delegation token is admitted only on the MCP re-entry rows (one per route a
   tool in `mcp.tools.v1.json` calls) and on `POST /agent/friction`. Any other REST call with it is refused.
5. **Person verbs.** The 49 `verbs` rows mark agent-api routes that need a person in the loop.
   `control_plane/route_policy.py` refuses a worker dispatched without one, before the handler runs.
