The Meetings API covers a meeting's whole life: **plan** it ahead (or import it from a calendar),
**send a bot** into the call (or let auto-join do it), and read the **transcript in real time**. It
is the public Vexa API — the same surface whether you use the hosted service or self-host.

## Base URL & auth

| | |
|---|---|
| Hosted | `https://api.cloud.vexa.ai` |
| Self-hosted | `http://localhost:18056` (the gateway; `API_GATEWAY_HOST_PORT`, default `18056`) |

Every request carries your key:

```bash
-H "X-API-Key: <API_KEY>"
```

**Don't have a key yet?** Hosted: sign in at [vexa.ai/signin](https://vexa.ai/signin) with a Google
account and copy your key from [your account page](https://vexa.ai/account) — free credit, no card
required. Self-hosted: `make all` prints a key when the stack comes up.

## Platforms

Pass one of these as `platform`:

| Platform | `platform` value |
|---|---|
| Google Meet | `google_meet` |
| Zoom | `zoom` |
| Microsoft Teams | `teams` |
| Jitsi Meet | `jitsi` * |
| Voice note (no meeting) | `voice_note` |
| Call in Minutes (a LiveKit room on this deployment) | `vexa_call` |

The bot joins like any participant — no plugins, no host configuration.

A **`voice_note`** joins nothing: `POST /bots {"platform": "voice_note"}` (no `meeting_url`,
`passcode` or `teams_base_host`; `native_meeting_id` is minted as `vn-…` when omitted; optional
`speaker_name`) makes the meeting and its bot, and the audio is then streamed over
`WS /voice-notes/{native_meeting_id}/stream`. Everything else — status, transcript, stop, delete —
is a meeting's. See [Voice notes](/minutes/voice-notes#how-it-works) for the socket protocol.

A **`vexa_call`** is a room meeting-api creates on the deployment's LiveKit server:
`POST /bots {"platform": "vexa_call", "session_id": "s-…"}`. Send no `meeting_url`, `passcode`,
`teams_base_host` or `native_meeting_id`: the room name (`call-…`) is minted and becomes the
`native_meeting_id`. `session_id` (optional) names the chat the call belongs to. `transcribe`
(optional boolean, default `true`) may be `false` only when the deployment sets
`CALL_TRANSCRIPTION_SWITCHABLE=true`; otherwise `false` answers `422`. A deployment without a LiveKit
server answers `503` with `{"error": "calls_not_deployed"}`. See [Calls](/minutes/calls#how-it-works).

\* **Jitsi is join + capture offline-proven; live validation is pending.** Meet, Zoom and Teams are
production. On Jitsi the bot joins and records audio, but transcripts are not yet proven live —
[#883](https://github.com/Vexa-ai/vexa/issues/883) reports a witness run on self-hosted
docker-jitsi-meet where the speaker binder matched **0 of 122** frames and the meeting completed
with 0 transcript segments. Track [#570](https://github.com/Vexa-ai/vexa/issues/570).

For `teams`, a meeting is addressed either by its **numeric meeting ID** (10–15 digits, the one
Teams prints beside a passcode) or by the **thread id** from a `…/l/meetup-join/19:meeting_…@thread.v2`
link. With the numeric ID, send the passcode as `passcode` — the bot joins at
`…/meet/<id>?p=<passcode>`, and the passcode is kept off the stored `constructed_meeting_url` and
out of the logs. Add `teams_base_host` for a non-default cloud (`teams.live.com` for personal
meetings, `gov.teams.microsoft.us` / `dod.teams.microsoft.us` for GCC-High and DoD); hosts outside
the Teams web clients are rejected with `422`. Sending the full `meeting_url` settles host and
passcode together.

Only `passcode` is read. `password`, `meeting_password` and similar aliases are rejected with a
`422` naming the right field, rather than accepted and dropped.

For `jitsi`, the full `meeting_url` is **required** (like Zoom): a Jitsi room name is scoped
to a deployment — `MyRoom` exists on meet.jit.si *and* on every self-hosted instance — so only
the URL says which one to join. The `native_meeting_id` reflects that scoping: the bare room
name on meet.jit.si (`MyRoom`), and `room@host` on any other deployment
(`MyRoom@video.example.org`) — so same-named rooms on different deployments never collide.
A password-protected room is joined by passing the optional `passcode` field. To make
**calendar sync** recognize a self-hosted deployment's links, list its hostnames in the
`VEXA_JITSI_HOSTS` env (comma-separated). On Jitsi speaker names come from the conference's own
dominant-speaker signal.

A `meeting_url` must be an `https://` link on its platform's hosts: Google Meet on
`meet.google.com`; Teams on `teams.microsoft.com`, `teams.live.com`, `teams.microsoft.us` or
`teams.cloud.microsoft`; Zoom on `zoom.us` (vanity `<org>.zoom.us` included), `zoom.com` or
`zoomgov.com`, or an organisation's own Zoom front door when the link has Zoom's join shape; Jitsi
on any deployment. Every address the host resolves to must be public, so a link that points at, or
resolves to, a loopback, private, CGNAT, link-local or cloud-metadata address is refused with a
`422` naming the host. A host the API cannot resolve is passed to the bot, whose browser resolves it and holds it to the same rule. A Jitsi server inside your own network joins once the operator lists it in
`VEXA_MEETING_HOST_ALLOW` ([Configuration](/configuration)). The bot's browser holds every
navigation and redirect to the same rule; a refusal there fails the join with a reason starting
`meeting_host_refused`.

On **Google Meet** and **Jitsi** the transcript also carries the meeting's **chat**: each chat
message from another participant arrives as a segment with `source: "chat"` (the sender is the
`speaker`). Read it alone with `GET /bots/{platform}/{native_meeting_id}/chat`, follow it live as
`chat_message` frames on `/ws`, and post into it with `POST /bots/{platform}/{native_meeting_id}/chat`
(the native-id support table below has each answer). On Meet the bot opens the
chat panel itself and reads only lines sent after it joined.

## Meeting statuses

A meeting is **one record from plan to transcript**:

| Phase | `status` values | Who owns it |
|---|---|---|
| Planned (intent) | `idle` (no time) · `scheduled` (time set) | you — freely editable |
| Live (bot FSM) | `requested` · `joining` · `awaiting_admission` · `needs_help` · `active` · `stopping` | the bot lifecycle |
| Terminal | `completed` · `failed` | — |

Sending a bot to a planned meeting (yours or auto-join's) **upgrades the same record in place** —
its title, workspace binding, and transcript stay together. `PATCH`/`DELETE` work only while the
record is still planned; once the bot lifecycle owns it they answer `409`.

## Plan a meeting

Create a meeting **before it happens** — no bot is spawned. All fields are optional: a plan can be
just a title, and the link can be attached later.

<ParamField body="title" type="string">What the meeting is about — shown in the Meetings list.</ParamField>
<ParamField body="scheduled_at" type="string">ISO-8601 start time. Present → status `scheduled` (and [auto-join](#auto-join) arms); absent → `idle`.</ParamField>
<ParamField body="meeting_url" type="string">A Meet/Zoom/Teams link — parsed server-side into `platform` + `native_meeting_id`. Unrecognized links are rejected with `422`.</ParamField>
<ParamField body="workspace_id" type="string">Bind the meeting to a shared workspace — its members then see the meeting, its live feed, and the transcript. You must be a member (`403` otherwise). `personal` keeps the meeting yours alone. Omitted, a bot an agent worker sends belongs to the shared workspace its chat is working in, when you are a member of it; any other caller's meeting stays private.</ParamField>
<ParamField body="auto_join" type="boolean">Send the bot automatically at start time. Default `true`.</ParamField>

```bash POST /meetings
curl -X POST "$API_BASE/meetings" \
  -H "X-API-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{"title":"Q3 kickoff with Acme","scheduled_at":"2026-07-10T15:00:00Z",
       "meeting_url":"https://meet.google.com/abc-defg-hij","workspace_id":"ws-acme"}'
```

Returns `201` with the meeting record. `409` when a non-terminal meeting already exists for the
same link.

### Edit a plan or delete meeting artifacts

Planned meetings are addressed **by record id** (a plan without a link has no platform/native
path). Send only the fields you're changing; `null` clears a field (`scheduled_at: null` flips the
status back to `idle`, `meeting_url: null` detaches the link, `workspace_id: null` unbinds).

```bash PATCH /meetings/{meeting_id}
curl -X PATCH "$API_BASE/meetings/12345" \
  -H "X-API-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{"scheduled_at":"2026-07-10T16:00:00Z","auto_join":false}'
```

```bash DELETE /meetings/{meeting_id}
curl -X DELETE "$API_BASE/meetings/12345" -H "X-API-Key: $API_KEY"
```

`PATCH` is plan-only. `DELETE` has two deliberately distinct meanings:

- For an `idle`/`scheduled` plan, it deletes the plan row.
- For a `completed`/`failed` meeting, it deletes durable transcript rows, transcript-derived
  notes/shares, recording objects from primary object storage, and recording metadata. The terminal
  meeting row remains as lifecycle evidence, but transcript reads return `404`.

Both answer an owner-indistinguishable `404` for an unknown or unowned record.

**Deleting a meeting whose bot is still running or finishing** answers `409` by default, as 0.12 did.
With `VEXA_MEETING_DELETE_LIVE=stop` on meeting-api it answers `202` with
`{"status":"deletion_scheduled","id":…}`. The request is recorded on the meeting, the bot is asked to
leave (the same stop as `DELETE /bots/{platform}/{native_meeting_id}`), and the transcript and
recordings are deleted when the meeting's lifecycle ends. A meeting that ends without a bot callback
(for example, one ended by a sweep) keeps the request; deleting it again then deletes at once,
because it is terminal.

The same edit/delete is also reachable **by native key** — `PATCH`/`DELETE
/meetings/{platform}/{native_meeting_id}` — which resolves `(platform, native_meeting_id)` to your
newest owned row and applies the same rules (`404` unknown/unowned; `PATCH` answers `409` while in
flight, `DELETE` answers `409`, or under `stop` `202` with `deletion_scheduled`, plus `platform` and
`native_meeting_id`).
Use it when you address meetings by their join-link identity rather than the record id; a finished
`DELETE` answers `200` on this path (the by-record-id `DELETE` answers `204`).

<Warning>
Deletion confirms erasure from the live Postgres/Redis state and configured primary object storage.
It does **not** claim immediate erasure from database snapshots, object-store version history, or
other backups; those residuals expire under the operator's deployment retention policy.
</Warning>

### Set the planned status by native key

`PUT /meetings/{platform}/{native_meeting_id}/intent` writes only the two **user-owned** statuses —
this is the route a dropdown drives, where `PATCH` is the route a form drives.

```bash PUT /meetings/{platform}/{native_meeting_id}/intent
curl -X PUT "$API_BASE/meetings/google_meet/abc-defg-hij/intent" \
  -H "X-API-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{"intent":"scheduled","at":"2026-07-10T15:00:00Z"}'
```

| Field | Rule |
|---|---|
| `intent` | `idle` or `scheduled` only. Any FSM-owned status (`requested`, `active`, `completed`, …) is refused with `422`. |
| `at` | ISO-8601 string. **Required** when `intent` is `scheduled`; ignored for `idle`. |

Returns `200` with `{meeting_id, status, scheduled_at}`. `404` for a record you don't own. The write
is idempotent — setting the status it already holds changes nothing and emits no WebSocket frame.

### Bind a meeting to a shared workspace

`POST /meetings/{platform}/{native_meeting_id}/workspace` sets the meeting's `workspace_id`. Members
of that workspace can then subscribe to the meeting's live transcript feed. Many meetings may point
at one workspace.

```bash POST /meetings/{platform}/{native_meeting_id}/workspace
curl -X POST "$API_BASE/meetings/google_meet/abc-defg-hij/workspace" \
  -H "X-API-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{"workspace_id":"ws-acme"}'
```

Returns `200` with `{"workspace_id": "ws-acme"}`. `422` when `workspace_id` is missing or empty;
`404` for a record you don't own. `POST /meetings` accepts the same binding at creation time.

Binding takes **edit access** to the workspace (role contributor or owner): it publishes the meeting to
every member. A caller who can only view the workspace, or is not a member, gets `403` — on this route,
on `POST /meetings` and `PATCH /meetings/{id}` with a `workspace_id`, and on `POST /bots` with one.
Unbinding (`workspace_id: null`) is always allowed on your own meeting.

### Share a meeting

A meeting is shared with a **share grant**: a capability the owner mints and a signed-in person
redeems. Redeeming adds them to the meeting's readers. A reader gets the meeting in `GET /meetings`
(with `shared: true`), its detail, its transcript (`GET /transcripts/by-id/{id}`), its live feed (the
terminal's stream and `/ws`), and its recording only when the owner allows it. The owner manages
grants and readers with the routes below. All of them take the meeting's row id and need the `tx` scope.
A meeting that isn't yours returns `404`, exactly like one that doesn't exist.

| Route | What it does |
|---|---|
| `POST /meetings/{meeting_id}/share` | Mint a grant. Body: `{mode, allowed_emails?, expires_in_sec?, notify?}`. Each `allowed_emails` entry must be exactly one address (`422` otherwise). With `notify: true` — only for a `restricted` grant with exactly one address, at most 30 per owner per hour (`429` past that, before anything is minted) — that address is emailed its own link by the deployment's mail service, minted at send time; the answer carries `notified: {address: true\|false}`, whether that email was handed over. No token leaves meeting-api in the email fact. `mode` is `restricted` (only the listed verified addresses can redeem it) or `open` (any signed-in person can). The TTL is clamped to 60 s–30 days. Returns `{id, token, mode, expires_at}`, and the `token` appears **only in this response**. |
| `POST /transcripts/share/accept` | Redeem a token as the signed-in caller: `{token}` → `{meeting_id, ok}`. `403 not_allowed` for an address not on a restricted grant, `403 revoked` / `403 expired` for a withdrawn or lapsed grant, `404` for an unknown token. |
| `GET /meetings/{meeting_id}/access` | Who can read the meeting: `{people:[{user_id, email, role:"viewer", grant_id, since}], invites:[{id, ids, emails, expires_at}], links:[{id, joined, expires_at}], workspace_id, recording}`. One invite row per pending address; `ids` lists every live grant behind it (withdraw them all to withdraw the invite). Carries no tokens or hashes. |
| `PATCH /meetings/{meeting_id}/access` | `{recording: true\|false}`: whether readers may play and download the recording. The default is `false`. Returns the access view. |
| `DELETE /meetings/{meeting_id}/share/{grant_id}` | Revoke a grant (a pending invite or a link). Anyone who joined through it loses access immediately, unless another live grant they redeemed still admits them; turning off an OPEN link also removes readers with no record of how they joined. Returns the access view; `404` for an unknown grant. |
| `DELETE /meetings/{meeting_id}/viewers/{viewer_id}` | Remove a reader. REST reads return `404` at once; an open live stream ends within about 17 seconds on the terminal stream (`access-revoked`) and about 15 on `/ws` (`subscription_revoked`, matched by the meeting row being streamed). A grant minted before the removal no longer admits them. A new invite does. |

```bash Invite one person, then remove them
curl -X POST "$API_BASE/meetings/42/share" -H "X-API-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{"mode":"restricted","allowed_emails":["ana@example.com"],"expires_in_sec":2592000}'
curl "$API_BASE/meetings/42/access" -H "X-API-Key: $API_KEY"
curl -X DELETE "$API_BASE/meetings/42/viewers/1187" -H "X-API-Key: $API_KEY"
```

Recording reads (`GET /recordings/{id}`, `…/master`, `…/media/{media_file_id}/raw`) serve a reader the
recordings of a meeting shared with them only while that meeting's `recording` setting is `true`, and
until then the reader's meeting and transcript responses carry no recording metadata either.
`GET /recordings` stays a list of your own recordings unless you pass `meeting_id`.
Deleting a recording stays owner-only. The terminal flow is described in
[Share a meeting](/how-to/share-a-meeting).

## api.v1 native-id support (per route)

`api.v1` is sealed as a **file hash** (`contracts.seal.json`), which pins the schema document, not
the running implementation. This table states, per route, whether the `(platform,
native_meeting_id)` keying a 0.10 client uses is served by the 0.12 core:

| Route | Native-id keying in 0.12 |
|---|---|
| `PATCH /meetings/{platform}/{native_meeting_id}` | **Yes** — resolves to your newest owned row. |
| `DELETE /meetings/{platform}/{native_meeting_id}` | **Yes** — `200` on success (by-id path is `204`). |
| `GET /bots/status` | **Yes** — body carries both `running_bots` (0.10) and `running`/`count` (0.12). |
| `POST /transcripts/{platform}/{native_meeting_id}/share` | **Aliased** to the moved `POST /meetings/{platform}/{native_meeting_id}/share` mint. The response is the capability-token share (`{id, token, mode, expires_at}`), not the 0.10 public-URL `TranscriptShareResponse` — the public-URL-share backend is not in the 0.12 core. |
| `GET /recordings/{recording_id}/media/{media_file_id}/download` | **Aliased** to the `.../raw` master byte stream (Range-capable). |
| `GET /bots/{platform}/{native_meeting_id}/chat` | **Yes** — the chat the bot captured in your newest owned meeting on that link, oldest first, as `{messages: [{sender, text, timestamp, is_from_bot}]}` (`timestamp` in epoch milliseconds). It is the transcript's `source: "chat"` segments, so it holds only what the platform's chat reader captured (Google Meet and Jitsi). `is_from_bot` is always `false`; the bot's own lines are not captured. Each new line also arrives live over `/ws` as `{"type": "chat_message", "meeting": {id, native_id, platform}, sender, text, timestamp, is_from_bot}`. |
| `POST /bots/{platform}/{native_meeting_id}/chat` | **Yes, on Google Meet and Jitsi** — body `{"text": "…"}`, at most 2000 characters; only the meeting's owner can send. Hands the line to your bot in that meeting and answers `200 {"status": "queued", "request_id", "meeting_id", "native_meeting_id"}`: the bot received it. Whether the line then showed in the meeting's chat is read with `request_id` from the route below. `404` with no live meeting, `409` before the bot is admitted or when no bot is listening, `429` past 10 messages in 10 seconds to one meeting (whoever sends them; the `Retry-After` header says when to retry, and nothing was sent), `422` for empty or too-long `text`, an unknown platform, or a platform whose bot cannot send chat (Zoom, Teams), `503` when the command bus is down (nothing was sent, retry). |
| `GET /bots/{platform}/{native_meeting_id}/chat/{request_id}` | **Yes** — whether one line sent with the route above posted: `{"request_id", "status", "reason"?, "meeting_id", "native_meeting_id"}`. `status` is `queued` until the bot reports, then `posted` once the line shows in the meeting's chat, or `failed` with `reason` (`no_composer`: no chat box; `not_landed`: sent but never appeared; `no_chat_api` or `page_error`: the page could not send; `unsupported_platform`; `empty_text`; `unknown`). A line still `queued` 60 seconds after it was sent reads `unconfirmed`: the bot's answer is not coming (a bot older than this release never answers). Only the sender can read it, for one hour; any other id, or this one under another meeting, is `404`. |
| `POST /meetings/{meeting_id}/transcribe` | **Not implemented** — no on-demand re-transcribe backend in the 0.12 core. |

<Note>
**What the seal enforces now.** Because the file hash pins the *document* and not the *running
implementation*, CI now also runs a **reverse** conformance check (`gate:contract-conformance`): for
every `(path, method)` `api.v1` declares, the shipped gateway + meeting-api must serve it — otherwise
the route must be recorded in the audited `core/gateway/contracts/api.v1/KNOWN_GAPS.json` ledger (with
a reason + issue link), which the gate prints loudly on every run. A sealed endpoint renamed or dropped
without a ledger entry fails CI. The frozen golden examples are also driven against the real responses,
so a renamed response field (e.g. `running_bots` → `running`) fails too. The two **Not implemented**
rows above and the share **response-shape** divergence are the current recorded gaps — a client can rely
on the seal meaning "served, or explicitly listed as a gap", not merely "the schema file didn't change".
</Note>

## Auto-join

A `scheduled` meeting **with a link** is joined automatically: a background sweep sends the bot
~60 s before `scheduled_at` (never more than 10 min after — a stale plan is skipped, not joined
late). Opt out per meeting with `auto_join: false`. Failures are loud: a concurrency-cap or spawn
failure stamps `auto_join_error` into the meeting's `data` and retries after a backoff. Timing is
tunable on a self-host — see [Configuration](/configuration).

## Calendar sync

Connect up to ten named ICS feeds through the [Calendar API](/api/calendar). Each connection owns
its auto-join policy and bot name. Sync imports every upcoming event as a planned meeting: events
with Meet/Zoom/Teams links are armed for auto-join, while link-less events remain visible with
`platform: "unknown"` until a link appears.

Imported rows retain normalized scheduling/participant fields and the complete per-source ICS
snapshot under `data.calendar_sources[].event`. Moves, cancellations, attendee changes, and custom
provider metadata follow the feed only while the meeting remains planned; calendar sync never
rewrites a meeting after the bot lifecycle claims it.

<Note>
The endpoints below are the **singular** compatibility routes, which address one feed. An account can
hold up to ten named connections, each with its own `auto_join` and `bot_name`, through
`/user/calendars` — the full contract is the [Calendar API](/api/calendar). New integrations should
use that.
</Note>

```bash PUT /user/calendar
curl -X PUT "$API_BASE/user/calendar" \
  -H "X-API-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{"ics_url":"https://calendar.google.com/calendar/ical/…/basic.ics","auto_join":true}'
```

See the [Calendar API reference](/api/calendar) for connection CRUD, per-connection sync endpoints,
request/response schemas, compatibility endpoints, error statuses, and metadata persistence. See
[Calendar sync](/how-to/calendar-sync) for Google Calendar and Outlook setup.

## Send a bot to a meeting

<ParamField body="platform" type="string" required>`google_meet` · `zoom` · `teams` · `jitsi` · `voice_note` · `vexa_call` (see [Platforms](#platforms)).</ParamField>
<ParamField body="native_meeting_id" type="string">The meeting id from the join URL (e.g. `abc-defg-hij`). Required for `google_meet` and `teams` unless `meeting_url` is sent. Optional for `voice_note`: omitted, a `vn-…` id is minted and returned. Refused with `422` for `vexa_call`, whose id is always minted.</ParamField>
<ParamField body="meeting_url" type="string">The full join link. Required for `zoom` and `jitsi`. Refused with `422` for `voice_note` and `vexa_call`.</ParamField>
<ParamField body="bot_name" type="string">Display name the bot uses in the call. Defaults to `Vexa`.</ParamField>
<ParamField body="language" type="string">Language code (e.g. `de`). **Set** = every STT call is pinned
to this code and every segment carries it. `"auto"` = each window's language is detected independently,
overriding the person's and the deployment's default. **Omitted** = the person's default (Settings), then
the deployment's, then auto. With `allowed_languages`, it must be one of them and is the fallback.
Granularity is the transcription window (a few seconds of one speaker's audio), not word-level; in auto
mode a low-confidence detection on the mixed-audio lane discards the window rather than guessing.
Undetermined windows yield `language: null`. See [Transcription language](/how-to/transcription-language).</ParamField>
<ParamField body="allowed_languages" type="string[]">Codes detection is restricted to (e.g. `["de","en"]`,
at most 16): a window detected outside the list is transcribed again in `language`, or in the first
entry. The meeting stores the setting it runs with as `data.transcription_language`
(`{language, allowed_languages, source}`). A refused value is `422`.</ParamField>
<ParamField body="task" type="string">`transcribe` (default) or `translate`.</ParamField>

The codes `language` and `allowed_languages` can take for your bots, and the deployment default, come
from the deployment:

```bash Transcription languages — GET /transcription/languages
curl -H "X-API-Key: $API_KEY" "$API_BASE/transcription/languages"
```

`200` with `{languages: [{code, name}], default: {language, allowed_languages}, model, source}`.
`languages` is the list for the transcription model your bots use; `source` is `provider` (the backend
reported its model), `configured` (the configured model id) or `assumed` (no model known: every accepted
code). Scope `bot` or `tx`. Details:
[Transcription language](/how-to/transcription-language#which-languages-you-can-choose).
<ParamField body="transcribe_enabled" type="boolean">Whether this spawn should request transcription. **Resolution:** an explicit value wins; else the deployment env `TRANSCRIBE_ENABLED`; else `true`. Non-boolean values (other than the common string forms `true`/`false`/`1`/`0`/`yes`/`no`/`on`/`off`) are refused with `422` (`transcribe_enabled must be a boolean`). When the resolved value is `true` and no STT backend is configured, `POST /bots` answers **503** with a detail naming the unset keys, e.g. `no transcription backend configured — set it in Settings or environment variables TRANSCRIPTION_SERVICE_URL + TRANSCRIPTION_SERVICE_TOKEN`. "Settings" there means [`PUT /user/transcription`](/api/settings#transcription-backend). Set `false` for **capture-only** (bot may still join; no STT client is constructed).</ParamField>
<ParamField body="recording_enabled" type="boolean">Whether this spawn should persist an **audio** recording (see [Recordings](/how-to/recordings) — there is no video recording path). Same resolution pattern as `transcribe_enabled` against env `RECORDING_ENABLED` (default `true` at the env resolver; the service default when callers omit it follows the request/env chain). Capture-only (`transcribe_enabled=false`) is **not** the same as recorded — recording is gated separately.</ParamField>

```bash POST /bots
curl -X POST "$API_BASE/bots" \
  -H "X-API-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{"platform":"google_meet","native_meeting_id":"abc-defg-hij","bot_name":"Vexa","language":"en"}'
```

If a **planned** meeting exists for the same link, the spawn **claims it**: the same record moves
to `requested`, keeping its title, `scheduled_at`, and workspace binding. `409` when a bot is
already active on that link; `429` past your concurrency limit — see the
[concurrency-refusal divergence](/api/errors#by-surface), which answers `403` today.

With transcription requested (the default) and STT unconfigured, the spawn is **refused loud** —
`503` naming `TRANSCRIPTION_SERVICE_URL` / `TRANSCRIPTION_SERVICE_TOKEN`. Two ways out: set the
backend for your account over the API — [`PUT /user/transcription`](/api/settings#transcription-backend),
which overrides the deployment default without a restart — or set those env vars for the whole
deployment ([Configuration](/configuration#transcription-stt)). Capture-only:
`{"transcribe_enabled": false}` (or `TRANSCRIBE_ENABLED=false` for the deployment). Configured and
still failing? See [Troubleshooting](/troubleshooting#bot-joins-but-theres-no-transcript).

### Completion service provenance

The signed `meeting.completed` webhook includes
`data.meeting.service_provenance` when the meeting has complete producer-owned lifecycle facts:

```json
{
  "bot_admitted_at": "2026-07-28T10:05:00.000Z",
  "bot_departed_at": "2026-07-28T10:30:00.000Z",
  "bot_outcome": "served",
  "transcription_provider": "customer",
  "transcription_outcome": "served",
  "lifecycle_contract_version": "2026-07-28"
}
```

`transcription_provider` is frozen when that bot is created: `vexa`, `customer`, or `none`.
`bot_admitted_at` and `bot_departed_at` are the bot-observed lifecycle transitions, not meeting
wall-clock time or delayed webhook receipt time. A bot that never reached `active` reports
`bot_outcome: "never_admitted"` with both timestamps absent. The block never contains an endpoint
URL, hostname, token, credential, meeting title, or transcript.

If a legacy or mixed-version run lacks provider ownership or producer timestamps, the block is
`null` or absent. Consumers must treat that as unresolved provenance; do not reconstruct it from
`transcribe_enabled`, current user settings, endpoint URLs, or meeting start/end time.

```json Response
  "segments": [
    {
      "segment_id": "sess_9c2a:spk1:12400",
```

Segments stream in while the meeting runs — poll this endpoint, or subscribe over **WebSocket** for live,
per-segment updates. Live drafts arrive as `completed: false` and are replaced by `completed: true`

The same response is reachable **by record id**, which is what you have after planning a meeting that

```bash GET /transcripts/by-id/{meeting_id}
curl -H "X-API-Key: $API_KEY" "$API_BASE/transcripts/by-id/12345"
```

Both forms return the meeting record alongside its `segments` — `id`, `platform`,
`native_meeting_id`, `status`, `start_time`, `end_time`, `constructed_meeting_url`, `notes`,
`recordings`, and the full `data` detail. `404` for an unknown record or one you don't own.

## Manage the bot

```bash Change the language — PUT /bots/{platform}/{native_meeting_id}/config
curl -X PUT "$API_BASE/bots/google_meet/abc-defg-hij/config" \
  -H "X-API-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{"language":"de"}'
```

The body (`language`, `allowed_languages`) replaces the running setting: an omitted field is cleared, so
both `null` is auto. `202` with `{meeting_id, platform, native_meeting_id, transcription_language}` once
the bot received it; `409` when the bot is not listening yet (nothing changed); `403` unless you own the
meeting or are an owner or contributor of its workspace. Details:
[Transcription language](/how-to/transcription-language#change-it-during-the-meeting).

```bash Stop / leave — DELETE /bots/{platform}/{native_meeting_id}
curl -X DELETE "$API_BASE/bots/google_meet/abc-defg-hij" -H "X-API-Key: $API_KEY"
```

Stop answers `200` with `{"status":"stopping","meeting_id":…,"also_stopped":[],"cancelled":[]}`.
The answer comes as soon as the stop is recorded and the leave command is published. Tearing down a
bot that is still starting happens after the answer, so a slow teardown never turns a working stop
into a timeout.

### List rows are slim; detail is full

The two list endpoints — `GET /bots` and `GET /meetings` — return **lightweight rows**. Each row keeps
its light metadata (id, status, times, `title`, connected docs) but **omits the heavy `data` detail
keys**: `speaker_events`, `bot_logs`, `recordings`, `status_transition`, `chat_messages`,
`error_details`, `last_error`, and the complete `calendar_sources` event snapshots. Compact calendar
identity such as `calendar_connection_id`, `calendar_uid`, and `scheduled_at` remains available in a
list row. Fetch a meeting's full `data` from `GET /meetings/{meeting_id}` — the detail endpoint is
unaffected and still returns every key.

The list is also **paged**: with no `limit`, a default page size of `50` applies (pass `limit`/`offset`
to page explicitly). `GET /bots` returns `has_more: true` when more rows remain past the current page.
Pass `exclude_planned=true` to either endpoint when rendering run/transcript history: the server
removes `idle` and `scheduled` plans before applying `limit` and `offset`. An explicit `status=...`
filter takes precedence. This keeps future Calendar entries on schedule surfaces without letting
them consume a history page.

## Speaker-attributed transcripts

Each segment carries **word-level timestamps** (`words[]`) and a `confidence`, and most segments are
**diarized** — attributed to a bound speaker display name. **Attribution is not guaranteed:** when the
binder cannot resolve a turn it publishes the segment with an **empty speaker** rather than guessing, so
your client must handle unattributed segments. Under heavy crosstalk roughly **4–7% of rows publish
unnamed** ([v0.12.22 release notes](https://github.com/Vexa-ai/vexa/releases/tag/v0.12.22)).
Speaker attribution is
text-level (who said what), via speaker binding / clustering / captions — *not* separate audio tracks.
Times are seconds from session start; `absolute_start_time` / `absolute_end_time` give wall-clock.

The same segments arrive **live** (`completed: false`, a pending draft) and then **confirmed**
(`completed: true`) — the gateway forwards the confirmed-plus-pending bundle to subscribers as the meeting
runs.

## Export and import a meeting

A meeting moves between deployments as one file, a [`meeting-bundle.v1`](/how-to/move-a-meeting) zip.
Both routes need the `tx` scope.

```bash Export (owner only) — GET /meetings/{meeting_id}/export[?media=false]
curl -OJ -H "X-API-Key: $API_KEY" "$API_BASE/meetings/42/export"
```

`200` with `application/zip` and `Content-Disposition: attachment`. `404` when the caller cannot see
the meeting, `403` when they see it through a share or a workspace but do not own it, `409` while a
bot is in it, `502` when a recording cannot be read (the export is refused, never produced without it).
`media=false` leaves recordings out. `POST` the same path with a parts archive as the body (the
meeting's workspace and page, from `GET /agent/meeting/bundle-parts?meeting_id=`) to have them placed
in the bundle; after an import, `POST /agent/meeting/bundle-restore?meeting_id=<new id>` with the same
file restores them.

```bash Import — POST /meetings/import[?dry_run=true]
curl -H "X-API-Key: $API_KEY" -H "Content-Type: application/zip" \
  --data-binary @meeting.meeting-bundle.zip "$API_BASE/meetings/import?dry_run=true"
```

With `dry_run=true`: `200` and a preview (meeting, segment count, speakers, media, `skipped`,
`duplicate_of`); nothing is written. Without it: `201` and the new `meeting_id`, owned by the caller
only. A refusal is `{"detail": {"code", "detail"}}` — `409 duplicate_import`, `413 too_large`, or
`422` with one of the codes in the [refusal table](/how-to/move-a-meeting#what-you-see-when-it-is-refused).

In the Terminal the same import runs when a person drops the bundle file into any chat; see
[Move a meeting between deployments](/how-to/move-a-meeting#import).

## Meeting participants

```bash GET /meetings/{platform}/{native_meeting_id}/participants
curl "$API_BASE/meetings/google_meet/abc-defg-hij/participants" -H "X-API-Key: $API_KEY"
```

```json
{
  "meeting_id": 12345,
  "platform": "google_meet",
  "native_meeting_id": "abc-defg-hij",
  "participants": [
    {"name": "Alice Example", "email": "alice@example.com", "source": "invite", "response_status": "accepted"},
    {"name": "Bob Silent",   "email": "bob@example.com",   "source": "invite", "response_status": "accepted"},
    {"name": "Alice Example", "email": null, "source": "speaker"}
  ],
  "sources": ["invite", "speaker"],
  "observed_roster": "not_recorded"
}
```

Every row says where it came from, because the two sources answer different questions:

| `source` | What it is | What it misses |
|---|---|---|
| `invite` | The calendar invitation's attendee list, from the feed you connected under [Calendar sync](#calendar-sync). Carries `email` and, when the feed supplied one, `response_status`. | Only exists for meetings imported from a calendar. Lists who was **asked** — an invitee who never showed up still appears. |
| `speaker` | Distinct speaker names heard in the transcript, ordered by first utterance. | Only people who **spoke and were named**. A silent participant is absent; so is a speaker the binder could not name (see [Speaker-attributed transcripts](#speaker-attributed-transcripts)). |

`404` for a meeting you don't own — not an empty list. `sources` names only the sources that
actually contributed, so `[]` means neither did.

<Note>
**`observed_roster` is always `"not_recorded"` today, and that is the important field.** Nothing in
the current core records who was *present* in a meeting: the bot's platform modules watch only tiles
that emit a speaking signal, so a participant who joins and never speaks leaves no trace anywhere
(tracked as [#861](https://github.com/Vexa-ai/vexa/issues/861)). So an empty `participants` means
**attendance was never captured** — it can never mean "nobody attended", and your client should not
render it that way. Today the only route to a complete list including silent people is the `invite`
source, i.e. connecting the calendar the meeting came from.

**No identity resolution is performed.** Someone both invited and heard appears **twice**, once per
source, as Alice does above. Matching a voice label to an invitee is a guess, and the wrong guess
silently merges two people — so the API hands you both layers, labelled, and leaves the join to you.
</Note>

## Recordings

The meeting's **audio recording** is uploaded to object storage — on a self-host, storage you run (Lite and
Compose keep it as plain files in a local volume), so it never leaves your environment. This is the meeting audio, stored separately from the diarized
transcript above (there is no "per-speaker audio" — speaker separation lives in the transcript as text).

```bash List recordings — GET /recordings
curl -H "X-API-Key: $API_KEY" "$API_BASE/recordings"
```

```bash Recording detail — GET /recordings/{recording_id}
curl -H "X-API-Key: $API_KEY" "$API_BASE/recordings/42"
```

```bash Delete one recording — DELETE /recordings/{recording_id}
curl -X DELETE -H "X-API-Key: $API_KEY" "$API_BASE/recordings/42"
```

After the meeting is terminal, recording deletion is owner-scoped (`404` for unknown and unowned
ids; `409` while the meeting is in flight) and removes all discovered
chunks/masters from configured primary object storage before removing the recording metadata. If
storage deletion fails, metadata is retained so the same request can be retried safely. This route
does not delete the meeting transcript; use `DELETE /meetings/{meeting_id}` after completion to erase
the meeting's transcript and all of its recordings together.

```bash Master metadata (finalize-on-read) — GET /recordings/{recording_id}/master?type=audio
curl -H "X-API-Key: $API_KEY" "$API_BASE/recordings/42/master?type=audio"
```

The master metadata returns a `raw_url` pointing at the byte stream
`GET /recordings/{recording_id}/media/{media_file_id}/raw`, which the player loads. The `/raw` endpoint
honours a `Range` header and returns `206 Partial Content` with `Content-Range` and `Accept-Ranges` —
these are preserved **through the gateway**, not only on a direct hit, so browser playback and seeking work. Add
`download=1` for `Content-Disposition: attachment` (same ownership check; the filename carries the
real container's extension).

## How it works

1. **Gateway.** Your request reaches the gateway with `X-API-Key`. The gateway checks the key with
   admin-api and fails closed: `401` for a missing, unknown, revoked or expired key, `403` when the
   key lacks the route's scope. Each route's scopes come from `core/meetings/routes.v1.json`.
2. **Signed identity.** The gateway forwards the request to meeting-api with the caller's identity,
   signed with the gateway's Ed25519 key (`gateway-identity.v1`). meeting-api checks the signature
   with the public key and refuses an unsigned or forged identity. It also checks the route's scopes
   against the same manifest.
3. **meeting-api.** It answers from Postgres (meetings, transcripts) and from object storage
   (recordings). `POST /bots` asks the [runtime](/core/runtime) to start the bot.
4. **Ownership.** A meeting, transcript or recording you do not own answers `404`, the same as one that
   does not exist.

## Why it complies

- **P4 sealed contracts.** `api.v1`, `routes.v1` and `gateway-identity.v1` are sealed; `gate:schema`
  and `gate:contract-version` enforce it.
- **P8 the shipped API matches its contract.** `gate:contract-conformance` checks meeting-api's routes
  against `api.v1` in both directions.
- **P6 one front door.** `gate:domain-doors` fails when a client or the gateway reaches the meetings
  domain other than through a route declared in `routes.v1.json`.
- **P20 authorize every access.** Deny tests under `gate:python`, in
  `core/meetings/services/meeting-api/tests/`: `test_identity_guard.py`
  (`test_an_unsigned_identity_is_refused`, `test_a_forged_signature_is_refused`),
  `test_route_scopes.py` (`test_a_key_without_the_route_s_scope_is_refused`), `test_collector_api.py`
  (`test_get_transcript_other_user_is_404`), `test_completed_artifact_deletion.py`
  (`test_non_owner_gets_indistinguishable_404_and_cannot_delete_any_artifact`). `gate:access` proves
  the default-deny rule itself.
