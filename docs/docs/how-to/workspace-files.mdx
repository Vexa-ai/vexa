The [workspace](/concepts#workspace) is a git folder of Markdown — knowledge, plans, and the agent's
session, all just files. The knowledge itself follows an open standard
([OKF](#the-knowledge-graph-is-an-okf-bundle), below). Every workspace route derives your identity from the
API key; you never pass a subject.

## Browse and read

```bash
# the file tree
curl -H "X-API-Key: $API_KEY" "$API_BASE/agent/workspace/tree"
# → { "files": ["kg/entities/acme.md", "meetings/2026-06-29-acme.md", ...] }

# one file's content (404 if absent)
curl -H "X-API-Key: $API_KEY" "$API_BASE/agent/workspace/file?path=kg/entities/acme.md"
# → { "path": "...", "content": "..." }

# git state — branch, uncommitted changes, recent commits
curl -H "X-API-Key: $API_KEY" "$API_BASE/agent/workspace/git"
```

Pass `hidden=true` to `tree` to include dotfiles. `git` is the durable state and the undo — every agent
write is a commit.

## The knowledge graph is an OKF bundle

The `kg/` subtree follows the
[Open Knowledge Format](https://github.com/GoogleCloudPlatform/knowledge-catalog/tree/main/okf) (OKF)
v0.1 — Google's open, vendor-neutral standard for markdown knowledge. Each entity is one file at
`kg/entities/<type>/<slug>.md` with YAML frontmatter:

```markdown
---
type: company            # OKF's only required key
id: acme-corp            # Vexa-required: stable slug, unique per type
title: Acme Corp         # Vexa-required: human title
description: Design-partner prospect, met at OSFF.   # OKF recommended
resource: https://acme.example.com                   # OKF recommended
tags: [prospect]
timestamp: 2026-07-02T14:00:00Z
---

Body is plain markdown. Entities cross-reference each other with [[wikilinks]]
by title — the knowledge graph emerges from the links.
```

Vexa's frontmatter contract (`type`/`id`/`title` required, per the
[`workspace.v1` schema](https://github.com/Vexa-ai/vexa/blob/main/core/agent/contracts/workspace.v1/workspace.schema.json))
is a strict superset of OKF, which requires only `type` — so every workspace is a conformant bundle any
OKF consumer can read, and `[[wikilinks]]` are a tolerated extension.

Two **reserved filenames** carry no frontmatter and are not entities:

- `index.md` — a per-directory listing (`- [Title](file.md) — description`) for progressive
  disclosure; seeded workspaces ship them generated, and the agent maintains them as entities are
  added or removed.
- `log.md` — optional change history, newest first, grouped under `## YYYY-MM-DD` headings.

Because the bundle is just files in git, it is portable by construction: `tree` + `file` above read it
over the API, and a `git clone` (or the swap endpoint below) moves the whole knowledge base between
tools — nothing about it is Vexa-specific.

## Upload documents

Add files to the workspace so agents can ground on them (multipart; ≤25 MB each). In the terminal,
drop them on the chat or paste them instead: see [Attach files to a chat](/how-to/chat-attachments).

```bash
curl -X POST "$API_BASE/agent/workspace/upload" \
  -H "X-API-Key: $API_KEY" \
  -F "files=@./contract.pdf" -F "files=@./notes.md"
# → { "files": [ { "name": "contract.pdf", "path": "..." }, ... ] }
```

## Initialize a fresh workspace

Idempotent — seeds the workspace if it doesn't exist yet:

```bash
curl -X POST "$API_BASE/agent/workspace/init" -H "X-API-Key: $API_KEY"
# → 201 { "workspace": "...", "seeded": true, "already_initialized": false }
```

## Load a workspace you already have

Most teams already keep their knowledge in a git repo. You do not have to move it: point a workspace at
it and that repo **becomes** the workspace — the agent reads and writes it in place, and `push` / `pull`
keep it in step with the remote. Whatever was in the workspace before is **parked**, never destroyed, and
can be swapped back to at any time (a swap-back restores the parked tree with no re-clone, so work done
while it was detached survives).

**In minutes mode**, this is one action: the `+` beside the chat's workspace chips → **Attach existing
repo…**, or the same item in the account menu at the foot of the chat list. Pick the target (your own
workspace, or any group you can write to), paste the repository URL, choose the branch, and attach.

**In conversation**, just ask — the agent has the same verb:

> *"Load the ASWF DNA workspace from github.com/aswf/dna into this group."*

```
workspace_attach(workspace="<group-slug>", repo="git@github.com:aswf/dna.git", ref="main")
workspace_status(slug="<group-slug>")   # look first: ahead/behind and the commits on each side; changes nothing
workspace_pull(slug="<group-slug>")     # bring in what changed upstream (fast-forward only)
workspace_push(slug="<group-slug>")     # send our work back (never a force push)
```

**Over the API** — your own workspace, and a shared one:

```bash
# your own workspace
curl -X POST "$API_BASE/agent/workspace/swap" \
  -H "X-API-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{"repo":"https://github.com/acme/knowledge.git","ref":"main"}'

# a shared (group) workspace — contributor or owner only
curl -X POST "$API_BASE/agent/workspace/shared/<workspace_id>/attach" \
  -H "X-API-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{"repo":"git@github.com:acme/knowledge.git","ref":"main"}'

curl -H "X-API-Key: $API_KEY" "$API_BASE/agent/workspace/shared/<workspace_id>/attached"
# → { "active": "...", "slots": {...}, "home": {...}, "credential": "origin git@…, deploy key set" }
```

Omit `repo` (and pass `"slug":"seed"`) to swap back. A repo with no `CLAUDE.md` is not refused — it is
nested under `kg/<repo-name>/` inside a governed workspace, so an ordinary docs repo loads unchanged.
The group's member list travels across the swap and is deliberately kept **untracked** in the attached
clone, so attaching never locks anybody out and your member list is never pushed to your repository.

### Private repos: add a key, don't paste a token

A private repo needs a credential, and Vexa's first answer is not to ask you for one. Every workspace can
mint its own **ed25519 deploy key**: you add the *public* half to your repository, and nothing of yours
travels to us. The private half is generated server-side, kept in the credential broker, and exists on disk only for
the length of one git operation.
`repo` must be an `https://`, `ssh://` or `git@host:owner/repo` URL pointing at a public or company
git host. A host inside the deployment is refused: a loopback, private, link-local, reserved or
multicast address, or an unqualified name with no dot. Local filesystem paths are refused too,
unless the operator sets `VEXA_ALLOW_LOCAL_REPO_ROOT` to an `os.pathsep`-separated list of
directories (`:` on Linux and macOS) that a local path must resolve inside.

Omit `repo` to swap back to the seed workspace. Check what's attached:

```bash
curl -X POST "$API_BASE/agent/workspace/<workspace_id>/deploy-key" \
  -H "X-API-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{"repo":"git@github.com:acme/knowledge.git"}'
# → { "public_key": "ssh-ed25519 AAAA… vexa-workspace-ws-…",
#     "add_at": "https://github.com/acme/knowledge/settings/keys",
#     "add_as": "a deploy key with WRITE access", "then": "say `done` when added" }
```

Add it there with **write** access, then attach again with an `ssh://` or `git@…` URL. If you attach
before adding it, the failure answers with exactly that key and that sentence rather than a box asking
for a secret — in chat, tell the agent `done` once you have added it and it will retry. Use the deploy
key for anything private; the [saved GitHub token](/core/workspaces#reusable-github-token) remains the
fallback for `https://` remotes, and is entered in the terminal (account menu → **GitHub token**) and
never in a chat.

## How it works

1. **Gateway.** Every call goes to `/agent/workspace/*`. The gateway forwards it to agent-api's
   `/api/workspace/*` (`core/agent/control_plane/routers/workspaces.py`) with the signed caller identity.
2. **Reads.** `tree` and `file` resolve which workspace to read: your own by default, or a `slug` from
   your active set or a shared workspace you belong to. Any other slug is refused. Paths are checked by
   one path layer that refuses absolute paths, `..`, links and the reserved `.git` / `.vexa` folders.
3. **Uploads.** Each file is checked against 25 MB (`413`), named by a content-hash prefix, and written
   without following links: images to `assets/`, everything else to `uploads/`.
4. **Swap and attach.** These are `person` verbs in `core/agent/routes.v1.json`: a worker dispatched
   without a person is refused. The repository URL is checked before any git process starts (`422`).
   The credential is the workspace's deploy key for SSH, else your saved token for `https://`, else none.
5. **Deploy key.** Generated once per workspace and returned again on every call. Only the public half
   is ever returned; the private half is kept in the [credential broker](/connections) (agent-api's `git`
   role) and written to disk only for one git operation. Without a broker, generating one is refused.

## Why it complies

| Rule | How this design meets it | Enforced by |
|---|---|---|
| P20 — authorize every access | A slug resolves only inside your own slots or a membership; swap and attach refuse anything else. | `test_workspace_slug_containment.py` (`test_swap_refuses_a_slug_that_is_not_one_of_the_callers_slots`, `test_shared_attach_refuses_a_slug_outside_the_groups_store`) |
| Person in the loop | Verbs that load a repository with saved credentials refuse a worker with nobody behind it. | `test_person_verbs.py` (`test_an_unwatched_worker_is_refused_and_nothing_changes`, `test_every_destructive_or_membership_route_is_flagged`) |
| P15 — secrets protected | A token in the repository field is refused by name; git errors are scrubbed; the private key has no read path. | `test_repo_ref_and_redaction.py` (`test_a_token_in_the_repository_field_is_refused_by_name`), `test_deploy_keys.py` (`test_ensure_is_idempotent_and_returns_only_the_public_half`, `test_the_private_half_is_kept_by_the_broker_and_nowhere_here`) |
| Internal hosts | A loopback, private or unqualified host, or a local path outside `VEXA_ALLOW_LOCAL_REPO_ROOT`, is refused before any subprocess. | `test_repo_ref_host.py` (`test_internal_host_is_refused`, `test_the_api_gate_refuses_before_any_subprocess`) |
| P14 — config is a contract | `VEXA_ALLOW_LOCAL_REPO_ROOT` is declared in agent-api's `config.v1.json`. | `gate:config-contract` |

All tests are in `core/agent/tests/` and run under `gate:python`.
