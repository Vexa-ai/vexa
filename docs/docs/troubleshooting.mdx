This page starts from a symptom you can see. If the run has already ended and you want to know
what ended it, every terminal meeting carries a reason —
[Completion reasons](/troubleshooting/completion-reasons) is the reference for all ten.

## Bot won't join the meeting

A `POST /bots` returns success once the bot is **dispatched**, not once it's in the call — a join can
still fail. Check the bot's live state:

```bash
curl -H "X-API-Key: $API_KEY" "$API_BASE/bots/status"
```

- **Bot image not built (self-host)** — the meeting bot is **built from source** (`make bot`), not
  pulled. If it's missing, the bot can't spawn and the meeting sticks at `requested`; if you're on the
  stale published `vexaai/vexa-bot:dev` (the old 0.10 line) the bot reaches `joining` then fails the
  `lifecycle.v1` handshake. Fix: `make bot`, and point `BROWSER_IMAGE` at the built tag.
- **Bad meeting id** — `native_meeting_id` is the id *inside* the join URL (e.g. `abc-defg-hij`), not the
  whole URL. Wrong platform value also fails: use `google_meet`, `zoom`, or `teams`.
- **Waiting room / admission** — on Meet and Teams the bot may be parked in a lobby until a host admits
  it. Admit it like any guest. A run that ended in the lobby says so:
  [`awaiting_admission_timeout` or `awaiting_admission_rejected`](/troubleshooting/completion-reasons),
  and `automatic_leave.max_wait_for_admission` sets how long it waits.
- **Teams bot never asks to join (`teams_prejoin_blocked`)** — Teams refuses a guest name that
  contains anything other than letters, numbers, spaces and `- ' . _ @`, such as parentheses or a
  colon. Teams then keeps **Join now** disabled, so no host sees a request to admit the bot. The run
  ends `join_failure`, and its reason text (`data.reason`) starts with `teams_prejoin_blocked`, quotes
  the rule Teams showed and lists the characters it refused. Rename the bot: see
  [Bot participant name](/configuration#bot-participant-name). How the check works:
  [A name Teams refuses](/troubleshooting/completion-reasons#a-name-teams-refuses-teams_prejoin_blocked). Older bots reported this case as
  waiting in the lobby until `max_wait_for_admission` ran out.
- **Concurrency cap** — a user can run at most `max_concurrent_bots` bots at once (set when the user was
  created). Stop an existing bot or raise the cap.

## Authenticated bot fails or joins signed-out

Applies only to deployments with `BOT_AUTHENTICATED=true` (see
[Authenticated bots](/authenticated-bots)).

- **`session-restore` failure at spawn** — the bot could not download the stored session (wrong
  `BOT_S3_ENDPOINT`, bad scoped credentials, or the `aws` CLI missing from a custom image). The bot
  log names the step and endpoint; the meeting fails rather than joining signed-out. Fix the config
  and respawn.
- **meeting-api refuses to boot (or 503 on `POST /bots`)** — `BOT_AUTHENTICATED` is set but
  `BOT_USERDATA_S3_PATH` / `BOT_S3_ENDPOINT` / `BOT_S3_BUCKET` are incomplete, or half of `BOT_S3_*`
  equals the storage's root pair or `S3_*`. The error names what is missing or which variables match.
- **`make login` refuses before opening the browser** — set `LOGIN_S3_ACCESS_KEY` /
  `LOGIN_S3_SECRET_KEY` to a pair that can write the userdata prefix (on Compose, `.env`'s
  `MINIO_ACCESS_KEY` / `MINIO_SECRET_KEY`); the bots' `BOT_S3_*` pair is read-only.
- **`session write-back failed` in the bot log** — `meeting-api` refused or could not store the
  rotated session: 403 when the bot is no longer the live authenticated bot (a later spawn
  superseded it, or its meeting ended more than ten minutes earlier), 422 when the profile held a
  file outside the session profile, 502 when meeting-api's own S3 credentials cannot write
  `BOT_S3_BUCKET`. The stored session stays at the last good write.
- **409 "authenticated session in use"** — one stored session runs one bot at a time; the message
  names the meeting holding it. Wait for it to finish, stop it, or provision another identity.
- **The session decayed (signed-out on join)** — re-provision with `make login`; the next spawn
  picks the fresh session up automatically. If this fires soon after provisioning rather than
  after weeks of use, check write-back and the
  [session-lifetime levers](/authenticated-bots#3-session-lifetime--the-session-stays-alive-because-it-is-used)
  instead of re-provisioning in a loop.

## A scheduled meeting didn't auto-join

Auto-join sends the bot ~60 s before the scheduled time (see
[Configuration](/configuration#auto-join--calendar-sync)). If the bot never appeared, check the
meeting's row in the Terminal — auto-join failures are stamped **onto the meeting** as a visible
`auto_join_error`, never swallowed. The usual causes:

- **No meeting link** — a plan without a Meet/Zoom/Teams link has nothing to join. Attach the link
  in the meeting's prep view.
- **Auto-join is off** — the per-meeting toggle, or the source calendar's Auto-join switch
  (dashboard Calendar page on hosted; `PATCH /user/calendars/{calendar_id}` anywhere).
- **Concurrency cap** — you were already running `max_concurrent_bots` bots at start time. The row
  shows the cap error and retries after a backoff (default 5 min).
- **The start time is long past** — a meeting more than the grace window (default 10 min) past its
  start is skipped deliberately; the bot never joins hours late.
- **STT not configured** — like a manual spawn, an auto-spawn refuses to launch a bot that could
  never transcribe; the row shows the unset keys. See
  [Bot joins but there's no transcript](#bot-joins-but-theres-no-transcript).

## Calendar isn't syncing

**Start with the connection's status line** — on hosted Vexa that is the Calendar page of the
dashboard at [dashboard.vexa.ai](https://dashboard.vexa.ai), which shows each feed's last
sync outcome, and every failure names itself (`⚠ Last sync failed: …`). **Sync now** re-runs that
connection. Self-hosted deployments do not ship that dashboard, and the API carries the same two
facts either way: `GET /user/calendars/{calendar_id}/sync` (last status),
`POST /user/calendars/{calendar_id}/sync` (run now).
The full message-by-message reference is in
[Calendar sync → Reading the sync status](/how-to/calendar-sync#reading-the-sync-status). The
usual causes:

- **Wrong URL kind** — you need the **secret ICS address** (Google: *Secret address in iCal
  format*, `…/private-…/basic.ics`; Outlook: the published **ICS** link). The **public** iCal
  address of a private calendar answers `HTTP 401`/`404`; a calendar *page* URL (embed/share) is
  rejected at save. Reads via `GET /user/calendars` show every connected feed masked.
- **The secret-address field is missing** (Google Workspace) — a restrictive Workspace sharing
  policy hides it. An admin unlocks it: **admin.google.com → Apps → Google Workspace → Calendar →
  Sharing settings → External sharing options for primary calendars → "Share all information…"**.
  Details in [Calendar sync](/how-to/calendar-sync#1-find-your-secret-ics-address).
- **The event has no meeting link** — it still imports as an unarmed planned meeting with
  `platform: "unknown"`; Vexa cannot auto-join until the feed contains a recognizable
  Meet/Zoom/Teams link.
- **Self-host wiring** — confirm `ADMIN_API_URL` and `INTERNAL_API_SECRET` are set for
  meeting-api; without them the sync loop is disabled (and `POST /user/calendar/sync` answers
  `503`).
- **Feed too large / unreachable / redirecting** — feeds over 2 MB, behind redirects, or resolving
  to blocked/internal addresses are refused; the status line records which.

## POST /bots returns 503 (transcription required)

Default spawns resolve `transcribe_enabled=true`. When no STT backend is configured, meeting-api
refuses **before** writing a meeting row:

```text
no transcription backend configured — set it in Settings or environment variables
TRANSCRIPTION_SERVICE_URL + TRANSCRIPTION_SERVICE_TOKEN
```

That is intentional (refuse loud). Fixes:

- Configure `TRANSCRIPTION_SERVICE_URL` + `TRANSCRIPTION_SERVICE_TOKEN` (see
  [Configuration](/configuration#transcription-stt)), or
- Spawn capture-only with `{"transcribe_enabled": false}`, or set `TRANSCRIBE_ENABLED=false` for
  the deployment.

If STT *is* set but the live probe says the backend is wrong, the 503 detail names the probe
reason instead — fix the URL/token and re-probe (`GET /health?force=1`).

## Bot joins but there's no transcript

The bot is capturing audio, but transcription isn't configured — or the bot was spawned
**capture-only**, which looks identical from the outside.

- **First, check whether the bot was spawned capture-only.** `GET /bots` (or `GET /meetings/{id}`)
  reports the resolved flag: `data.transcribe_enabled: false` means the bot was never asked to
  transcribe, so no STT request was ever made and no error will appear anywhere. If it is `false`
  and you did not intend that, an explicit `{"transcribe_enabled": true}` on `POST /bots` overrides
  the deployment default and confirms the diagnosis in one call.
- Confirm `TRANSCRIBE_ENABLED` is not set to a false value in your `.env`. An **empty**
  `TRANSCRIBE_ENABLED=` means `true` (the default) — but a trailing comment on that line does not:
  `docker run --env-file` keeps the comment as part of the value. Keep comments on their own line.
- Confirm `TRANSCRIPTION_SERVICE_URL` and `TRANSCRIPTION_SERVICE_TOKEN` are set (see
  [Configuration](/configuration#transcription-stt)). Unset → audio is recorded, no text is produced.
- Segments arrive draft-first (`completed: false`) then confirmed (`completed: true`) — a short delay is
  normal, not a failure.
- A stale bot key shows up as `native_resolve:{ok:false,kind:"unauthorized"}` on
  `GET /api/meeting/relay-health` rather than as silent dead air.

## Transcript covers only part of the meeting

The bot was in the meeting and some lines arrived, but long stretches of speech are missing. The
usual cause is a slow transcription backend: a remote STT can take 15–30 s to answer a few seconds
of audio.

- Read the bot's `[COVERAGE]` line (written every minute and when the bot leaves):
  `captured=…s submitted=…s transcribed=…s (…% of captured) no_speech=…s short=…s dropped=…s`.
  `transcribed` close to `captured` means nothing was lost. `no_speech` is silence or audio the STT
  returned nothing for. `short` is whole turns under a second that were not sent (see
  `BOT_SPEAKER_MIN_FINAL_AUDIO_SEC`). Any `dropped` seconds also appear as an `[AUDIO-DROPPED]` line
  naming the reason.
- `[TranscriptionClient] timeout (attempt n/4)` lines mean requests are outliving
  `BOT_STT_TIMEOUT_SEC` (default 90 s). Raise it, or move to a faster backend. Requests that answer
  within it are waited for, however long they take.
- Repeated `[SpeakerStreams] [FILTERED] Hallucination … "Thank you."` lines on short windows are the
  STT answering near-silence. They are filtered out and are not missing speech.
- `[TranscriptionClient] [STT-OVERLOAD]` and `[SttGate] [BREAKER-OPEN]` lines mean the transcription
  service answered 429, 503 or a 5xx relaying a rate limit. The bot pauses all its requests and sends
  them again in order when the service answers; nothing is lost unless a speaker's held audio passes
  300 s, which logs `[AUDIO-DROPPED]` with the missing time range.

### How it works

Each speaker channel turn has its own audio buffer in the bot (`SpeakerStreamManager`, the Google
Meet and Zoom lane). The buffer is the only owner of that audio until it has been transcribed. One
request per buffer is in flight at a time. While it is in flight, new audio keeps accumulating in
the buffer and rides the next request, so a slow STT makes windows longer instead of losing audio.

- **Turn close.** The buffer's last transcript is published only if it covers the buffered audio
  (within 0.5 s). Otherwise the whole window is sent as a final request. If a request is still in
  flight, the final request goes out when that one answers. The closed turn is freed only after its
  final answer arrives, capped at 10 minutes.
- **Input gap.** When frames resume after more than 2 s, the buffered stretch is detached under its
  own request route, which may already be in flight. It finishes its final request, and its answer
  cannot land on the new stretch. Up to 4 detached stretches per speaker can be finishing at once.
  After that the live window is extended instead.
- **Hard cap.** At `BOT_SPEAKER_MAX_BUFFER_SEC` (30 s) with no covering transcript, the window up to
  its quietest recent frame is sent as a final request, and the rest stays buffered.
- **Bound.** Audio held behind a request that never answers is capped at 300 s per speaker. Past the
  cap, new frames are dropped and counted.
- **Overload.** All of a bot's STT requests pass one gate: at most 8 in flight, released in arrival
  order. An overload answer (429, 503, or a 5xx whose body relays a rate limit or saturation) pauses
  every request of that bot for the service's `Retry-After` (at most 120 s), or else a jittered
  backoff from 2 s up to 30 s. After 3 overload answers in a row one probe goes out, and the rest
  follow when it succeeds. While the gate holds requests the lane sends no window a second time and
  no pipelined draft, and a request's stall clock starts when the hold ends. A slow (not overloaded)
  request gets at most one duplicate beside it. Audio dropped past the 300 s bound is recorded as a
  missing range (speaker, start, end, reason) and logged with its ISO times.
- **Retries.** A timed-out or failed request is retried with the same window (up to 4 attempts).
  The caller receives one answer, so the same audio is never transcribed twice. If the final window
  still fails, its seconds are counted as dropped.

Configuration: `BOT_STT_TIMEOUT_SEC`, `BOT_SPEAKER_MIN_FINAL_AUDIO_SEC` and the other
`BOT_SPEAKER_*` keys ([Configuration](/configuration#transcription-stt)). The runtime forwards them
to every spawned bot.

### Why it complies

- **P18, fail loud and attributed.** Every second of captured audio ends in exactly one counted
  outcome, and a loss is an `error`-level `[AUDIO-DROPPED]` line with its seconds and reason. STT
  faults still reach the host through `onError` as typed `TranscriptionError`s. Gate: the
  `@vexa/gmeet-pipeline` test suite (`slow-stt`, `fault-surfacing`, `count-channelswitch`), which
  runs in `gate:node`.
- **Back-pressure, not retry storms.** The STT's overload answer is honoured once per bot, not per
  request, and a held request is not counted as stalled. Tests: `@vexa/transcribe-whisper`
  `overload.test.ts` (Retry-After, backoff, breaker, bound in flight) and `@vexa/gmeet-pipeline`
  `stt-overload.test.ts` ("no window is sent again while the client is backing off", "requests in
  flight never exceed the gate's bound", "a hung request gets one duplicate beside it, not a chain of
  them", "the loss line names the missing time range"). Ungated beyond the package suites: reviewed.
- **P7, configuration by environment.** The new keys are declared in the runtime's `config.v1`
  contract and forwarded the same way as the existing `BOT_SPEAKER_*` keys. A timeout under 20 s is
  refused with a warning, and the default stays in force. Gates: `gate:config-contract` and the bot
  `config` test.
- **Data ownership.** Audio never leaves the bot except in the STT request it was already sent in.
  Nothing new is stored or transmitted. The coverage line carries durations only, never text or
  audio.
- **Security model.** Unchanged. A customer-owned STT endpoint still goes through the outbound URL
  guard on every request, retries included (`url-guard` tests). The bot's STT token is read from
  the invocation and is never logged.

## What terminal errors look like — and where the technical details live

Terminal error surfaces speak user vocabulary ("Couldn't reach the Vexa server — check that the
stack is running.", "Your API key was rejected — sign in again.", or the backend's own reason when
it sent one). The full technical string — proxied URL, HTTP status, backend exception detail, e.g.
`/api/vexa/user/calendars → 502: upstream unreachable: ConnectError` — is never lost: it is written
verbatim to the **browser console** (`api failure …` / `meeting action failed …` warnings) on every
presented error. Support and self-hosters debug from the console line; the on-screen headline tells
the user which layer to suspect.

## A bot on a fresh k8s node fails instantly with exit code 3 (`control_plane_unreachable`)

On Kubernetes each bot is a bare Pod, and a freshly autoscaled node's network can take up to a few
minutes to converge *after* the node reports `Ready`. A bot scheduled into that window may find its
control plane (the meeting-api callback **and** redis) unreachable. Rather than crashloop opaquely or
report a misleading `join_failure`, the bot now **fails fast**: it refuses to join and exits with a
dedicated code.

| Signal | Where to read it | Meaning |
|---|---|---|
| Pod exit code `3` | `kubectl describe pod <bot>` → `Last State: Terminated, Exit Code: 3` | control plane unreachable at boot — the bot never navigated to the meeting |
| `infra_fault: control_plane_unreachable`, `failure_stage: requested` | meeting API / dashboard (if any callback channel recovered) or the pod logs | distinguishes a **broken node** from a **broken join** (a real join failure is exit `1`, `failure_stage: joining`/`awaiting_admission`/`active`) |

**What to check on the node:** is the CNI fully programmed? can a canary pod on that node reach the
meeting-api Service and redis? Deleting the pod to force a reschedule (onto a warmed node, or the same
node after its window passes) is the manual remedy. The bot's exit is fast (< a few seconds) and the
retry budget on the first emit (≤ ~15s) already rides out brief transient programming lag. See
[Kubernetes deployment → autoscaling and bot bursts](/deployment-kubernetes).

## Authentication failures

| Symptom | Cause | Fix |
|---|---|---|
| `401 Missing API key` | no `X-API-Key` header | add the header |
| `401 Invalid API key` | unknown or revoked key | mint a fresh one ([Authentication](/authentication)) |
| `403 Insufficient scope for this endpoint` | key lacks the route's scope | mint with the right `scopes=` |
| `403 Invalid or missing admin token.` on `/admin/*` | missing or wrong `ADMIN_TOKEN` | use the `X-Admin-API-Key` matching your `ADMIN_TOKEN` |
| `503 Authentication temporarily unavailable, retry` | the gateway could not get an answer from admin-api about the key; the key was **not** rejected | retry after the `Retry-After` seconds; if it persists, check admin-api ([below](#503-authentication-temporarily-unavailable)) |

**Don't have a key yet?** Hosted: sign in at [vexa.ai/signin](https://vexa.ai/signin) with a Google
account and copy your key from [your account page](https://vexa.ai/account) — free credit, no card
required. Self-hosted: `make all` prints a key when the stack comes up.

### 503 Authentication temporarily unavailable

The gateway checks every API key with admin-api before forwarding the request. A `503` with
`Authentication temporarily unavailable, retry` (and `Retry-After: 1`) means no verdict was reached on
the key: admin-api did not answer, answered with a server error, or answered something that is not a
verdict. The key is not invalid; send the request again. On the live WebSocket the same case sends
an `auth_unavailable` error frame and closes with code `4503`, not `4401`.

A short admin-api restart does not produce it: when the gateway cannot connect to admin-api at all,
it tries again after 0.5 s and then 1.5 s before answering `503`. If you see it repeatedly, admin-api
is down or overloaded: check that its container or pod is running and ready, and look for
`auth_infra_unavailable` lines in the gateway log, which carry the reason.

#### How it works

1. For each credential, the gateway's admin-api adapter (`AdminApiAuthorizer.resolve`,
   `core/gateway/services/gateway/src/gateway/adapters.py`) POSTs it to admin-api `/internal/validate`
   with a 5-second budget per attempt.
2. A `200` with a readable body admits the key. A `4xx` means the key is invalid, and the gateway
   answers `401`.
3. A hop that could not connect (`ConnectError`, `ConnectTimeout`) never reached admin-api, so it is
   sent again: at most three attempts, after waits of 0.5 s and 1.5 s
   (`VALIDATE_CONNECT_RETRY_BACKOFF`). A refused connection costs about 2 s in all; a connect that
   times out can use its 5-second budget on each attempt.
4. Every other failure is answered at once, without a retry: a read timeout (admin-api has the
   request and is slow), a pool timeout (this gateway's own connection pool is full), a `5xx`, a
   redirect, or an unreadable `200`. These, and the last failed connect, answer `503`.

The waits are fixed in code; there is nothing to configure. admin-api remains the only service that
decides whether a key is valid; the gateway only asks.

#### Why it complies

| Rule | How | Gate |
|---|---|---|
| P18 fail loud | No verdict is a `503` with `Retry-After`, never a `401` that blames the key, and it is logged as `auth_infra_unavailable` with the reason. | `gate:python` (`core/gateway/services/gateway/tests/test_adapters_resolve.py`) |
| P20 authorize every access | The gateway stays fail-closed: no path admits a key without a `200` from `/internal/validate`. A retry repeats only a request admin-api never received, so no verdict is asked for twice. | `gate:python` (tests below) |
| P5 adapt at the boundary | The retry lives in the gateway's admin-api adapter; nothing else in the gateway changed. | ungated: reviewed |

**Security.** The retry adds no way in: each attempt carries the same key and headers to the same
admin-api address, and only an answer from admin-api can admit a key. A slow admin-api gets no
extra load, because a request it already received is never repeated. Tests, in
`core/gateway/services/gateway/tests/test_adapters_resolve.py`:

| Protection | Tests |
|---|---|
| No verdict is never an admission or a `401` | `test_resolve_transport_failure_raises_unavailable`, `test_resolve_server_error_raises_unavailable`, `test_resolve_redirect_is_no_verdict_unavailable`, `test_resolve_unparseable_200_body_raises_unavailable` |
| Only a `4xx` from admin-api rejects a key | `test_resolve_client_error_is_invalid_key_none` |
| Only a hop that never connected is retried, and only twice | `test_a_connect_failure_that_recovers_resolves_the_key`, `test_a_persistent_connect_failure_still_answers_unavailable`, `test_a_hop_that_reached_admin_api_or_hit_this_edges_pool_is_not_retried` |

The gateway's own notes are in its
[README](https://github.com/Vexa-ai/vexa/blob/main/core/gateway/services/gateway/README.md); the
identity check itself is described in [Identity & trust](/architecture/identity-and-trust#admission-at-identity).

## Agent chat says no model credentials are configured

`POST /agent/chat` streams a single `error` frame — *"No model credentials are configured, so the
agent cannot run…"* — and no turn runs. This is the credential preflight: the deployment has no
model credential and your user has no custom endpoint, so a worker could only fail. Fix either side:

- **Deployment-wide** — set ONE of `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY`,
  `ANTHROPIC_AUTH_TOKEN` or `HOST_CLAUDE_CREDENTIALS` in `deploy/compose/.env`,
  then `make all` (the frame names exactly the keys it found unset).
- **Per-user** — add a custom endpoint under **Settings → Models** in the Terminal (a `custom`
  config needs its `base_url`; the API key is optional for keyless local gateways).

A turn that *starts* and then fails with **"Model credentials are missing or expired for this
deployment"** (a `done` frame, `ok:false`) is the mid-flight variant: a credential that existed at
dispatch went stale — on macOS typically the Keychain-exported `HOST_CLAUDE_CREDENTIALS` file
(install the [sync daemon](/configuration#claude-subscription-credentials-host_claude_credentials));
otherwise refresh/rotate the key. The raw provider text rides in the frame's `detail` field.

## Agent chat says the model provider is out of credits

When the model provider refuses a turn for lack of credit, the chat ends the turn with one block:

- the headline `Model provider · out of credits (402)` (the status is the one the provider sent;
  some providers report an empty balance as `400` or `429`, and their wording still marks it out
  of credits);
- the provider's own explanation, on one line, with anything key-shaped redacted;
- a remedy line: `Add credits at <provider>, or choose another model under Settings → Models.`

When the provider says the balance covers a smaller answer ("can only afford", "fewer
max_tokens"), the remedy also names the output cap: lower `VEXA_AGENT_MAX_OUTPUT_TOKENS` (see
[Configuration](/configuration)). The provider's raw `API Error` text does not appear as the agent's
reply, and no second "Model inference failed" line follows.

Links in the provider's message, such as its key-management page, are for the operator. They are
left out of the chat and written to the agent worker's log on the `model provider fault:` line,
with the provider, kind, status and model.

## Containers don't spawn (self-host)

The [runtime](/core/runtime) spawns bot and agent containers via the Docker socket.

- The runtime needs access to the host Docker socket and the right group — set `DOCKER_GID` to the host's
  docker group id.
- The meeting bot (`BROWSER_IMAGE`) is **built from source** (`make bot`) and the runtime spawns it
  **without pulling** — it must exist locally first. Confirm it's there (`docker image inspect "$BROWSER_IMAGE"`);
  the published `vexaai/vexa-bot:dev` is the old 0.10 line and is incompatible. `AGENT_IMAGE` is built by
  `make all` — confirm it resolves and `IMAGE_TAG` matches what you built.

## Leftover chrome/node processes after a bot ends (Lite)

On **Lite** every bot and agent runs as a child process inside one shared container (the
[process backend](/core/runtime)). If a meeting ends and you still see stray `chrome`/`node`
processes, check inside the container:

```bash
ps -eo pid,ppid,etime,comm   # PPID 1 = orphaned (reparented to init)
```

As of this release the backend reaps each workload's whole process group when it exits or is
stopped, so no strays should remain — a descendant that detached into its own process group
(the debug-view x11vnc/websockify) is the one declared exception. On older Lite images the
workaround is a container restart.

## Agent write was rejected

A streamed turn can end with a `rejected` frame carrying `violations`. This is governance, not a bug:
**untrusted input** (email, web) runs [propose-only](/architecture/governance) and cannot write directly —
it emits proposal cards a human approves. Trusted input (your chat) may write. If a legitimate trusted
write is rejected, check that the dispatch's trigger is `message`/`scheduled` (which mount the workspace
`rw`), not an untrusted event.

## The stack won't come up

- `make all` brings the compose stack up health-gated; tail the logs with `make logs` or
  `docker compose -p vexa-v012 logs -f` to see which service is wedged.
- Port already in use → override the host port (e.g. `API_GATEWAY_HOST_PORT`) in `deploy/compose/.env`.
- Stop and restart: `make down`, then `make all`. Compose `make down` keeps data volumes.
  To deliberately wipe the stack, use `make -C deploy/compose destroy DESTROY=yes`, then
  `make all`. Destroy removes the database, recordings, Redis data and agent workspaces.
- Storage readiness failed → inspect `docker compose -p vexa-v012 logs storage-init` from
  `deploy/compose`. The failure names the configured endpoint, bucket and failed operation.
  Check credentials and bucket/probe permissions. After a MinIO upgrade, old recordings remain
  in the old volume; update the endpoint and copy them with the
  [migration tool](/upgrade-from-minio) to restore playback from the new storage.

## Scaling meeting-api to more than one replica

Running `meetingApi.replicaCount > 1` (the Helm chart default is `2`) is **safe**. Every replica
starts the same background sweeps, but each sweep's real work is **single-flighted** by a Postgres
session-level advisory lock (one per loop): the replica that acquires the lock runs the tick, the
others skip it that interval. So a sweep's real work — notably the `calendar-sync` external ICS
fetch — runs **once per interval across the cluster, not once per replica**. Sweep intervals
(`CALENDAR_SYNC_INTERVAL_S`, etc.) are therefore per-cluster, not per-replica. A replica that dies
mid-tick drops its lock on disconnect, so the next interval is picked up by another replica — no
leader-election setup required. On a single replica the lock is always free, so behaviour is
unchanged. Note that `scheduler-tick` is not a production loop and is no longer started.

## Still stuck?

[Support](/support) is where to send it, and says what to include: the meeting id and platform (the
