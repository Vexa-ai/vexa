---
title: "Model catalog"
description: "Offer several models — a self-hosted Qwen 3, anything on OpenRouter, Anthropic — and let each person pick the one a chat runs on."
---

The model catalog is the list of models your deployment offers, and the one place they are listed.
Every entry is a real model, by its name. Each person picks one per chat, in the chat's composer.
You decide:

- which providers the deployment reaches;
- which models it offers on each;
- what each model can do;
- who may use it;
- which one people start on.

Without a catalog, nothing changes. Every turn runs on `VEXA_AGENT_MODEL` and each person's
Settings → Models, as before.

## The catalog

The catalog is one JSON object in agent-api's environment, `VEXA_MODEL_CATALOG`. Its schema is
`core/agent/contracts/models.v1`, the `Catalog` shape. It has two parts:

- **providers:** one entry per endpoint, each naming the adapter that knows how to reach it;
- **models:** the models offered on those providers.

```json
{
  "providers": {
    "lab-vllm": {
      "adapter": "openai_compatible",
      "base_url": "http://10.0.0.5:8000/v1",
      "auth": "none",
      "extra_body": { "chat_template_kwargs": { "enable_thinking": false } }
    },
    "openrouter": {
      "adapter": "openrouter",
      "auth": "secret",
      "secret_ref": "env:VEXA_MODEL_SECRET_OPENROUTER"
    }
  },
  "models": [
    {
      "id": "qwen3-32b",
      "display_name": "Qwen 3 32B (self-hosted)",
      "provider": "lab-vllm",
      "model": "Qwen/Qwen3-32B",
      "capabilities": { "tool_calling": true, "streaming": true, "context_tokens": 32768 },
      "default": true
    },
    {
      "id": "or-sonnet",
      "display_name": "Claude Sonnet via OpenRouter",
      "provider": "openrouter",
      "model": "anthropic/claude-sonnet-4.5",
      "access": "admins"
    }
  ]
}
```

### Providers and their adapters

| `adapter` | Reaches | Harness | Fields |
|---|---|---|---|
| `openai_compatible` | any OpenAI-compatible endpoint: a self-hosted vLLM or llama.cpp, a LiteLLM proxy, an inference gateway | `openai-agent` | `base_url` (required, the OpenAI root, usually ending `/v1`); `auth: none` or `auth: secret` with `secret_ref`; `extra_body` |
| `openrouter` | any model OpenRouter serves | `openai-agent` on `/api/v1` (default), or `claude-code` on OpenRouter's Anthropic-compatible `/api` | `harness`; `auth: secret` with `secret_ref` (required); `extra_body` (openai-agent only) |
| `anthropic` | Anthropic directly | `claude-code` | `auth: secret` with `secret_ref` (an API key), or `auth: subscription` (the deployment's own Claude subscription; read [Model credentials & licensing](/model-credentials-licensing) before offering it to other people) |

On a claude-code route through OpenRouter, every model tier the claude CLI uses is pinned to the
chosen model, so background calls go to that model too.

### Models

| Field | Meaning |
|---|---|
| `id` | What a chat and a person's default name, e.g. `qwen3-32b`: lowercase letters, digits, `.`, `_`, `-`, at most 64 characters. Keep it stable. |
| `display_name` | What people see in the picker. |
| `provider` | A key of `providers`. |
| `model` | The model's id at the provider. Required. |
| `capabilities` | `tool_calling` (must be true: every harness is an agent loop), `streaming` (default true), `context_tokens` (the openai-agent harness trims history to it), `reasoning_efforts` and `default_effort` (see [Effort levels](#effort-levels)). |
| `extra_body` | Request fields merged over the provider's, for the openai-agent harness. |
| `max_output_tokens` | The output-token cap this model's requests ask for. Absent: the deployment's `VEXA_AGENT_MAX_OUTPUT_TOKENS`, else the harness's own default (the claude CLI asks for 32000, which OpenRouter refuses on a small balance with a 402). |
| `effort_control` | `openai_compatible` only: `reasoning_effort` (default) or `enable_thinking`. See [Effort levels](#effort-levels). |
| `access` | `everyone` (default) or `admins`. An admins-only model is not shown to, and is refused for, anyone else. |
| `default` | `true` on at most one model: the one people run on before they pick. |

### Effort levels

A model can offer an effort level, picked per chat beside the model. List the levels in
`capabilities.reasoning_efforts`, and optionally the one a chat starts at in `default_effort`.
A model without `reasoning_efforts` has no effort control, and the picker shows none for it.

The levels are one vocabulary: `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`. Each
adapter sends them in its provider's own field and accepts only the levels that field can carry:

| Adapter | Sent as | Levels it can send |
|---|---|---|
| `openrouter` (openai-agent harness) | `reasoning.effort` | `none` … `xhigh` |
| `openrouter` (claude-code harness) | — | none: declare efforts on an openai-agent OpenRouter provider |
| `openai_compatible`, `effort_control: reasoning_effort` | `reasoning_effort` | `none` … `xhigh` |
| `openai_compatible`, `effort_control: enable_thinking` | `chat_template_kwargs.enable_thinking` (a Qwen behind vLLM) | `none` (off), `high` (on) |
| `anthropic` | the claude CLI's `--effort` | `low` … `max` |

A catalog that lists a level its adapter cannot send is refused at boot. A chat that picks a level
its model does not offer is refused with the typed fault `effort_unsupported`, and the pick is not
stored. A level is never dropped silently.

The claude CLI decides per model whether it sends the effort at all. Measured on CLI 2.1.293:
`claude-sonnet-4-6` and `claude-opus-4-6` carry every level, `claude-opus-4-5` sends `max` as
`high`, and `claude-sonnet-4-5` ignores the flag. List levels only for a model that takes them.

### Credentials are references, never values

A provider's credential is `secret_ref: env:VEXA_MODEL_SECRET_<NAME>`, the name of a variable in
agent-api's environment. Only that prefix is allowed, so a catalog can never name one of agent-api's
own secrets. These variables are not in the config contract's declared keys: the operator names
them, and the prefix is their contract. agent-api reads the value at dispatch. The value never appears in the catalog, in a
log, in a refusal or in anything the browser receives. It goes only to that provider's endpoint, as
the header that provider expects:

- a bearer token for an OpenAI-compatible endpoint and for OpenRouter;
- `x-api-key` for Anthropic.

agent-api refuses a catalog that writes a credential inline: a field named like one (`api_key`,
`token`…), a credential-shaped value, or credentials in a URL. The refusal names the field, never the
value.

## Where the catalog is set

The catalog is one value, `VEXA_MODEL_CATALOG`, on agent-api. Each deployment surface sets it in one
file:

| Surface | Where you write it | How it reaches agent-api |
|---|---|---|
| Compose | `deploy/compose/.env`, key `VEXA_MODEL_CATALOG` (documented in `deploy/compose/.env.example`) | compose passes `.env` to the agent-api container |
| Helm | your values file, key `models.catalog` (default empty in `deploy/helm/charts/vexa/values.yaml`); keys in `models.catalogSecrets` | `deploy/helm/charts/vexa/templates/deployment-agent-api.yaml` renders it as the `VEXA_MODEL_CATALOG` env var and each secret from the Secret you name |
| Lite | the repository-root `.env` that `make -C deploy/lite up` reads, key `VEXA_MODEL_CATALOG` | `deploy/lite/entrypoint.sh` exports it to agent-api |

A provider's key is never in the catalog. The provider names a variable
(`secret_ref: env:VEXA_MODEL_SECRET_<NAME>`), and you set that variable beside the catalog: on its
own line of `.env`, or through `models.catalogSecrets` in Helm.

After a change, recreate agent-api (compose), roll the deployment (Helm), or restart the container
(Lite). Settings → Models has no model list of its own: it only picks a default from this one.

A member sees the first three; an instance admin sees all four.

**agent-api refuses a catalog with anything wrong in it at boot, and names every problem.** The
checks are:

- an unknown adapter, or `custom`: a person's own endpoint is not a model, and the refusal says to
  list each model by its real name instead;
- a field an adapter does not take;
- an inline credential;
- a duplicate id;
- two defaults;
- a model on an undeclared provider;
- a model without tool calling;
- a `secret_ref` that is not set.

A catalog is never half-applied.

## What people see

- **The picker.** A model picker sits in the chat's composer, beside the send button.
  - It shows only the models the person may use, each by its catalog name. An `admins` model
    appears only for instance admins.
  - It shows nothing on a deployment with no catalog.
- **Settings → Models.** With a catalog, the only model field is the default model. The provider,
  endpoint, key, model and effort fields are not shown, because every turn runs on a catalog model.
  Without a catalog they work as before.
- **A pick is per chat.**
  - It takes effect on the chat's next message, which starts a fresh agent on that model.
  - "Use … for new chats" makes the current model the person's default.
  - "Follow my default" un-pins the chat.
- **Effort.** When the chat's model lists effort levels, an effort selector sits beside the model
  chip. Changing the model clears the effort pick, so the chat runs at the new model's default.
- **Defaults.** A chat nobody picked for runs on the person's default, else the organisation's,
  else the catalog's `default`, else the first model the person may use.
  - The person sets theirs with "Use … for new chats", or under Settings → Models → Default model,
    which lists the catalog's models.
  - The organisation's default is the same selector in an admin's global settings.
- **Autonomous runs.** Routines and other runs nobody starts by typing use the person's default.
  Background jobs a chat starts run on that chat's model.

The same list is available over the API (`GET /api/models/catalog`) and to MCP clients as the
`models_list` tool. See the [agent API](/api/agent#the-model-catalog-and-a-chats-model).

## When a model cannot run

A pick that cannot run is refused before anything starts, and the chat says why. Its typed fault is
`source: model-provider`, naming the model and the provider, with one of these kinds:

| `kind` | Meaning |
|---|---|
| `unknown_model` | the chat's model is no longer in the catalog |
| `not_permitted` | an admins-only model, for someone else |
| `not_configured` | the catalog offers this person nothing |
| `credential_missing` | the provider's `secret_ref` is not set any more |
| `effort_unsupported` | the chat's effort level is not one its model offers |

A chat never silently runs on a different model.

A provider that fails mid-turn reports in the same shape, with kinds `unpaid`, `unauthorized`,
`rate_limited`, `unavailable` and `refused`. In that case the provider is the host the turn went to.

**Settings → Models → Test** probes your default model through the same route a turn on it would
take, in that route's own dialect, with exactly that route's credential. To test any other model you
may use, call `GET /api/models/test?model=<id>`.

## How it works

1. **Catalog.** agent-api reads `VEXA_MODEL_CATALOG` once at boot and refuses it whole, naming every
   problem, if anything in it is wrong.
2. **Pick.** The picker lists `GET /api/models/catalog` for the person and stores a chat's model and
   effort with `POST /api/chat/model`, which refuses a pick the next turn could not run.
3. **Dispatch.** On the chat's next message, agent-api resolves the pick through the provider's
   adapter, in the one place a worker's route is decided, and refuses the turn before anything
   starts if the pick can no longer run.
4. **Worker env.** The route is stamped into the new agent's environment: the endpoint, that
   provider's one credential, the model, the effort in the provider's own field, and the output cap.

The full flow, data ownership, and why it complies with the architecture and security rules, with
the tests that prove each refusal, are in the module README
(`core/agent/control_plane/model_providers/README.md`) and
[ADR-0043](https://github.com/Vexa-ai/vexa/blob/main/docs/adr/0043-model-choice-catalog-behind-a-provider-port.md).

## Security

- **People cannot add endpoints.** The catalog is deployment configuration. With a catalog, a turn
  runs only on an endpoint the catalog declares; a person's own endpoint under Settings → Models
  is not used.
- **Each credential goes to one place.**
  - A provider's credential goes only to that provider's endpoint.
  - The deployment's credentials never go to a catalog provider's endpoint.
  - The deployment's subscription goes only to Anthropic.
- **Nothing sensitive reaches the browser.** No endpoint, credential or request setting is in
  anything the browser or an MCP client receives.
