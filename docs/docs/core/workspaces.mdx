The workspace model an agent turn sees (for the person-facing guide, see
[Minutes → Workspaces](/minutes/workspaces)), how workspaces are shared, how a user joins and manages
them, and how members collaborate live during a meeting. This is the canonical explainer; the code
lives in `core/agent/control_plane/` (membership, invites, mounts, purpose, git-sync, git-credentials),
`core/agent/worker/` (the turn + mount preamble), `core/runtime/` (the binds), and
`clients/terminal/src/` — `surfaces/workspace.tsx` (sidebar), `surfaces/workspaceManage.tsx` (the manage
panel), `app/join/` (the invite page), `surfaces/tokens.tsx` (the GitHub token). Status is marked
✅ done / 🟡 partial / ⬜ planned throughout.

## The mount model — three tiers

Every agent turn mounts an ordered set `[_global, *normal, _system]`:

| Tier | Slug | Access | Always mounted | Purpose |
|---|---|---|---|---|
| **Global system** | `_global` | **read-only** (fs `:ro`) | yes | Platform-owned self-awareness: a synced **Vexa branch** (code + docs) + behaviour/skills. One copy, central. |
| **Normal** | `<id>` / `.attached/<subject>/<slug>` | read-write | opt-in (flat, equal rank) | The user's own + shared knowledge workspaces — all the **same rank** (see below). |
| **Private system** | `_system` | **read-write** | yes | Per-user private store — **who you're helping** (`identity.md`), settings, routines, membership/attachment records. Never shared. **Holds no chat:** conversations are kept in the session store, apart from every workspace ([Shared chats](/minutes/shared-chats)). |

- **There is NO "baseline"/"primary" rank** (2026-07-07 flat model). The normal tier is a **flat,
  equal-rank list** (`active_set`) — every workspace activates/deactivates the same way. The mount
  set's `primary` flag marks only the **dynamic default HOME** (the *first active* normal workspace =
  the turn's cwd, whose `CLAUDE.md` auto-loads); it moves as workspaces are switched on/off, and is
  absent when nothing normal is active. Code: `workspace_attach._normalized_active_set` (flat, with a
  one-time `_flat_v1` migration off the legacy baseline state), `dispatch._worker_cwd`.
- **`_system` carries the light self-identity** (`identity.md`): the user's **name** + a pointer to the
  full `self: true` profile in their Personal workspace. Always mounted, so the agent knows who it's
  helping even when Personal is switched off; the worker preamble routes identity here and **asks for
  the name until it's set** (✅). Full profile (company/role/relationships) stays in Personal.

- `_global` and `_system` are **"system possessions" always attached** to a user's agent. They are
  **invisible** in the workspace lists and **non-sharable** — both are in `RESERVED_SLUGS` and
  `ensure_workspace_shareable` refuses them (✅). `_system` can be **surfaced read-only in the files
  panel via a toggle, hidden by default** (the key icon in the KNOWLEDGE header) (✅).
- `_global` lives in the workspace store at `<VEXA_WORKSPACES_DIR>/_global`, created EMPTY at boot —
  an empty `_global` is fine and nothing waits for it to be filled (founder ruling 2026-10-08). Set
  `VEXA_GLOBAL_SYSTEM_WORKSPACE_PATH` only to provision it from a separate host dir / synced branch,
  which the runtime then gives its own `:ro` bind; a configured path that is absent fails dispatch
  closed. The worker loads
  its `CLAUDE.md`, `PURPOSE`, and `README.md` into every turn so Personal reasoning starts with shared
  organisation facts rather than merely having them available on disk. (✅ wired;
  auto-sync of the branch is a ⬜ follow-up.)
- Code: `core/agent/control_plane/system_mounts.py` (`GLOBAL_SLUG`, `SYSTEM_SLUG`, `global_mount`,
  `system_mount`, `system_store_path`), the mount stack in `dispatch.py`, binds in
  `core/runtime/src/runtime_kernel/mounts.py:workspace_binds`.

## Tenant isolation — enforced by the substrate (✅ all three backends)

The mount set is not just a declaration to the model — it is **the enforced boundary**. A worker's
filesystem physically contains ONLY its dispatch's declared mounts; another tenant's workspace is
not reachable, so a prompt injection cannot read or write it. Read-only roles (viewer shares,
`_global`) are enforced at the mount, not just at the commit token.

| Backend | Mechanism |
|---|---|
| **docker** | One bind per mount: a named-volume store rides the Mounts API's `VolumeOptions.Subpath` (**requires engine ≥ v26** — older engines fail the container create loudly); a host-path store joins the subpath (no version requirement). The whole-store root bind is never emitted. |
| **k8s** | One `volumeMount` per mount against the single store PVC — native `subPath` + `readOnly` (no version caveat). With the s3 backend: a private `emptyDir` holding only the dispatch's mounts, fetched through agent-api. |
| **lite (process)** | POSIX: workers drop to a **per-subject uid** (`100000+id`), private/system tiers are `0700`-owned, each shared workspace gets its own **gid** (persisted registry, joined as a supplementary group), per-subject `HOME`/`TMPDIR`, and a **default-deny sweep** seals never-dispatched tenants' dirs on every apply. Unavailable conditions (non-root runtime, non-numeric subject) degrade **loudly** to shared-trust. |

There is **no opt-out knob** — strict is the only mode. Known lite limitation: within a shared
workspace, viewer-vs-contributor *write* gating stays at the commit layer (a POSIX group can't
split read from write per member without ACLs); cross-tenant isolation is fully kernel-enforced.
Code: `runtime_kernel/mounts.py` (`workspace_binds`, `k8s_volume_mounts`),
`runtime_kernel/isolation.py` (the POSIX plan/apply), tests `test_mounts.py` + `test_isolation.py`.

## Personal + normal workspaces

- **Personal is just a normal workspace** — no special rank. It's the workspace **auto-seeded at
  account creation** and shown as **"Personal"** in the UI; beyond that it activates/deactivates,
  reads/writes, and behaves exactly like any other normal workspace (✅). Switch it off and it leaves
  the active set — **its files drop from the finder** and the agent stops working in it, same as any
  workspace. Its tree still physically lives at `<root>/<subject>` (the "seed slot" — a **storage
  detail, not a rank**); code resolves that path via `_seed_slot_slug` / `_slug_dir`.
  - 🟡 residual: **share/archive/delete of the seed slot are still refused** (you can't yet delete/
    share the exact slot whose tree sits at `<root>/<subject>`). Making Personal *fully* like others
    means relocating that tree out of the seed slot — a ⬜ follow-up (see Deferred).
- **Provisioned eagerly on account creation** (✅): first login provisions BOTH Personal (light seed)
  and `_system` via `POST /api/workspace/init` (idempotent; the lazy first-dispatch seed remains a
  fallback). Wired from the terminal's `findOrCreateUserToken`.
- **Light default seed** (✅): a new workspace seeds from the light `default` template (**not** FINOS —
  `DEFAULT_TEMPLATE`/`default_template` flipped), whose **`README.md` is a human onboarding-dashboard**
  ("what's in here and what matters"), not developer docs. Convention: **the README is every
  workspace's dashboard**, kept current by the agent (stated in the seed `CLAUDE.md`). `default` is
  the one template that ships (`behavior/workspaces/default`); `VEXA_DEFAULT_TEMPLATE` names another
  subdirectory of `VEXA_WORKSPACE_SEEDS_DIR` if you add one, and the worker loads that template's skills.
- **First-view / landing** (✅, `firstView.ts` + `Workbench.resolveFirstView`) — on login the pinned
  first tab is chosen by what's shared: **nothing → own README-onboarding**, **shared workspace → that
  workspace's README**, **shared meeting → the meeting**, **meeting + workspace → the workspace README
  + the meeting** (its live badge). One resolver, replacing the old racing auto-opens.
  - A **just-accepted invite is explicit** and outranks a saved layout: it **pins the shared workspace's
    README AND forces the Knowledge section open** so the joiner actually sees the shared workspace's
    tree (`pinReadme(slug, forceKnowledge)`). **Gotcha handled:** the default Sessions view is *chat-only*
    (the dockview grid isn't mounted, so the resolver's `onReady` never fires) — an early effect
    un-chat-onlys the layout when a pending landing (`vexa.openWorkspace` / `vexa.openMeeting`) exists, so
    the grid mounts and the resolver runs. Without it an accepted invite silently dropped onto the session
    chat instead of the workspace.
- **Normal workspaces are single rank** (sharing roles — see below). Created blank + additive; every
  workspace has a root `README.md`.
- **Per-workspace PURPOSE** (✅, `workspace_purpose.py`) — the capability that makes the flat model
  *usable*. Each workspace carries a one-line statement of what it's **for / what the agent should write
  there**, stored as a plain `PURPOSE` file at the workspace root (committed to its git, so it **travels
  when the workspace is shared** — a member who mounts a `customer-deal` workspace inherits its purpose).
  The dispatcher reads each mount's purpose (`dispatch.py`) and `engine.mounts_preamble` declares it to
  the model with a routing instruction — so an agent with a *composition* mounted (Personal + a
  customer-deal shared ws + a sales-dept ws) **knows what belongs where** instead of dumping everything in
  one place. Editable in the manage panel (below); capped to a one-liner (`MAX_PURPOSE_LEN`) so it stays a
  cheap preamble line, not a document. **Why:** flat mounting is the *mechanism*; purpose is what keeps a
  multi-workspace mount set from becoming a junk drawer.

## Workspace states — active, inactive, hidden

Every workspace a person has is in one of three states, for that person:

| State | Mounted for the agent | Listed (Files, pickers, `workspaces`) | Reversible |
|---|---|---|---|
| **Active** | yes, by default in new chats | yes | — |
| **Inactive** | only in a chat that names it | yes | — |
| **Hidden** | never | no — the agent is not told about it unless asked | yes, unhide = active |

Each chat has one **target** (where writes go, or none) and its own **reads** (what is mounted). A
new chat starts from the person's default profile, else their default target and active workspaces.
Everything is set in the chat: "write here", "exclude this", "include Example Bank", "no workspaces",
"hide the old ones", "new chats should write to Example Bank". The chat header shows one read-only
chip — the profile and its parameters, e.g. **Work · writes to biz · reads 3**, **Incognito**, or
**Writes to Personal · Reads 2 workspaces** — and the full parameters on hover. There are no toggles
in the header or the Files pane; the agent announces each change in one line.

**Chat profiles** are named presets of a chat's scope: **work**, **study**, **hobby** (the person
edits what each writes to and reads), **shared work** (writes to and reads only the workspace bound to
its `{{workspace}}` variable — "use shared work for Collab Room") and **incognito** (no workspaces,
nothing written to workspaces, never read by another chat, left out of chat search, deleted once it has
been idle longer than `incognito_retention_days` in `_global/POLICIES.md`, 7 by default; the purge
runs the next time the person's chat list is read, and until then the conversation itself is kept
in the person's private system space). "Start an incognito chat" opens a new chat in it.
The company seeds more profiles in `_global/PROFILES.md` front matter
(`profiles: {name: {target, reads}}`, `{{workspace}}` allowed) and a default for new chats with
`default_chat_profile:` in `_global/POLICIES.md`; a person's own default and edits win. Opening a
workspace invite link starts the person's next new chat in **shared work** bound to that workspace.
Two workspaces with one name are always named apart: *biz (yours · biz · empty)*, *biz (shared ·
biz-864aed)*.

Hiding a **shared** workspace hides it for that member only; membership and everyone else's view are
unchanged. The **personal** workspace can't be hidden, shared or deleted. **Deleting** a shared
workspace is for its owner; when other members exist, the first call names them and nothing is
deleted until the person confirms. Existing workspaces start active; nothing is hidden for anyone
automatically.

Agent tools: `workspace_list` (states, this chat's target and reads, the defaults),
`workspace_state_set` (`workspaces` or `"all"`, `excluding`, `state`, `scope`),
`workspace_defaults_set` (`target`, `active`), `workspace_target` (this chat's target),
`workspace_remove` (`confirm` for a shared one), `workspace_new` (`slug` to choose one),
`workspace_pull` (`merge` to reconcile a workspace and its repository when both moved; a conflict
changes nothing and names the files), `chat_profile_list`, `chat_profile_set` (`workspace`,
`new_chat`) and `chat_profile_edit`.

### How it works

- **One store per fact.** The person's states live in their attach state
  (`workspace_attach.py`, `<root>/.attached/<subject>/state.json`): `active_set` for their own,
  `hidden_shared` for shared ones switched off, `hidden` for both kinds. The older per-workspace
  "archived" flag reads as hidden. A chat's reads and target live on the chat's session record
  (`_Sessions.set_reads` / `set_target`); the default target where it always was. agent-api is the
  only writer of all of them.
- **Mounts follow the state.** `dispatch.build_mount_set` mounts the chat's reads plus its target when
  the chat has its own reads, and the person's active set when it does not. A hidden workspace is not
  mounted by any path — active set, chat reads, or a scaffold naming it — so it is not on the worker's
  disk.
- **Which chat.** A worker's call names its chat by the unit its delegation was signed for and cannot
  name another; the header's toggles pass the chat id.
- **The header follows the agent.** When a state, target, profile or defaults verb answers, the
  terminal re-reads `GET /api/workspace/states` and the chip updates. Opening a chat no longer
  changes the person's states. A person-wide change marks every warm chat of theirs stale, so its
  next message runs with the new mounts.
- **Profiles** live in the same attach state (`profiles`, `default_profile`). A new chat's first turn
  applies the default profile (else the default target) — server-side, so the header and the turn
  read one record.

### Why it complies

- **One writer** per surface: agent-api for states, reads, target and defaults; the terminal only
  mirrors them.
- **MCP first:** every act is a tool; the header line is a view of the same verbs.
- **The leak rule is unchanged:** a turn other people read is still narrowed by
  `session_access.narrow_mounts` after the chat's reads are applied, so reads can only narrow it.
- **Person in the loop:** `workspace_state_set` and `workspace_defaults_set` are person verbs
  (`routes.v1.json` `verbs`); a worker running without a person is refused. Delete stays a person
  verb and names the members who would lose a shared workspace before anything is removed.

**Gates.** P2 `gate:isolation`, P4 `gate:schema` and `gate:contract-version` (the new routes and
tools are rows in the sealed `routes.v1` and `mcp.tools.v1`), P6 `gate:exports` and P23
`gate:dataflow` are green on the release head. P20 (who may change a state, a default or a
profile) and P21 (the header reads the server's state, never a draft) are ungated: reviewed, and
held by the tests below.

## Sharing model (`workspace_membership.py`)

The person-facing steps (adding a member, joining from a link, what each refusal means) are on
[Minutes → Workspaces](/minutes/workspaces). This section is the model behind them.

**Three roles.** `owner > contributor > viewer` in the lattice, said to people as owner, contributor
and reader (`ROLE_SENTENCES`): an owner writes the workspace and adds or removes members, a contributor
writes it, a reader reads it. An invite may be minted for any of the three (`INVITABLE_ROLES`).

- **Inviting a person** — `POST /api/workspace/invite` (the agent's `workspace_invite` tool) is
  owner-only. It mints an invite `restricted` to the named address, hands the link back for an address
  this instance knows, and otherwise publishes a `workspace.invited` event for the flows service to mail.
- **A link** — `POST /api/workspace/invites` mints a link for an owner or contributor of the workspace;
  `DELETE /api/workspace/invites/{id}` withdraws one. An invite that names addresses is `restricted` to
  them; one that names none is `open`. Asking for both is refused.
- **Only an owner** removes members or changes a role (`require_role(..., "owner")`).
- The system workspace and a person's own private workspaces are never shareable (`assert_shareable`).

**Where membership and invites live:**
- **Members** — the workspace's own git repo, `policy/members.json`
  (`[{subject, role, added_by, added_at, email?}]`), authoritative and travelling with the workspace.
- **Index** — `users.data.memberships[]` for "shared with me", through the `MembershipIndex` port
  (admin-api `/internal/users/{id}/memberships`).
- **Invites** — `<store-root>/.invites/<workspace_id>.json`, outside every workspace mount, holding only
  the sha256 of each token (`{id, hash, role, mode, allowed_emails, expires_at, max_uses, uses,
  created_by, created_at, revoked}`). An invite is capability material, so it never sits in a tree that
  gets published, attached or reseeded.

**Human roster.** The gateway-verified `X-User-Email` is written into the member record at every grant
(`ensure_owner`, and `accept_invite` → `grant_membership`), so the participant list shows addresses; a
row granted before that fills in its email the next time that member opens the list.

**`policy/` is platform-write-only:** an agent turn may never write `policy/`; the worker's turn-commit
reverts any `policy/` change (`_revert_policy_writes` → `{"type":"policy-reverted"}`). Membership is
written only by `workspace_membership.policy_commit` (platform git identity).

**A worker stays inside its dispatch's workspaces.** An agent worker dispatched without a person in
the chat (a routine, an event) carries the exact set of workspaces it may touch. agent-api refuses
(`403`) any route that names a workspace outside that set, checked where the workspace is resolved,
and the worker sees only the shared workspaces inside it. See
[Security & compliance → Agent workers](/security-compliance#agent-workers).

## Joining a workspace — `/join`, preview, sign in, accept

1. **Link.** An invite link is `<VEXA_UI_URL>/join?i=<token>` (`JOIN_PATH`). With `VEXA_UI_URL` unset,
   agent-api returns no link and says which key names it.
2. **Preview, before sign-in.** The `/join` page calls the terminal's `GET /api/join/preview?i=`, which
   passes the token to agent-api's `GET /api/workspace/invites/preview`. The preview takes no user key,
   grants nothing and consumes no use; it answers who invited you, to which workspace and as what, and
   `404` for a token that matches nothing, so it never enumerates workspaces.
3. **Sign in** with any of the terminal's sign-in doors; the invite rides through sign-in.
4. **Accept.** The terminal calls `POST /api/workspace/invites/accept` through the gateway. agent-api
   checks the gateway-verified email against a restricted invite's addresses, the expiry and the use
   count, then adds you to the roster with the invite's role.
5. **Land** on the shared workspace (see First-view above).

Code: `workspace_membership.preview_invite` / `accept_invite`, `routers/sharing.py`,
`clients/terminal/src/app/api/join/`.

## Managing a workspace — the manage panel (✅)

Every workspace opens a **center-tab manage hub** (click the workspace name in the WORKSPACES sidebar).
One place for everything about that workspace, so the sidebar row stays minimal (just a **checkbox** =
mount/park + the **name** = open panel; the old per-row action icons were removed). `workspaceManage.tsx`:

- **Rename** (display label) · **on/off** toggle (mount into the agent or park).
- **PURPOSE** — view/edit the one-liner that steers what the agent writes here (see Per-workspace PURPOSE).
- **GitHub** — publish (create repo + push), **push** / **pull** (fast-forward only, ahead/behind counts),
  Open-on-GitHub. Uses the saved GitHub token (below) so it doesn't re-prompt.
- **Participants** — the roster (emails), **invite link**, **add by email**, remove member, **leave**
  (self), **unshare** (creator), **archive** / **delete**.

A **shared (group) workspace can be loaded from an existing repo too** — `POST
/api/workspace/shared/{workspace_id}/attach`, contributor-or-owner only, with the same park-and-clone
mechanic as the personal swap. The group's `policy/members.json` is carried into the attached clone and
kept untracked there, so loading a repo can neither lock the group out nor push its member list to
somebody else's repository. In minutes mode the action is in the chat's workspace `+` menu and in the
account menu (**Attach existing repo…**).

Create flows are also panel/modal-based, not inline: **Attach repo** opens a portaled `Modal`
(`ui-kit/Modal.tsx`); **New workspace** creates a blank additive workspace. Code:
`clients/terminal/src/surfaces/workspaceManage.tsx`, `workspace.tsx` (sidebar rows), `ui-kit/Modal.tsx`.

## Reusable GitHub token (✅)

Save a GitHub PAT **once** and reuse it for every git op across **all** repos, instead of re-entering it
per push/pull/publish/attach. Set it in **API Tokens → GitHub**; the git-op forms then don't prompt.

**Security model:**
- **Kept in the credential broker** — saved in the [credential broker](/connections#git-credentials)
  (AES-256-GCM, its own volume and key), never on agent-api's volume and never inside a git tree.
  agent-api fetches it as the broker's `git` role, only for the person the gateway signed for, and uses
  it for one operation. Without a configured broker, saving one is refused (`503`,
  `git_credentials_unavailable`).
- **Browser-isolated** — never returned to the client; a read yields only a `••••abcd` mask.
- **Never transits the gateway as a header** and never leaves the services that keep and use it.
- **Applied then scrubbed** — git ops fall back to it when no per-call token is given; it rides the push
  URL for that op only, is **redacted from every error/log** (P15), and is never written to `.git/config`.
- **Moving from older releases** — a token an older agent-api kept under `<workspaces>/.secrets/`
  (sealed with `VEXA_SECRETS_KEY`, or plaintext `<subject>.ghtoken`) moves into the broker on first use
  and the old file is removed after the broker confirms it; the broker's one-shot import moves all of
  them at once ([Connections → Git credentials](/connections#git-credentials)). Still use a
  **minimally-scoped, revocable fine-grained PAT**: a stored PAT is password-equivalent.

Code: `git_credentials.py` (`set`/`read`/`masked_github_token`), `git_secret_store.py` (the broker client),
`api.py` (`GET`/`POST /api/workspace/git-token`; push/pull/publish/attach fallback), `tokens.tsx` (the
card, reachable in minutes mode from the account menu).

## Deploy key per workspace (✅)

The **primary** credential for loading an existing repo, and the reason "how do we manage the secrets?"
has an answer that is not "a box". Each workspace mints its own **ed25519** keypair; the person adds the
**public** half to their repository as a write deploy key, and nothing of theirs is ever held here.

- **Scoped to one repository**, unlike a PAT (which is a bearer credential over every repo the account
  can reach) — and revoked by the person, on their own repo, without telling us.
- **The private half has no read path.** Generated by `ssh-keygen`, kept in the credential broker,
  and materialized into a `0600` file inside a `0700` temp dir for the length of ONE git op. Git ops run
  with `GIT_SSH_COMMAND` through `shared/gitexec.py` (no program the repository names runs), `IdentitiesOnly=yes` (the host's own
  keys can never stand in for a workspace's) and `BatchMode=yes` (a bad key fails loud, never hangs).
- **Idempotent** — re-asking returns the SAME public key, so a key already added is never invalidated.
- **The URL decides which credential is used**: `ssh://` / `git@host:` → the deploy key; `https://` →
  the saved PAT. Neither is ever embedded in a persisted remote.
- **What an agent may see is a capability, never material**: `"origin git@github.com:acme/kg, deploy key
  set"`. Not the key, not the PAT's last-4.
- **The refusal is the feature**: the control-MCP workspace tools take no credential parameter, and
  reject one smuggled into a URL or branch — a secret pasted into a chat is in that transcript forever.
  When git refuses us and we hold nothing, the reply is the public key plus *"say `done` when added"*.

Code: `deploy_keys.py`, `workspace_credentials.py` (which credential, in what order),
`api.py` (`GET`/`POST /api/workspace/{slug}/deploy-key`), `core/agent/mcp.tools.v1.json`
(`workspace_attach` · `workspace_status` · `workspace_pull` · `workspace_push`).

## Live collaboration (during a meeting) — all ✅

Meetings BIND to workspaces (`meetings.data.workspace_id`): a member of the bound workspace sees the
meeting — the upcoming PLAN (planned meetings + auto-join + ICS calendar sync, 2026-07-08), the live
feed, and the transcript. The user-facing story is `docs/docs/core/meetings.mdx` +
`docs/docs/how-to/plan-a-meeting.mdx`; the prep tab is `clients/terminal/src/surfaces/meetingPrep.tsx`.

A member's edits in a shared workspace surface live to the other members:

- **One aggregated activity feed** — the SOURCE CONTROL panel merges commits across ALL active
  workspaces, recency-sorted, each labeled with its workspace (no per-workspace strips). Changed files
  are **clickable links** that open the doc.
- **"New updates" badge on the Knowledge nav** — counts OTHER members' commits since Knowledge was
  last opened; polled always (even on Meetings/Sessions); clears on opening Knowledge.
  (`clients/terminal/src/surfaces/updatesBadge.ts` + the Workbench poll.)
- **Live doc auto-reload** — an OPEN doc reloads (5 s poll) when a member edits it; an "Updated just
  now" banner + one-click **Changes** panel showing that file's latest highlighted diff.
- **Attribution by EMAIL** — commits are authored as the human editor's email (`X-User-Email` stamped
  as the git author name; the synthetic `<subject>@vexa.local` stays for the you/member classification).
  `git_state_at(viewer)` classifies each commit `you` / `member` / `system`.
- **Highlighted diffs** — `GET /api/workspace/git/show` returns a commit's unified diff; the UI renders
  `+`/`−` line highlighting.
- **Cross-workspace file search** — Find-file spans every active workspace, not just the primary; hits
  are tagged with their workspace and open against the right mount.
- **README auto-pinned** when a shared workspace connects — collaborators land on the doc.
- **The 6 s poll is the accepted change-feed** (owner ruling) — no SSE push needed.

Delivery mechanics: **Lane W** serialises the attributed writer per shared repo
(`core/agent/shared/adapters.py workspace_write_lock`); note the flock is not yet on the live commit
path (`dispatch.py` comment) — drive concurrent shared writes **sequentially** for now (⬜ to wire).

## Entity pages — sources, the company tier and write-back (✅)

An agent records what it learned about a person, company, meeting, project or decision with
`entity_upsert`, which writes `kg/entities/<kind>/<slug>.md` (`core/workspaces/shared/entities.py`).

- **Sources.** Every call carries one `source`. The page lists each distinct source once, in the
  `sources:` front matter and under `## Sources`. A source may contain commas, quotes or `#`
  (*"Zoom call 17, 2026-10-09 14:07 UTC"*); it stays one source, and upserting it again adds
  nothing. A page written before this rule, whose sources were split at their commas, is repaired the
  next time the same source is upserted.
- **The company tier.** `slug="_global"` writes a company-tier page into the organisation's layer.
  Only the admin account may do that; anyone else gets `403 only the admin account may write company-tier pages
  into _global` and writes the page on their own desk instead. The `extend-meeting` and `create`
  briefs say so, so an agent that is not the admin account does not try.
- **Write-back.** After a turn, a mechanical pre-pass lists names the turn mentioned that have no
  page, and a write-back phase may create them. The assistant's own model name (*Claude Sonnet …*,
  *Claude Opus …*) is never a candidate; a person or company that merely starts with the same word
  still is.

**Limits and faults.** The front matter stays one-line YAML flow lists, so any YAML reader parses it.
A split page heals only for a source that is upserted again; other halves stay until edited.

## How it works

**Importing a repository as a workspace** (`POST /api/workspace/import`, also the control MCP's
`workspace_import`):

1. The terminal or an agent calls agent-api through the gateway. The route is declared `person` in
   `core/agent/routes.v1.json`, so a worker with nobody in the loop is refused.
2. agent-api checks the repository URL and ref, and derives the new workspace's slug from them. If the
   caller names a `credential_workspace` to reuse its deploy key, they must be its owner.
3. The route answers `202` with an `operation_id` at once. The import runs as a job whose status record
   is written under `.imports/<subject>/` in the store, outside every workspace mount. Poll
   `GET /api/workspace/import/{operation_id}/status`; only `completed` means the workspace is usable.
4. `workspace_credentials.for_workspace` picks the credential: the workspace's deploy key for an
   `ssh://` or `git@host:` remote, else the person's saved token for `https://`, else nothing (a
   public repository). The credential lives only inside the operation, never in the job record.
5. The clone runs through `gitexec` into its own slot `<store>/<slug>`, with its own root and Git
   history. Personal and the other workspaces are left as they are.
6. `workspace_ids.sync_workspace` gives the tree an id (kept in `.vexa/workspace.json`, committed to
   the tree) and points agent-api's registry at the slot. A repository that already carries an id keeps it.

A shared workspace can load a repository too (`POST /api/workspace/shared/{workspace_id}/attach`,
contributor or owner). Its `policy/members.json` is carried into the clone and kept untracked there.

**Syncing with GitHub** (`workspace_status`, `workspace_pull`, `workspace_push`). The agent's sandbox
cannot write a workspace's `.git` and has no git credential, so it syncs only through these platform
verbs, each a route in `routers/workspaces.py`:

1. `workspace_status` (`POST /api/workspace/status`) resolves the workspace through `_manage_dir`
   (the caller's own, or a shared one they are a member of), picks the credential a pull would
   (`workspace_credentials.for_workspace`), and runs `workspace_git_sync.fetch_status`: a fetch of
   the branch into `refs/remotes/<home>/<branch>` and nothing else. It reports branch, upstream,
   ahead/behind, the commits on each side (sha, subject, file count; at most 50 listed), uncommitted
   and untracked paths (read with `GIT_OPTIONAL_LOCKS=0`, so not even the index is rewritten), and
   `fetched_at` / `previous_fetch_at` (from `FETCH_HEAD`). Refusals carry `detail.refused`:
   `no_remote` and `detached` (409), `no_credential` (424, with the deploy-key sentence) and
   `network` (502, with `previous_fetch_at`).
2. `workspace_pull` fetches and fast-forwards; a divergence is refused. `workspace_push` pushes
   fast-forward only. Both are `person` verbs; `workspace_status` is not, because it changes nothing a
   person sees.

### Where repositories live: a volume or S3

`VEXA_WORKSPACE_BACKEND` (Helm `agentApi.workspaces.backend`) is `volume` by default: the tree under
`VEXA_WORKSPACES_DIR` on the `agent-workspaces` volume is the truth, and workers mount it. With `s3`,
an S3-compatible bucket is the **single durable truth** and every pod copy is a disposable cache
(`core/workspaces/store`):

1. **Boot.** agent-api writes, reads and deletes a probe object, then probes conditional PUT and bucket
   versioning (`objects.self_test`). A failed probe stops the boot with a sentence naming the endpoint,
   the bucket and the failed call. It loads the platform files and `_global`. Every other workspace
   becomes a stub: its folders, empty placeholders for HEAD's files, and a marker. The boot drops
   anything cached that the bucket does not hold and installs the observers on `gitexec` and
   `workspace_paths`.
1. **First use.** The first access to a stub through `workspace_paths` or `gitexec` (the only ways
   agent-api reaches a work tree) hydrates it. It is built beside the stub and swapped in by rename.
   The least recently used workspaces are evicted back to stubs to keep the cache under
   `VEXA_WORKSPACE_CACHE_MAX_BYTES`. Eviction never takes `_global`, a workspace in use or locked,
   one with uncommitted changes, or one whose refs are not the published generation's.
2. **A write from a route.** Every git command that can move a ref (`commit`, `merge`, `reset`,
   `clone`, …) passes the observer: it takes the workspace's Redis lock, checks the cache is at the
   bucket's current generation (refreshing it when clean), lets git run, then publishes the new refs as
   generation N+1: a git bundle (incremental, compacted after 32) and a manifest
   `repos/<path>/@/gen/<N+1>-<fence>.json`. Before the PUT it re-reads the current generation and
   refuses if that moved or carries a newer fencing token: this writer outlived its lock. After the
   PUT it acknowledges only if its object is alone at N+1. Only then can the route answer.
   A publish that fails puts the files it changed back to the last durable generation and the route
   answers 503 (`workspace_store_unavailable`), or 409 (`workspace_changed`) when another writer got
   there first.
3. **What is not a git command.** A platform file at the store root (attach state, `.policy/`, import
   status) written or removed through `workspace_paths`, `atomic_json` or a by-name writer's
   `notify_written` is in the bucket before the call returns, on any thread. A change the bucket did
   not take is reverted and the call raises (503). Trees moved whole inside a request are mirrored by
   `CacheSync` before the response leaves. A 30-second pass only reconciles and evicts.
4. **A worker.** Its `/workspaces` is an `emptyDir` (`VEXA_WORKSPACE_MOUNT_SOURCE=emptyDir:` on the
   runtime). At boot it fetches only its dispatch's mounts from `GET /agent/workspace-store/fetch`
   through the gateway with its delegation token; before each turn it fetches what changed. Each
   commit in a writable mount is pushed to `POST /agent/workspace-store/push` before `run_git` returns,
   so the turn's commit event comes after agent-api has made it durable. A refused push un-commits
   locally and the turn reports the write as not saved. agent-api refuses a push whose commits touch
   `policy/`, `.vexa/`, `.claude/` or `.git` in any letter case (403 `reserved_path`), and holds it to
   the private-write rule: when the session read the person's private data and someone else reads the
   workspace, every file version a pushed commit writes is checked as a page write, and a held one
   refuses the whole push (409 `private_sources_to_shared`, with the held paths and their confirmation
   codes). Who else reads it comes from the membership store that decides access, never from the
   `policy/members.json` copy in the tree. When that store does not answer, such a push is refused
   (503 `policy_unreadable`) and nothing lands. Commits the harness made by itself are checked the same
   way as the worker's own.

The guard needs no conditional PUT: the per-workspace lock, a monotonically increasing fencing token
stamped into every generation, and one key per (generation, token) with "alone at its generation" as
the condition for acknowledging. Readers take the highest generation and, within it, the lowest token.
Conditional PUT is only reported. Linode Object Storage closes the connection on a conditional PUT to
an existing key (probed 2026-10-17). `/health` reports
`workspace_store: {backend, bucket, conditional_put, versioning, guard, last_error}`. Moving an existing
volume into a bucket is `python -m workspaces.store.migrate` (the Helm migration Job), which verifies
every repository from a fresh cache before the switch.

**Every path from outside goes through one rule.** `core/workspaces/shared/workspace_paths.py` answers
whether a name or path stays inside a workspace:

- **A workspace name** is one path segment of letters, digits and `. _ -`, at most 121 characters,
  starting with a letter, digit or `_` (`is_workspace_name`). So never a separator, a dot-name, `.`
  or `..`. Names reserved for the platform (`_system`, `_global`, `seed`, …) are refused by the caller
  that owns them (`workspace_membership.RESERVED_SLUGS`).
- **A path inside a workspace** is refused if it is absolute, uses `..` to leave, leaves through a
  symlink, or reaches a reserved directory: `.git`, `.vexa` (the workspace id) or `.claude` (the
  agent's own state). The caller gets one sentence for all four reasons; the log line names which.
- **Fixed platform files** (`policy/members.json`, the id file, routine state, …) are read and written
  by descriptor without following a link at the file or at any directory above it.

**A lookup never registers.** Naming a slug in a request (`GET /api/workspaces/by-slug/{slug}`, a
link's "here") uses `workspace_ids.resolve_slug`. It can re-point a record the tree already carries,
but it never mints an id and never creates a record. Platform directories at the store root
(`.attached`, `.system`, `lost+found`, …) are never a workspace, whoever names them. Only acts that
create or move a workspace call `sync_workspace`.

**During a turn** the worker runs as root and starts the model's tools as the unprivileged
`vexa-tools` user (`core/agent/worker/Dockerfile`, `llm/ports.py`). Each turn it hands that user, by
group, only the workspaces the turn may write. A repository's `.git` is never handed over, so the
tools can read history but not write the repository; a work-tree root is made sticky so `.git` cannot
be renamed away. If a path cannot be handed over, the turn does not run. At write-back, any change
the turn made under `policy/` is reverted, and the commit runs through `gitexec`, which runs no
program the repository names (hooks, filters, credential helpers, …). Where the worker cannot switch
users (Lite's per-tenant UID), it makes itself non-dumpable instead.

**Recording an entity** (`POST /api/workspace/entity`, the `entity_upsert` tool):

1. The agent's call reaches agent-api as the person (`routers/workspaces.py` `ws_entity_upsert`).
   `slug="_global"` is refused unless `global_layer.is_admin` says the caller is an org admin;
   any other slug resolves through `_read_target(write=True)`.
2. `entities.upsert_entity` reads the page's front matter. `_list_field` reads `sources:` and
   `aliases:` as YAML flow lists, honouring quotes; `_render_list` writes them back deduplicated,
   quoting any item that would not read back as itself, and folds the comma-split halves of a value
   being added back into it.
3. `## Sources` is rebuilt from `sources:`; each new fact is stamped `— source: <source>` once.
4. agent-api commits the page and `kg/INDEX.md` by pathspec, authored by the person.

### Security

- **Who can reach what.** A person reaches only their own workspaces and the shared ones they are a
  member of. Inviting needs `contributor`; unsharing, removing members and changing roles need
  `owner`. Only the platform writes `policy/`.
- **At the gateway.** Workspace routes need a signed-in person; importing with saved credentials needs
  a person in the loop.
- **In agent-api.** Every slug or id is checked against the name rule and resolved inside the caller's
  store; every path against the four refusals. A lookup creates nothing.
- **In the worker.** The worker's filesystem holds only the turn's mounts. The model's tools run as
  `vexa-tools`, cannot write `.git`, and cannot change the member list.
- **The bucket (s3 backend).** Only agent-api holds the bucket key, a static key scoped to the
  workspaces bucket. A worker fetches and pushes only the mounts its own dispatch recorded
  (`wsstore:unit:<unit>`), pushes only writable ones, fast-forward only; a pushed commit range that
  touches `policy/`, `.vexa/` or `.git` is refused (`403 reserved_path`), and every pushed object is
  fsck'd and fetched through `gitexec`.
- **Credentials.** A Git token or deploy key is never returned to the browser or the agent, never
  written into a remote URL or `.git/config`, and never accepted from chat text.
