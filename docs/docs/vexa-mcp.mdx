The MCP server runs as its own service and is fronted by the gateway at `/mcp` on **self-hosted
Docker Compose from 0.12.18 onward**, on **Kubernetes**, and on the **hosted service** at
`https://api.cloud.vexa.ai/mcp`.

Verified against the hosted service on 2026-08-18: `initialize` returns
`Vexa MCP Service (v0.12)` over protocol `2024-11-05`, `tools/list` returns the nine tools below,
`prompts/list` returns the four prompts, and tool calls carry the caller's own credential through to
the gateway. That is the end-to-end client proof
[#888](https://github.com/Vexa-ai/vexa/issues/888) was waiting for.

## What it is

An MCP client — Claude Desktop, an IDE, any MCP-compatible agent — gets Vexa's meeting capabilities
as standard **MCP tools and prompts**, with no bespoke API integration.

The service is a stateless FastAPI app whose routes *are* the tools. It wraps the **public API
only**: every tool call forwards the caller's credential to the gateway as `X-API-Key`, and the
gateway resolves the key and enforces scopes. It holds no credentials, touches no database, and
never reaches into other services directly.

## Tools

Nine tools, plus four prompts (`vexa.meeting_prep` · `vexa.during_meeting` · `vexa.post_meeting` ·
`vexa.teams_link_help`).

| Tool | Wraps |
|---|---|
| `parse_meeting_link` | pure — URL to platform / `native_meeting_id` / passcode, no gateway hop |
| `request_meeting_bot` | `POST /bots` (accepts `meeting_url` **or** `native_meeting_id`) |
| `get_bot_status` | `GET /bots/status` |
| `update_bot_config` | `PUT /bots/{platform}/{native}/config` |
| `stop_bot` | `DELETE /bots/{platform}/{native}` |
| `list_meetings` | `GET /meetings` |
| `get_meeting_transcript` | `GET /transcripts/{platform}/{native}` |
| `list_recordings` | `GET /recordings` |
| `get_recording` | `GET /recordings/{recording_id}` |

`update_bot_config` wraps a route that is not wired in the v0.12 open core and returns `404` — see
[Meetings API → Manage the bot](/api/meetings#manage-the-bot). The other eight reach live routes.

### Tools the deployed domains add

At start-up the server asks each deployed domain for its tool manifest (`mcp.tools.v1`) and serves
the union beside the tools above — one server, one tool list. With the agent domain deployed that adds
the workspace tools (reading, and the page verbs `workspace_write`, `workspace_delete`,
`workspace_move`, `entity_upsert` and `fetch_asset`), the claim book (`propose`, `validate`), membership (`workspace_members`, `workspace_invite`,
`workspace_membership`), the transcript highlight (`transcript_terms`), the company-layer accept (`mark_global_ready`), Connections (`connection_request`, `connections_status`, `gmail_search`,
`gmail_read`, `gmail_thread`, `calendar_events`, `mail_inbox`, `mail_read`, `gmail_draft_create`,
`secret_service_call`, `onboarding_research`), the person's clock (`current_time`, `timezone_set`) and
`chat_name`; with flows deployed, `whats_waiting`, `report_friction` and the flow tools. Each is a route
its domain serves, and the tool's arguments and description are that route's own.

### Agent workers use this same server

Every agent worker attaches this server, through the gateway's `/mcp`, as its `vexa` toolbelt. Its
bearer is a delegation token minted for that one dispatch (`vxd_…`, 30 minutes by default, replaced
before it expires while the worker runs, and revoked when the worker's unit ends); the gateway
resolves it through identity like an API key — as the person the worker acts for, with scopes `bot` and
`tx` — and every tool call it makes is checked as theirs. Apart from the harness's own friction
report, the token works on `/mcp` and nowhere else: a worker calling the REST API with it is refused. A worker dispatched without a person in the
loop (a routine, a meeting-triggered run) is refused the verbs that need one. There is no second MCP
server for workers.

## Connect a client

Point the client at the **gateway**, not at the MCP service's own port — the gateway is the
authenticated front door.

**Don't have a key yet?** Hosted: sign in at [vexa.ai/signin](https://vexa.ai/signin) with a Google
account and copy your key from [your account page](https://vexa.ai/account) — free credit, no card
required. Self-hosted: `make all` prints a key when the stack comes up.

```json Hosted
{
  "mcpServers": {
    "Vexa": {
      "command": "npx",
      "args": ["-y", "mcp-remote", "https://api.cloud.vexa.ai/mcp",
               "--header", "Authorization: Bearer ${VEXA_API_KEY}"]
    }
  }
}
```

```json Self-hosted compose
{
  "mcpServers": {
    "Vexa": {
      "command": "npx",
      "args": ["-y", "mcp-remote", "http://localhost:18056/mcp",
               "--header", "Authorization: Bearer ${VEXA_API_KEY}"]
    }
  }
}
```

Self-hosted compose requires **0.12.18 or later** — that is the release in which the gateway began
fronting `/mcp`. `18056` is the compose `API_GATEWAY_HOST_PORT`.

The key may arrive as `X-API-Key` or as the MCP transport's `Authorization: Bearer <key>`; both are
forwarded on. Auth at the edge is fail-closed and identical to every other route
([Authentication](/authentication)).

<Note>
The MCP service also publishes a direct host port (`127.0.0.1:18010` by default) for local
debugging. **It bypasses the gateway, and therefore bypasses authentication.** Do not expose it.
</Note>

### How the transport is forwarded

The two legs of streamable HTTP are forwarded differently, and the difference is the point
([#795](https://github.com/Vexa-ai/vexa/issues/795)):

| Leg | What it is | How the gateway forwards it |
|---|---|---|
| `POST /mcp` (and `PUT`/`PATCH`/`DELETE`/`OPTIONS`) | a message — short request/response JSON | buffered forward, status and body verbatim |
| `GET /mcp` | the server-to-client SSE stream: headers, then silence until the server pushes | **relayed unbuffered**, on a dedicated streaming client |

Buffering the `GET` leg is what produced the original failure: the proxy waits on the next body read
of a healthy-but-silent stream, hits its read timeout, and manufactures a `503` the MCP service
never sees.

## How it works

This section follows a worker's tool call, the delegated path. A person's own API key takes the same
path from step 3 on, without steps 6 and 7.

1. **agent-api mints a token for the dispatch.** When it builds a worker's environment, agent-api
   mints a `vxd_` delegation token (`delegation.v1`, `core/agent/control_plane/dispatch.py`). The token
   names the person (`sub`), the regime (`human` for a `message` trigger, `autonomous` for any other),
   the workspace ceiling (`"*"` for a human turn, the dispatch's exact workspaces otherwise) and an
   optional default `target` workspace. Its lifetime is `VEXA_MCP_DELEGATION_TTL_SEC`, 1800 s by
   default.
2. **agent-api records it before the spawn.** It writes the token's `jti` against the unit, plus a
   live record that identity checks (`control_plane/delegation_revocation.py`). A token it cannot
   record is withheld: the worker then runs without the vexa toolbelt and the log says so.
3. **The worker calls the gateway's `/mcp`** with the token as its bearer. The worker writes its MCP
   attachment outside every mounted workspace, and removes the token from its own environment at boot
   so harness subprocesses do not inherit it.
4. **The gateway resolves the bearer** through identity's `POST /internal/validate`, declaring that
   it reads delegation answers. Identity verifies the signature, audience and expiry, checks the live
   record in Redis, and answers with the person, scopes `bot` and `tx`, the person's workspaces
   narrowed to the ceiling, and the `delegation` block. The `/mcp` row in
   `core/meetings/services/mcp/routes.v1.json` says `"delegation": true`, so the gateway admits it
   there.
5. **The gateway forwards to the MCP service** with a signed identity, `X-Vexa-Identity`
   (`gateway-identity.v1`), that carries the same person and delegation.
6. **The tool calls back into the gateway.** The MCP's tools act through the gateway's REST routes
   with the same bearer. The MCP sends back the signed identity it received, as
   `X-Vexa-Internal-Mcp-Identity` (`vexa_mcp/reentry.py`). It holds no key and verifies nothing.
7. **The gateway admits the re-entry only where both hold:** the route's `routes.v1` row says
   `"mcp_reentry": true`, and the signed identity is the gateway's own, still within its lifetime, for
   the same person and the same delegation as the bearer. The flagged rows are exactly the routes
   the MCP's tools call: the hand-written meeting tools, and every tool in a domain's `mcp.tools.v1`
   manifest (tests hold the two sets equal).
8. **The service behind the gateway enforces the ceiling.** agent-api checks each named workspace
   against the ceiling and the person's own access (`control_plane/ceiling.py`), and a verb that needs
   a person in the loop refuses a worker whose regime is not `human`.
9. **agent-api keeps the token current, then ends it.** Every 30 s its reaper compares its records with
   the runtime's live set. A unit still running gets a new token once half of the current one's life
   has passed. A unit that has ended has its tokens revoked. See
   [Identity & trust](/architecture/identity-and-trust#worker-delegation-tokens).

**Who owns what.**

| Data | Writer | Readers |
|---|---|---|
| The delegation token | agent-api (minted per dispatch, re-minted on refresh) | the worker presents it; identity verifies it |
| `vexa:delegation:*` keys in Redis (unit records, live record, revocation, current token) | agent-api only | identity reads `live:<jti>` and `revoked:<jti>` |
| `unit:<id>:delegation` (the worker's copy of its current token) | agent-api | that unit's worker, read-only |
| `X-Vexa-Identity` | the gateway, the only holder of the signing key | the MCP carries it back; services verify it |
| Which routes admit a worker | each domain's `routes.v1.json` | the gateway assembles them at boot |
| Which tools exist | each domain's `mcp.tools.v1.json` | the MCP assembles the tool list at start-up |

**Contracts and routes.** `delegation.v1` (`core/identity/contracts/delegation.v1/`),
`gateway-identity.v1` (`core/gateway/contracts/gateway-identity.v1/`), `routes.v1`, `mcp.tools.v1`
(`core/meetings/contracts/mcp.tools.v1/`), and identity's `POST /internal/validate`.

**Configuration.** agent-api: `VEXA_MCP_URL`, `VEXA_MCP_DELEGATION_SECRET`,
`VEXA_MCP_DELEGATION_TTL_SEC` (`core/agent/control_plane/config.v1.json`). admin-api:
`VEXA_MCP_DELEGATION_SECRET` and `REDIS_URL`. The gateway: `VEXA_GATEWAY_IDENTITY_SIGNING_KEY_FILE`.
With no endpoint or no secret on agent-api, no token is minted and workers run without the vexa
toolbelt; with no secret on admin-api, every `vxd_` bearer is refused.

**What a worker sees when it fails.**

| Situation | Answer |
|---|---|
| The token is revoked, expired, forged, or its live record is gone | `401 Invalid delegation: <reason>` from identity; the gateway answers `401` |
| Identity cannot read Redis | identity answers `503`; the gateway answers `503 Authentication temporarily unavailable, retry`. People's own API keys are unaffected |
| The worker calls a REST route directly | `403`, "a worker's delegation token is accepted on /mcp only" |
| A verb that needs a person, from an unwatched run | `403` with the shared person-in-the-loop refusal |
| A turn outlives its token | the turn ends with a typed fault (`source: "vexa-tools"`, `kind: "access_expired"`), which the chat shows with a Retry |

## Why it complies

**Architecture** (rules from [Architecture](/governance/architecture)).

| Rule | How this design meets it | Enforced by |
|---|---|---|
| P2 couple only through contracts | agent-api and identity share the minter and verifier as one file vendored byte for byte, not by import; the gateway, agent-api, meeting-api and the broker share `identity_token.py` the same way | `gate:fact-parity` (facts `delegation-token`, `delegation-prefix`, `delegation-accept-header`) |
| P4 sealed schemas at boundaries | `delegation.v1`, `gateway-identity.v1`, `routes.v1` and `mcp.tools.v1` are sealed and golden-pinned, re-verified in Node and Python | `gate:schema`, `gate:contract-version`, `gate:python` |
| P6 one front door | one MCP server for every bearer, behind the gateway's `/mcp`; each domain declares its own routes and tools, and the gateway and MCP assemble them | `gate:python` (`test_create_app_has_no_second_mcp_upstream`, `test_the_mcp_door_is_the_mcp_manifest_s_declaration`) |
| P7 config by env | one recorded departure: a refreshed token reaches a running worker through Redis ([ADR-0045](https://github.com/Vexa-ai/vexa/blob/main/docs/adr/0045-a-workers-delegation-token-lives-as-long-as-its-unit.md)) | ungated: reviewed |
| P18 fail loud | a token that cannot be recorded is withheld and logged; an unreadable store answers `503`, never "not revoked"; an expired token ends the turn with a typed fault | `gate:fault-surfacing` (`test_delegation_refresh.py`) |
| P20 complete mediation | identity verifies every `vxd_` bearer on every request; the gateway admits it per route; the service checks the ceiling | `gate:python` (deny tests below) |
| P23 one writer per carrier | agent-api is the only writer of every `vexa:delegation:*` key and of `unit:<id>:delegation`; the key names are held equal on both sides | `gate:dataflow`, `gate:fact-parity` (`delegation-revocation-key`, `delegation-live-key`) |

**Security.**

- **Who can use a delegation token:** the worker it was handed to, as the person it names, on `/mcp`,
  on the harness's friction report, and on the MCP's re-entry to the routes its tools call. Every
  other route answers `403`.
- **At the gateway:** the bearer is resolved through identity on each request. A `vxd_` prefix alone
  marks a worker, so an identity answer without `delegation` cannot turn it into a person's key.
  Re-entry needs the gateway's own signature, for the same person and delegation.
- **At identity:** signature, audience, expiry, then the live record must exist and no revocation
  must. A resolver that does not declare it reads delegation is answered as for an unknown token.
- **At the service:** the ceiling bounds which workspaces a worker touches, and it never grants what
  the account could not reach. An unwatched run is refused person-only verbs and is never the admin.
- **Between people:** a unit reached by a second person's dispatch never publishes either person's
  token where the other's worker could read it, and the token is in no file another workspace member
  can read.
