Vexa posts signed JSON to a URL you own when a meeting's state changes. Configuration is
self-serve over the API, and every delivery attempt is recorded in a history you can read back.

## Configure

```bash PUT /user/webhook
curl -X PUT "$API_BASE/user/webhook" \
  -H "X-API-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{"webhook_url":"https://example.com/hooks/vexa",
       "webhook_secret":"<shared secret>",
       "webhook_events":{"meeting.completed":true,"meeting.status_change":false}}'
```

<ParamField body="webhook_url" type="string" required>Destination URL. Pass `""` to clear it — `null` is rejected with `422`. A URL naming a loopback, private, link-local or metadata address, or a host name only this deployment resolves, is refused with `422`.</ParamField>
<ParamField body="webhook_secret" type="string">Shared secret used to sign each payload. Omit to leave the stored secret unchanged.</ParamField>
<ParamField body="webhook_events" type="object">A map of event name to boolean, e.g. `{"meeting.completed": true}`. An array is rejected with `422`. Omit to leave the stored selection unchanged; when no selection is stored, the default events fire.</ParamField>

Every delivery passes the same outbound URL guard as calendar feeds and the agent's fetches: the
address is checked where a connection to it lands, and the connection goes to the checked address.
See [Security & compliance](/security-compliance).

```bash GET /user/webhook
curl -H "X-API-Key: $API_KEY" "$API_BASE/user/webhook"
```

`PUT` and `GET` answer with the same shape:

```json Response
{ "webhook_url": "https://example.com/hooks/vexa",
  "webhook_secret_set": true,
  "webhook_secret": "********f3a9",
  "webhook_events": { "meeting.completed": true, "meeting.status_change": false } }
```

The secret is masked to its last four characters on read-back — enough to recognize which secret is
set, never enough to use it.

<Warning>
**Delivery works; the delivery *history* does not.** A production walk on 2026-07-19 (v0.12.15)
delivered `meeting.status_change`, `meeting.completed` and `bot.failed` to an external
`webhook.site` endpoint — the receiver's inbox and meeting-api's own delivery-outcome log matched
one-for-one at `code=200`. What is still broken is the user-facing **Delivery History**, which
reads a store those deliveries were never written to and so shows none of them
([#841](https://github.com/Vexa-ai/vexa/issues/841), open). Deliveries now succeed *silently* —
the exact inversion of [#815](https://github.com/Vexa-ai/vexa/issues/815), where they failed silently.
</Warning>

## Events

| Event | Fires when |
|---|---|
| `meeting.status_change` | every advance of the bot lifecycle state machine |
| `meeting.started` | the bot reaches `active` |
| `meeting.completed` | the meeting completes — carries the post-meeting envelope, including [service provenance](/api/meetings#completion-service-provenance) |
| `bot.failed` | the bot reaches terminal failure |

The typed events are additive: `meeting.status_change` still fires for the same transition.

## Signature

Each delivery carries `Content-Type: application/json` and, when a secret is set:

| Header | Value |
|---|---|
| `X-Webhook-Signature` | `sha256=<hmac_sha256(secret, "<timestamp>." + body)>` |
| `X-Webhook-Timestamp` | unix seconds, the value signed with the body |
| `Authorization` | `Bearer <secret>` — legacy back-compatibility |

Verify by recomputing the HMAC over `"<X-Webhook-Timestamp>." + raw_body` and comparing in constant
time. Reject timestamps outside your replay window.

## Delivery history

```bash GET /user/webhook/deliveries
curl -H "X-API-Key: $API_KEY" "$API_BASE/user/webhook/deliveries?limit=50"
```

```json Response
{ "deliveries": [
    { "event_type": "meeting.completed",
      "event_id": "evt_1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d",
      "target_host": "example.com",
      "outcome": "delivered",
      "status_code": 200,
      "attempt": 0,
      "created_at": "2026-08-18T17:54:03.871648Z",
      "meeting_id": 12345 } ] }
```

Newest first. `limit` defaults to 100 and accepts 1–500; the ledger keeps the most recent 100
attempts per account, so it is a recent window rather than a permanent audit log.

`outcome` is one of `delivered` · `queued` · `suppressed` · `blocked` · `failed`. `status_code` is
what your endpoint answered, when it answered. A row carries the **host only** — never the
configured URL, never the secret.

<Warning>
That is the contract. Today the store behind it is not the one real deliveries are written to
([#841](https://github.com/Vexa-ai/vexa/issues/841), open), so this endpoint can answer with an
empty `deliveries` array for an account whose webhooks are in fact arriving. **Do not read an empty
history as "nothing was delivered."**
</Warning>

## How it works

1. **Save.** `PUT /user/webhook` goes through the gateway to admin-api, which checks the URL as
   written (scheme, address, host name), refuses an internal one with `422`, and stores the URL,
   secret and event map on the user.
2. **Spawn.** When your key resolves, the gateway carries that config in the identity it forwards
   to meeting-api. `POST /bots` copies it into the meeting's record.
3. **Fire.** On a lifecycle transition meeting-api builds the `webhook.v1` envelope and drops
   events you did not select.
4. **Guard.** It resolves the host, checks every address, and posts through a transport that
   resolves again and dials a checked address, with the original Host header and TLS name. The
   delivery check is the save check, whenever the URL was saved.
5. **Sign and send.** It signs `"<timestamp>." + body` with your secret and posts (10 s timeout).
6. **Retry.** A `5xx`, `429` or transport error goes on a Redis retry queue and is tried again
   after 1 min, 5 min, 30 min and 2 h; an entry older than 24 h is dropped. Each outcome is logged
   with the target host only, never the URL or secret.

## Why it complies

| Rule | How this design meets it | Enforced by |
|---|---|---|
| P4: a cross-process contract is sealed | The envelope and headers are `webhook.v1`, sealed in `contracts.seal.json` | `gate:schema`, `gate:contract-version` |
| P23 and ADR-0044: no duplicated fact drifts | admin-api's save check and meeting-api's delivery guard are byte-identical copies of `outbound-url.v1`'s `ssrf.py` | `gate:fact-parity` (fact `outbound-url-guard`) |
| P18: fail loud | A blocked, suppressed or failed delivery is logged as a warning with its outcome | ungated: reviewed; `test_silent_non_delivery_outcomes_are_logged_as_warnings` |
| An upgrade does not silently stop a working webhook | URLs stored on 0.12 are delivered under the 0.12 ranges by default, through the same operator-allowance path every other fetch uses; nothing internal is admitted | `core/meetings/services/meeting-api/tests/test_webhook_stored_url_policy.py` |

**Security.** `/user/webhook` needs a `bot` or `tx` key and reads and writes only the key owner's
config. The secret is masked on read-back and never appears in the delivery record. Deny tests:
`core/identity/services/admin-api/tests/test_user_webhook_response.py`
(`test_an_internal_webhook_destination_is_refused_when_saved`,
`test_a_narrow_key_reads_back_the_webhook_and_no_stored_credential`) and
`core/meetings/services/meeting-api/tests/test_webhook_ssrf.py` (`test_blocked_urls`,
`test_dns_rebinding_to_private_blocked`, `test_every_form_of_an_internal_address_is_refused`).

## What is proven, and what is not

- **Live delivery — proven.** Owner-witnessed production walk, 2026-07-19: POSTs arrived at an
  external `webhook.site` inbox from production IPs, one per walk event, matched one-for-one by
  meeting-api's delivery-outcome log at `code=200`.
- **Delivery History — broken.** The user-facing history reads a store real deliveries were never
  written to, so it lists none of them ([#841](https://github.com/Vexa-ai/vexa/issues/841), open).
  Do not read an empty history as "nothing was delivered."
- **CI does not exercise the network leg.** The module and eval tests drive the real `WebhookSink`
  against a fake in-memory receiver, so a regression in the transport itself would not be caught
  by tests — only by another live walk.
- **No settings UI** — configuration is API-only (`PUT /user/webhook`).
- Exactly-once emission ([#519](https://github.com/Vexa-ai/vexa/issues/519)) and outage-durable
  retry ([#520](https://github.com/Vexa-ai/vexa/issues/520)) both closed as completed in July.
