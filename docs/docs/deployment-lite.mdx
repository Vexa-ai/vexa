title: "Vexa Lite (single container)"
description: "The whole control plane in one container — process runtime backend, no Docker socket, two datastore sidecars."
---

Vexa Lite packs every control-plane service into a single image (`vexaai/vexa-lite`) and runs
bots and agent workers as **in-container processes** (`RUNTIME_BACKEND=process`) — no Docker
socket, no per-bot containers. Two sidecars carry state: Postgres and the recordings storage
(versitygw, an S3 server that keeps each recording as a plain file in a volume). Lite is one of the
three supported deploy paths (lite · [compose](/deployment) · [Kubernetes](/deployment-kubernetes))
and ships from the same images and contracts.

## Quick start

```bash
git clone https://github.com/Vexa-ai/vexa.git && cd vexa
make lite
```

`make lite` (= `make -C deploy/lite all`) writes a minimal `.env` if you don't have one, pulls
`vexaai/vexa-lite:$IMAGE_TAG` (default `v012`; a locally built `vexa-lite:dev` wins when present),
starts the `vexa-lite-postgres` and `vexa-lite-storage` sidecars on the `vexa-lite-net` Docker
network, boots the app container, waits on the gateway health endpoint, and probes the three
front doors, giving each up to two minutes to answer (on first boot the terminal restarts once the
self-host key is minted):

| Front door | Port |
|---|---|
| **gateway** — the public REST API | `8056` |
| **terminal** — the workbench UI | `3001` |
| **agent-api** — the agent control plane. The port answers health checks; clients call it through the gateway as `/agent/*`, since agent-api accepts a user only from the gateway's signed identity | `8100` |

On first boot Lite mints its own credentials — a `self-host@vexa.ai` user and `bot,tx`-scoped API
keys — and hands them to the terminal, so `http://localhost:3001` opens signed in. Set
`VEXA_API_KEY` in `.env` to bring your own key and skip the minting.

That is **zero-login** (`VEXA_TERMINAL_ZERO_LOGIN=true`, Lite's default): every visitor who can
reach port 3001 acts as that self-host user. Set `VEXA_TERMINAL_ZERO_LOGIN=false` when the port is
reachable by anybody but you; the terminal then answers a visitor with no session as anonymous and
asks them to sign in. Compose and Kubernetes deployments have no zero-login.
While zero-login is on and the terminal listens beyond loopback, Lite prints a warning banner to the container log at every start; `make -C deploy/lite up` publishes 3001 on every interface, so either set `VEXA_TERMINAL_ZERO_LOGIN=false` or publish it as `-p 127.0.0.1:3001:3001`.

The terminal then asks for the **admin claim code** before anyone can become the instance's
administrator. admin-api writes it to the container log at boot, and it works once:

```bash
docker logs vexa-lite 2>&1 | grep -A4 'ADMIN CLAIM CODE'
```

Pass `-e VEXA_ADMIN_EMAILS=you@example.com` to name the admins instead; no code is issued then.

**Don't have a key yet?** Hosted: sign in at [vexa.ai/signin](https://vexa.ai/signin) with a Google
account and copy your key from [your account page](https://vexa.ai/account) — free credit, no card
required. Self-hosted: `make all` prints a key when the stack comes up.

Transcription needs a backend: point `TRANSCRIPTION_SERVICE_URL` / `TRANSCRIPTION_SERVICE_TOKEN`
at a [transcription unit](/deployment#transcription-the-separate-gpu-unit), or run the bundled
CPU sidecar:

```bash
# CPU Whisper (faster-whisper tiny.en, English-only) on :8083 — for trying it, not for real meetings
make -C deploy/lite up LOCAL_STT=1
make -C deploy/lite stt-smoke   # synthesizes speech in a container, asserts a transcript comes back
```

Without a transcription backend, bots join and capture but produce no text — a default
`POST /bots` answers `503` unless the spawn opts out
([capture-only](/how-to/send-a-bot#capture-only-no-stt)).

## What's in the container

One supervisord tree runs the services a compose deployment spreads across containers:

| Program | Role |
|---|---|
| **gateway** (`:8056`), **terminal** (`:3001`), **agent-api** (`:8100`) | the three published front doors |
| **meeting-api, admin-api, runtime** | loopback-only (`127.0.0.1`) — reach them with `docker exec` |
| **mcp** (`:8010`) | the MCP server, loopback-only; the gateway serves it at `/mcp` |
| **valkey** | in-container Redis-compatible store, loopback-only |

Bots and agent workers are **not** supervisord programs — the runtime spawns them as child
processes, one per meeting and per agent dispatch. No child runs as root. An agent worker runs as its
subject's own uid; a meeting bot runs as a uid of its own. Each child gets a fresh private home
directory, which is removed when it ends. If the runtime cannot isolate a child (for example, a
subject it cannot map to a uid), it refuses the spawn and starts nothing. Each bot brings up its own virtual display and
audio daemon as its own user, with a display cookie only it holds, so no bot can see or drive
another's meeting. There is no shared screen, and so no VNC view. Each bot's browser runs with
Chromium's sandbox: `make lite` starts the container under `core/runtime/src/runtime_kernel/seccomp-userns.json` (Docker's
default seccomp profile plus the user namespaces the sandbox needs, which only the bots keep).
Inspect a running deployment with:

```bash
docker logs -f vexa-lite                            # all service logs go to stdout
docker exec vexa-lite supervisorctl status          # the service tree
docker exec vexa-lite ps aux | grep dist/index.js   # live bot processes
```

What stays root's alone inside the container: Valkey's data (`/var/lib/redis`), the workload logs
(`/var/lib/vexa-runtime/logs`, one file per workload), the rendered service config and Valkey's config
(`/run/vexa`), and the mounted model credential. Valkey's password is in that root-only config file,
not on its command line. The browser install (`/ms-playwright`) is read-only to every child.

## Configuration

Lite reads the repo-root `.env` (via `docker run --env-file`) plus the flags the Makefile sets
explicitly. Every key in the [configuration reference](/configuration) applies; mind its warning
about inline `# comments` in `.env` values — it exists because of Lite's `--env-file` semantics.

The database password has no default either. `make lite` mints `DB_PASSWORD` into `.env` and sets it
on the bundled postgres sidecar on every run. **If you run the Lite image yourself, pass
`DB_PASSWORD`**: the entrypoint refuses to start on an unset value or one published in this
repository (`postgres` included).

The terminal's signing secret has no default. Leave `NEXTAUTH_SECRET` unset and the container
mints one on first boot and keeps it in `/var/lib/vexa/state` (the `vexa-lite-state` volume under
`make lite`); or set it in `.env` to a value of at least 32 bytes (`openssl rand -hex 32`). The
terminal refuses to start on a shorter value or one published in this repository.

If `~/.claude/.credentials.json` exists on the host, `make lite` mounts that one file read-only into
a root-only directory in the container, so agents run on your Claude subscription without copying
credentials into `.env`; nothing else from `~/.claude` enters the container. A file mount keeps the
file it started with: after the Claude CLI on the host refreshes its token, run `make lite` again.

To run agents on a Codex subscription, mount your `auth.json` into the container and set
`HOST_CODEX_CREDENTIALS` to its path inside the container. `make lite` does not do this for you. The
runtime copies the file into each worker's private home as `~/.codex/auth.json`, where the harness and
the Codex CLI read it.

## Persistence and upgrade

State lives in the sidecars' named volumes and survives app-container replacement:

| Data | Where |
|---|---|
| Users, meetings, transcripts (Postgres) | volume `vexa-lite-pgdata` |
| Recordings (the `vexa-lite-storage` sidecar, versitygw) | volume `vexa-lite-storagedata` — one plain file per object under `data/vexa/` |
| The terminal's signing secret (`NEXTAUTH_SECRET`, when `.env` sets none) | volume `vexa-lite-state` at `/var/lib/vexa/state` |
| Valkey state and `/workspaces` scratch | **in-container, ephemeral** — mount `/var/lib/redis` yourself if you need it kept |

The storage sidecar runs `versity/versitygw` (Apache-2.0), pinned by tag and digest in
`deploy/lite/Makefile`. meeting-api reaches it over S3 at `vexa-lite-storage:9000` with the
`MINIO_*` settings the Makefile passes. The names are unchanged; the credentials have no default:
`make up` mints `MINIO_ACCESS_KEY` / `MINIO_SECRET_KEY` into `.env` (or replaces the old published
`vexa-access-key` / `vexa-secret-key`) and restarts the sidecar with them over the same volume. Set
both on the `make` command line to use your own. Its port is not published. Back the volume up with a copy that keeps extended attributes (`rsync -aX`,
`cp -a`); see [Recordings → Backups](/how-to/recordings#backups).

Upgrading is re-running with a newer image: set `IMAGE_TAG` in `.env` (pin a specific release so
deploys are reproducible), then `make lite` again — it replaces the app container and leaves the
sidecars and their volumes untouched. Schema converges in-process on service startup; there is no
separate migration step.

**Coming from a Lite that ran MinIO**: old recordings stay in `vexa-lite-miniodata` and do not
play back until copied. `make lite` starts on the new storage without inspecting the old volume.
Run `make -C deploy/lite migrate-storage` to copy and verify objects by SHA-256; it never deletes
the old volume. [Where your recordings live now](/upgrade-from-minio) covers the copy and rollback.

```bash
make -C deploy/lite down                                  # containers go, volumes stay
docker volume rm vexa-lite-pgdata vexa-lite-storagedata vexa-lite-state   # full wipe
```

## Is this install actually working? — `make probe SURFACE=lite`

```bash
make probe SURFACE=lite
```

The probe mints a key and drives the whole journey — spawn → boot → join → transcribe →
live-view → stop. Lite runs the **real** bot in-process, so a dead meeting URL ends in a truthful
named failure, never a fake green. The container also carries a Docker `HEALTHCHECK` on the
gateway's `/health` (30s interval, 120s start period).

`make -C deploy/lite test` checks a running Lite from inside. It waits for the three front doors,
then starts an agent worker and a meeting bot through the runtime and checks each one. No spawned
process runs as root or can read another process's environment. A dispatch whose subject cannot be
mapped is refused. The root-only paths above are unreadable to every child, and no service secret
appears on a command line.

## How it works

1. **Boot.** The entrypoint mints every secret you did not set (the admin token, the internal secret,
   the runtime caller credential, Valkey's password). It writes Valkey's config and the rendered
   supervisor config into the root-only `/run/vexa`, then hands off to supervisord.
2. **Services.** supervisord starts Valkey, admin-api, the runtime, meeting-api, agent-api, the gateway,
   the MCP server and the terminal. Only the runtime, agent-api and meeting-api hold the runtime caller
   credential.
3. **The runtime starts clean.** Its launcher drops every inherited variable the runtime's `config.v1`
   does not declare, so no service secret reaches the runtime or anything it spawns.
4. **Spawn.** meeting-api (a bot) or agent-api (an agent turn) calls the runtime with the caller
   credential. The runtime starts the child as a non-root uid with a fresh private home, or refuses.
5. **Each bot is alone.** It starts its own virtual display and audio daemon as its own uid.
6. **Tools.** At boot the MCP server asks each domain for its tool manifest. agent-api serves its
   manifest at `/.well-known/mcp-tools.json` from the file the image carries.

## Why it complies

- **P14 config by env, validated.** `gate:config-contract` fails when the entrypoint exports a key no
  service's `config.v1` declares.
- **P20 and isolation.** The deny tests: in `core/runtime/tests/`,
  `test_isolation_root.py` (`test_a_workspace_dispatch_runs_as_its_subject_never_root`,
  `test_concurrent_children_cannot_read_each_other_or_the_runtime`,
  `test_a_child_that_cannot_be_isolated_is_refused_and_never_started`) and `test_isolation.py`
  (`test_a_root_runtime_refuses_a_subject_it_cannot_map`); in `deploy/lite/tests/`,
  `test_runtime_environment.py` (`test_no_instance_secret_survives_into_the_runtime`) and
  `test_child_isolation.py` (`test_valkeys_password_is_in_a_root_only_file_not_on_its_command_line`,
  `test_the_browser_install_is_not_writable_by_children`). The three `test_isolation_root.py` tests
  are skipped unless pytest runs as root on Linux, and no CI job runs them as root, so in CI they
  are skipped; run them as root on a Linux host to exercise them. The other tests here run under
  `gate:python`.
- **Nothing missing from the image.** `deploy/lite/tests/test_image_by_path_reads.py`
  (`test_every_file_a_service_reads_beside_its_code_is_in_the_image`) finds every file a service reads
  beside its code and fails when the image does not carry it.
- **The Makefile and the store.** `gate:lite-makefile` checks the Makefile's recipes;
  `gate:runtime-parity` checks that the Valkey version Lite pins supports every command the code calls.
- **P17.** `gate:vendor-payload` keeps the optional native meeting SDK out of the Lite build context.

## Limits vs compose and Kubernetes

- **Ephemeral Valkey.** In-container with no volume by default.
- **Sidecar ports are unpublished.** Postgres and the storage sidecar's S3 port are reachable only
  on the Docker network, not from the host.
- **No calls.** Lite runs no LiveKit server, so a chat has no Call button
  ([Calls](/minutes/calls)).
- **No authenticated bots.** Lite does not package the provisioning flow or a userdata store
  ([Authenticated bots](/authenticated-bots#availability-by-deployment-surface)).

Outgrown it? Switch to [compose](/deployment) — same images, same contracts. Per-feature honest
status: [Roadmap → Status](/roadmap/status).
