Every page in Minutes is a Markdown file in a [workspace](/concepts#workspace), a git repository the
agent reads and writes. The right half of the screen shows one page at a time. This page explains how to
find pages, edit them, ask the agent to grow them, and what happens to images and diagrams.

## What you can do

### Find a page

1. Click the **folder icon** at the left of the page header, or press <kbd>/</kbd> after it is open,
   to show the **navigator**. It is hidden by default, and your browser remembers whether you left it
   open.
2. The navigator lists **Personal** — your own workspace — first, then the company workspace (`_global`, shown under the
   company name when it is known), then every shared workspace you belong to, by name. Workspaces you
   cannot read are not listed at all. Click a workspace's **name** to open its README (the workspace's
   front page) and expand it; the arrow only expands or collapses it. On the keyboard, <kbd>Enter</kbd>
   opens the README and <kbd>→</kbd> / <kbd>←</kbd> expand and collapse.
3. Type in **Filter files** to match file *names* across every listed workspace. The list shows the
   first 50 matches. Content search is not available yet; a filter that starts with `>` says so and
   matches names.
4. **Click** a file to read it in the view slot. **Middle-click** it, or press **⧉** (*Open in a tab*),
   to keep it as a tab.

Press <kbd>Esc</kbd> in the filter to clear it, and again to close the navigator.

### Find a call

1. At the top of the navigator, switch from **Files** to **Calls**. Use <kbd>←</kbd> / <kbd>→</kbd> on
   the switch from the keyboard. Your browser remembers the view you left it on.
2. **Calls** lists the meetings you own and the ones shared with you, newest first. Calls happening now
   are at the top under **Live**. The rest are grouped by day. When you have more than 40 calls they are
   grouped by month. The first 30 calls are shown, and **Show more** adds the next 30. A call with no
   title shows its platform and meeting code. Planned meetings that have not run yet are not listed,
   and neither are calls you deleted. A call whose bot never got in is listed at the time you sent the
   bot, with the time in italics.
3. **Click** a call to open its transcript in the panel. A live call streams as it is spoken. What
   you can do there is on [Meetings](/minutes/meetings).
   **Middle-click** the call, or press **⧉**, to keep it in a tab. **⧉** and the row's other buttons
   appear in place of the time when you point at the row or move to it with the keyboard.
4. Type in **Filter calls** to match call titles. Start with `>` to search what was said: this searches
   the transcripts of calls **you own**. Calls shared with you are matched by title only.
5. If a call belongs to a workspace you can read, its row shows a folder button that opens that
   workspace in **Files**. In **Files**, that workspace's row shows how many calls belong to it.
   Click the count to list those calls.

### Rename a call

You can rename a call you own. The name is the meeting's own title, so it changes everywhere the call
appears: the **Calls** list, the chat list, the meeting's header and its tab.

- In **Calls**, point at the call, press **⋯** and choose **Rename**. Or move to the call with the
  keyboard and press <kbd>F2</kbd>.
- On the meeting's page, click its name in the header (see [Meetings](/minutes/meetings)).

Type the new name and press <kbd>Enter</kbd>. <kbd>Escape</kbd> cancels. In the list, moving away from
the field also saves. Clear the name and save to go back to the call's default name, its platform
and meeting code.

A call shared with you shows its name without a rename control. Only its owner can rename it. If a
save is refused, the field stays open and says so.

A chat's name is separate. Renaming a call does not rename a chat that you named yourself.

### Tabs and history

- The tab shown in *italics* is the **preview**: the next page you open replaces it. Pin a page
  (*Keep this as a tab*) to keep it.
- **‹** and **›** step back and forward through the pages you read (<kbd>⌘/Ctrl</kbd> + <kbd>[</kbd> and
  <kbd>]</kbd>).
- The breadcrumb under the header lists any folder on the path when you click it. A numeric folder reads
  *personal* and `.system` reads *private*.

### Edit a page

1. Press **Edit**. The page opens in an editor that keeps the file as plain Markdown with live
   formatting, in the same colours as the read view (light or dark).
2. Press **Save**. The page is written and committed to the workspace's git history with the message
   `edit <path> (terminal page editor)`, then re-read.
3. **Cancel** drops the draft.

There is no keyboard shortcut for Save. An empty path shows *No page here yet* with a **Create this
page** button.

### Extend or create a page with the agent

Under a page you will find one of these cards:

| Card | Shown on | What the agent does |
|---|---|---|
| **Extend this page** | any page | "Research it, write what is found around it, link both ways." |
| **Extend this meeting page** | a meeting's notes file, opened on its own | "Take in what has been said since last time, page what it names, link both ways." |
| **Create this page** | an empty path | "Research it, write it, link what is found around it both ways." |

Press the card, optionally type one line in **what to do with it (optional)**, and press
<kbd>Enter</kbd>. <kbd>Esc</kbd> goes ahead without a line; there is no cancel. The act runs as a
[background job](/minutes/chats#background-jobs): the card turns into a status line, the chat stays
free for other questions, and the page comes into view when the job commits.

What Extend researches, and where it looks, is described in
[Onboarding research and Extend](/how-to/onboarding-research#extend).

**Extend this meeting page** is the same act as **Update notes** in the
[meeting view](/minutes/meetings#read-and-update-the-notes). It reads only the transcript that arrived
since the last update. The page keeps a `transcript_cursor` in its frontmatter; a page with no cursor,
or an older page whose cursor is not a whole number, is read from the top.

To ask about *part* of a page or transcript, select the text. An **Ask about this** button appears; it
drafts a quote into the chat box, and you decide whether to send it. A selection never starts a job.

### Two people editing one page

When two people, or their agents, change the same page at about the same time, the second save is
merged with the first: changes in different places are both kept, and new lines added at the same
spot are both kept. If both changed the same lines, the second save is refused with the page as it
is now and nothing is written; the agent reads it again and applies its change.

### Images

- **Drop or paste** files into the editor. They are stored in the workspace under `assets/`, with a
  relative link inserted (`![name](assets/…)`). Pasted screenshots are named `pasted-YYYYMMDD-HHMMSS`.
  Files that are not images are stored and linked as plain links.
- An image that lives on another site shows *External image — it lives on* the host's name, with a
  **Fetch into the workspace** button. Fetching copies it into `assets/` and records where it came from
  in `assets/SOURCES.md`.
- If a fetch fails, **Find it** asks the chat to look for the image and **Remove the link** commits the
  page without it.

### Diagrams and properties

- A ` ```mermaid ` code block renders as a diagram, both in the read view and under the fence while you
  edit.
- A page whose frontmatter has a `type:` (an [OKF](/how-to/workspace-files#the-knowledge-graph-is-an-okf-bundle)
  entity) shows the frontmatter as **Entity properties**: a key/value list where web addresses are
  links.
- A link to a meeting (`/?meeting=<id>`) or to a meeting's notes page shows as a meeting chip: the
  meeting's title and date, opening the meeting. A meeting you cannot open shows as plain text. See
  [Links in replies](/minutes/chats#links-in-replies).

### Links, tasks and richer pages

Pages stay plain markdown in git; the panel and the chat read more of it:

- **Links go anywhere you can read.** `[[Name]]` opens the page here; `[[biz:graph/sg/Growth]]` (or
  `vexa://ws/biz/graph/sg/Growth.md`, or a relative link that climbs out of the workspace) opens a
  page in another workspace. Matching ignores case and dashes, and `.md` is optional. A `[[name]]`
  with no page here is looked for in every workspace you can read; several matches open a small
  picker. A link into a workspace you cannot read shows as **restricted**, with the link's own words
  and never the page's title. A person's or company's name written in plain text links at its first
  mention when it has a page here.
- **Mentioned in** at the foot of a page lists the pages that link to it, from workspaces you can
  read.
- **Tasks.** `- [ ]` items are checkboxes: ticking one writes `- [x]` to the file, committed as you.
  `TBD:` lines under a *Follow-ups* (or *Next steps*, *To-do*) heading are open tasks too. **Ask
  agent** beside a task sends it, with the page, to the chat. In a chat reply tasks are shown only.
- **Properties.** Front matter shows as the page's header: the company as a link, the email with
  **Copy**, dates relative.
- **Callouts** (`> [!note] Title`, `> [!warning] Title`), **heading anchors**, an **On this page**
  outline on long pages, and **dates** that read relatively ("3 days ago", exact on hover). A
  ` ```vexa ` block is drawn by the shared block renderer.

### Delete a page

1. Press the **trash icon** in the page header (beside Copy and Edit), or press **⋯** on the file's row
   in the navigator (or right-click the row) and choose **Delete…**.
2. The dialog reads *Delete \<page\>? It's removed from \<workspace\>; you can restore it from History.*
   **Delete page** has the focus, so <kbd>Enter</kbd> deletes and <kbd>Esc</kbd> cancels.
3. The page is removed as a commit. Every tab on it closes; if it was in front, the next tab comes
   forward. Links to it from other pages show as dashed *no page yet* chips.
4. A note at the bottom of the screen says *Deleted \<page\>.* with **Undo** for 10 seconds. Undo puts
   the page back exactly as it was, as a new commit, and opens it.

After that, open the workspace's README, press **History**, and press **Restore** on the row that
removed the page. Restore never overwrites: if a page has been written at that path since, it refuses.

You are offered Delete where you may edit: your own desk, a shared workspace where you are a
contributor or owner, and the company workspace (`_global`) only as its administrator. A reader sees
no Delete and no Restore. A meeting's own page and a workspace's README have no Delete button.

### Move pages, or delete them by asking

Ask in the chat ("move this page to the project workspace", "delete the draft"). The agent uses the
same delete as the button. The navigator has no rename or drag. A move inside one workspace leaves a
pointer page at the old path (`moved_to:` in its frontmatter), so old links still lead somewhere. A move
to another workspace writes the target and removes the source, without a pointer. A removed page stays
in the git history.

## Limits and errors

| You see | Why | What to do |
|---|---|---|
| *Could not save: …* under the editor | the write was refused or failed; your draft is kept | read the reason; see the refusals below |
| *not authorized for this workspace* | you are a viewer, or not a member | ask an owner for the contributor role |
| *only the admin account may edit _global* | the company workspace is written by the admin account | sign in as the [admin account](/minutes/workspaces#the-admin-account) |
| *kg/templates/ holds entity shapes, not records* | a desk's templates are not editable as pages | write the record elsewhere; the company's templates are `_global/kg/templates/`, edited by the [admin account](/minutes/admin-account#templates) |
| *Could not delete: …* in the dialog | the delete was refused (the same rules as a save); nothing was removed | read the reason |
| *Could not restore: a page is already at that path …* | a page was written at that path after the delete; a restore never overwrites | move or delete the newer page first |
| *that path is not inside this workspace* | the path is absolute, contains `..`, or names `.git`, `.vexa` or `.claude` | use a path inside the workspace |
| *… exceeds 25MB* | the upload ceiling is 25 MB per file | shrink or link the file |
| *External image* fetch refused | only `http`/`https` addresses on the public internet can be fetched; internal names and private, loopback and link-local addresses are refused | host the image publicly or upload it |
| *This image does not exist at that address (the site answered 404).* and similar | the remote site answered badly (shown as the site's status) or did not answer | use **Find it** or **Remove the link** |
| *diagram not drawn — …* | the Mermaid source does not parse | fix the diagram source |
| *… — queued behind the one running.* | another act on the same page is running | it starts when the first one ends |

Saves have **no conflict check**: a save replaces the whole file, so the last save wins. Fetches time
out after 20 seconds and follow at most 3 redirects. When the agent writes a page that links an external
image that is dead or not an image, the link is cut out (the text stays) and a friction report is filed.

## How it works

### Flow

1. **Read.** The page view calls `GET /api/workspace/file?path=…&slug=…` on the terminal. The terminal
   server forwards it to the gateway as `/agent/workspace/file` with your API key. The gateway resolves
   the key to you and forwards to agent-api `/api/workspace/file` with your identity signed. agent-api
   checks your access to the workspace and returns the file.
2. **Save.** `PUT /api/workspace/file` with `{path, content, slug}` goes the same way. agent-api checks
   that you may write there, drops external images that do not resolve, writes the file without
   following symbolic links, and commits.
3. **Extend / Create.** The card sends a typed *intent* (`extend`, `extend_transcript` or `create`,
   plus the path and your optional line) through the chat. agent-api runs it as a background job on the
   page; the agent's commit lands, and the terminal brings the page into view.
4. **Images.** A drop is `PUT /api/workspace/asset` (multipart; the terminal passes the bytes through
   undecoded). A fetch is `POST /api/workspace/asset {url}`: agent-api fetches it through its URL guard,
   stores it under `assets/`, records the source, and makes one commit.
5. **Delete.** The page header and the navigator call `POST /api/workspace/remove` with `{path, slug}`
   on the terminal, which forwards it to `/agent/workspace/remove` — the same agent-api verb the agent's
   `workspace_delete` tool calls. agent-api authorizes it as a save (plus: never `_system`), removes the
   file without following links, refreshes `kg/INDEX.md` for an entity page, and commits
   `<workspace>: <path> — removed`. The answer carries the commit. The terminal then closes the page's
   tabs, drops its cached link lookups, and re-reads the navigator.
6. **Undo / Restore.** `POST /api/workspace/restore` with `{path, slug, commit}` (Undo passes the
   removal's commit; History's Restore passes the row's). agent-api checks the same rights, refuses
   with `409` if a file is at the path, checks that the commit removed that path, writes the bytes from
   the commit's parent, and commits `<workspace>: <path> — restored`.
7. **Move.** The agent calls `workspace_move`, which reaches `POST /agent/workspace/move`. Both ends
   of a move are authorized before anything is written.

### Pages the agent writes for names

At the end of a turn, the agent checks the names the turn mentioned against the pages your workspaces
already hold, and writes a page for each name that has none (`entity_upsert`). Before a name is
offered:

- **Words that open a spoken sentence are removed.** *So*, *And*, *But*, *Well*, *Okay* and similar
  words are dropped from the front of a name, so "So Vexam" is read as "Vexam". What is left must still
  be two words. Highlighted transcript terms use the same list.
- **A near spelling of an existing page is that page.** A name one letter away from a page's title or
  alias (two letters for long names) is matched to that page, not offered as a new one. "Vexam" is
  Vexa.
- **A name heard once in a transcript is a question, not a page.** When the only source is one line
  of a meeting transcript, the agent adds "Who or what is …?" to the meeting's open questions instead
  of writing a page. A name with a second source, such as your message, a file or an email, gets its
  page.

### Who writes what

| Data | Single writer | Where |
|---|---|---|
| Pages, `assets/`, `assets/SOURCES.md`, git history | agent-api (the `workspaces` library inside the agent domain) | the workspace's git repository |
| Navigator open/closed | your browser | `localStorage` key `vexa.minutes.navigator` |
| Navigator view (Files or Calls) | your browser | `localStorage` key `vexa.minutes.navigator.view` |
| Calls, transcripts, a call's workspace | meeting-api | the meetings database; the terminal only reads them |
| A call's name | meeting-api (annotate route) | the meeting's `data.title`; the terminal writes it only through that route |
| Extend job state | agent-api's worker jobs | in the agent domain; shown on the card |

The terminal stores no page content. It reads and forwards.

### Routes

| Browser calls (terminal) | Gateway | agent-api |
|---|---|---|
| `GET /api/workspace/tree`, `/file`, `/active`, `/shared` | `/agent/workspace/…` | `/api/workspace/…` |
| `PUT /api/workspace/file` | `/agent/workspace/file` | `/api/workspace/file` |
| `PUT`, `POST`, `GET /api/workspace/asset` | `/agent/workspace/asset` | `/api/workspace/asset` |
| `POST /api/workspace/remove` (Delete), agent tool `workspace_delete` | `/agent/workspace/remove` | `/api/workspace/remove` |
| `POST /api/workspace/restore` (Undo, Restore) | `/agent/workspace/restore` | `/api/workspace/restore` |
| agent tool `workspace_move` | `/agent/workspace/move` | `/api/workspace/move` |
| Calls list: `GET /api/meetings` | `/meetings` | meeting-api `GET /meetings` |
| Call transcript: `GET /api/transcripts/by-id/{id}` | `/transcripts/by-id/{id}` | meeting-api, same route |
| `>` in Filter calls: `GET /api/transcripts/search?q=` | `/transcripts/search` | meeting-api, same route |
| Rename a call: `POST /api/meetings/{id}/annotate` `{"title": …}` | `/meetings/{meeting_id}/annotate` | meeting-api, same route |

The gateway's mapping of `/agent/*` onto agent-api's `/api/*` is declared in `core/agent/routes.v1.json`;
the tools are declared in `core/agent/mcp.tools.v1.json`.

### Calls

The **Calls** view reads the same meeting list as the chats rail, `GET /api/meetings`. It makes no
read of its own, so a meeting appears in the panel only if that list contains it. Clicking a call opens
the panel's meeting view for that meeting. That view loads the transcript by meeting id and streams a
live call. The panel has no transcript viewer of its own.

The `>` search calls `GET /api/transcripts/search`. Results are limited to calls you own, so the list
can contain calls the search cannot reach. The terminal then drops any result whose meeting is not in
your list. A search can make the list shorter but never adds a call to it.

A deleted call is not listed. Deleting a finished meeting erases its transcript and recordings and
keeps the row as history, marked `data.artifact_deletion`. The list still returns that row, so the
terminal drops it.

A call's time is when it started, else when it was planned, else when the bot was requested. This is
the order meeting-api uses for the list.

**Renaming.** A rename posts `{"title": …}` to `POST /api/meetings/{id}/annotate`, addressed by the
meeting's row id. This is the route the MCP `annotate_meeting` tool and the REST API use. meeting-api
stores the title in the meeting's `data.title`. An empty title removes it, and the call goes back to
its default name. The terminal keeps no copy of the name. When the route answers, the terminal
updates its in-memory meetings list and reads the list again, so every view shows the stored title.
A tab for a call takes its name from that list.

A call's workspace is the meeting's own `workspace_id`. The folder button and the count on a
workspace row are both read from it, so nothing is copied onto the workspace. A workspace you cannot
read is not in the navigator, so its calls show no folder button.

### Two writers on one page

`PUT /api/workspace/file` (the agent's `workspace_write`) runs read, merge, write and commit under one
lock per workspace (`core/agent/control_plane/page_merge.py`). A write that does not start from the
page's current version is matched against the page's versions committed in the last 15 minutes (at
most 12): the closest one the new text still mostly contains is taken as the version the writer read,
and the two changes are merged three ways in memory. A clean merge is written and the answer says
`merged`; a change to the same lines is refused with `409` and the current page; a write from the
current version, a full rewrite, or a return to an earlier version is taken as written. A page edited
outside the page routes since its last commit is taken as written. Every writer's commit is
authored `vexa-terminal`.

### Configuration

`GATEWAY_URL` on the terminal server (default `http://127.0.0.1:18056`). A terminal built in
[meetings mode](/minutes/overview#configuration) refuses page writes with `404`; reads still work.

### References to anything: `/r/<kind>/<id>` and `[[kind:id]]`

Every workspace, chat, page, entity, meeting, flow and sensor has one reference: the link
`https://<your Vexa>/r/<kind>/<id>`, which you can paste anywhere (a chat, an email, a calendar event,
another app), and the chip `[[kind:id|label]]` the agent writes in a reply. A join link (`/join/<token>`)
is a reference that also lets the holder in.

Opening a reference asks the server what it points at **for you, now**. If you can open it, the chip
shows its name and opens it. If you cannot, it says **No access** and offers **Request access**, which
tells the owner who asked. If it no longer exists, it says **Not found**. Pasting a reference link into
the composer turns it into a chip. A `[[Title]]` chip is found by the server's own spelling rule, so a
name with accents (`[[mühlemann+popp AG]]`) opens its page. The agent uses `ref_resolve` before it
quotes or opens anything a reference names.

How a reference is answered: the grammar lives once on the server (`core/workspaces/shared/links.py`)
with a twin in the terminal (`ui-kit/universalRefs.ts`). `GET /api/refs/resolve?ref=` (agent tool
`ref_resolve`) is the one resolver (`core/agent/control_plane/universal_refs.py`); it asks each
kind's own access decision for the person asking and answers `readable`, `not-yours`, `unavailable`,
`gone` or `grant`. `POST /api/refs/request-access` is a person verb: agent-api writes the owner's
`access_requested` notice (a kind in the sealed `ws.v1`) and answers only `{requested: true}`. Flows
and sensors answer `unavailable` until flows exposes a per-viewer read. Nothing is configured.

### Security

**Who can do what.** You can read your own personal workspace, the company workspace, a colleague's personal workspace (read-only),
your own private tier, and every shared workspace you belong to (viewers included). You can write your
personal workspace, your private tier, a shared workspace where you are a contributor or above, and the company
workspace only as the admin account (which writes nothing else). Nobody writes a workspace's `kg/templates/`; the admin account writes the company's, in `_global/kg/templates/`, validated on save, and new pages are created from them. An agent acting for you is further held
to the workspace scope of the chat that dispatched it. You can rename only calls you own: the terminal
sends the rename with your sign-in, the gateway names you to meeting-api, and meeting-api writes the
title only when the meeting's owner is you. A call shared with you is read-only here.

**Protections.**

- Identity comes from your sign-in cookie on the terminal server and is signed by the gateway; the
  browser never names a user.
- Paths are refused if they are absolute, contain `..`, name a repository or identity directory, or
  reach outside the workspace through a symbolic link.
- Remote images are fetched only over `http`/`https`, never from internal names or private, loopback or
  link-local addresses; every redirect is checked again, and the body is capped at 25 MB.
- Stored assets are served with `nosniff` and a `default-src 'none'; sandbox` content security policy.
- Diagrams render with Mermaid's strict security level from the bundled package. Frontmatter
  properties never run links or markup.

## Live pages (`home2`)

With the `home2` feature on, a page in the right panel can be live. It stays plain markdown, so
people and the agent edit it as before; the panel draws these extras:

| Write | You see |
|---|---|
| `[[room:<id>]]`, `[[chat:<id>]]`, `[[call:<id>]]`, `[[file:<path>]]`, `[[person:<id>]]`, `[[card:<id>]]`, `[[routine:<id>]]`, `[[workspace:<slug>]]` | a live chip (unread count, stage, last run…) that opens the thing |
| `{{status}}`, `{{needs-you}}`, `{{working-here}}`, `{{members}}`, `{{upcoming}}` | the workspace's own state |
| `:::columns` … `---` … `:::`, `:::callout` … `:::`, `:::stats source=<file.json>` … `:::` | columns, a callout, figure tiles |
| `[[action:<verb>:<target> \| label]]` | a button: `run-routine`, `start-call`, `join-call`, `new-chat`, `accept-proposal`, `prepare`, `move-card`, `schedule-call` |
| a ```` ```view ```` block: `source: pages \| crm.card \| meetings \| rooms`, `as: table \| board`, `group:`, `columns:`, `folder:`, `filter:` | a live table or board |

Any plain table can be searched, filtered by a column and sorted.

### How it works

The panel asks agent-api once per page what each reference is **for you**. A view's rows are things
you can already open (pages from the workspace, cards on your desk, your meetings, the workspace's
rooms). Editing a view writes through the owner: a page's field is saved into its front matter as a
page save, and a card's stage goes through the CRM's own update. Actions run as you, through the same
routes the rest of the app uses; anything the agent does (running a routine, preparing a meeting,
drafting a schedule) is said in your own chat, and scheduling is only ever a draft you send.

### Why it complies

- **No code in pages.** Only the verbs above are buttons; any other `[[action:…]]` is just its words.
  Raw HTML is cleaned of scripts, frames, styles, handlers and `javascript:` links before it is drawn.
- **Never named if you cannot see it.** A reference you cannot open shows nothing (a room shows only
  "a private room"), never its name and never the label the writer typed.
- **Confirmed when it reaches others.** Running a routine, starting a call, accepting a proposal,
  moving a card and scheduling a call ask first.
