A workspace is a shared folder of pages with a roster. Your **desk** is yours; a **shared workspace**
has members; the **company** workspace (`_global`) is read by everyone and written by the
administrator. This page covers the front page of a workspace, how people join one, links into it,
attaching an existing repository, and the **Connections** page where you connect your own accounts.

## What you can do

### Read a workspace's front page

Open a workspace's `README.md` (or a `/w/<workspace>` link) and its header shows:

- **What it is:** *Your desk*, *Shared workspace* or *Company layer*, with its title.
- **Who is in it:** for a shared workspace, up to two names with *you* first ("you, … and 2 more");
  for your desk, whether agents read it for your meetings; for the company workspace, who reads and
  who writes it. A reader who may not see the roster sees *you and the other members*.
- **What is in it:** the page count, and what the workspace is bound to (a meeting series, or where it
  came from).
- **What changed last:** *… changed the … page …*, with a link when one page changed, or *Nothing
  written here yet*.

The buttons depend on your role:

| You are | Buttons |
|---|---|
| a member who is not an owner | **History** only |
| owner of a shared workspace | **Add a member**, **Connect a repo** (or **Sync**), **History** |
| owner of your desk | **Connect a repo** (or **Sync**), **History** |
| the administrator, on the company workspace | **Set up policies**, **Add an editor**, **History** |

Every button except History starts a conversation in the chat; none opens a form.

**History** opens *People*, *Repo* and *History* (and *Meetings* for a shared workspace):

- **People** lists members and roles. Owners can **Change role**, **Remove** and **Add a member…**.
  Members who are not contributors or owners see their own role only.
- **Repo** shows the attached remote, branch, and how far ahead or behind it is. Owners get
  **Sync now**, **Pull**, **Push** and **Detach**; Pull, Push and Detach ask you to confirm. Detaching
  stops syncing and leaves the files as they are.
- **History** lists commits ten at a time, for the workspace or *This page only*.

### Add a member

1. Press **Add a member** (or ask in the chat).
2. The agent asks for their email address and a role, and confirms in one sentence:
   - **owner** — writes the workspace and can add or remove members;
   - **contributor** — writes the workspace;
   - **reader** — reads it and does not write it.
3. The agent creates an invite link for that address. If the person has no account here, the link is
   emailed to them; otherwise the chat gives you the link to pass on.

Changing a role and removing someone work the same way, from **People** or in the chat. A workspace
always keeps at least one owner.

### Join from an invite

1. Open the link (`/join?i=…`). The page says who invited you, to which workspace, and as what.
2. Sign in with Google, Microsoft or an emailed sign-in link. If the invite names one address, that
   address is filled in and cannot be changed.
3. You are added and land on the workspace's front page. If you were already signed in, this happens
   at once.

An invite link works for **one person, for seven days**, and only for the address it names. Invites made
by the agent during a chat turn stay valid after the turn ends.

### Link to a page

Every workspace has a permanent id. A link `/w/<id>/<path>` (or `/w/<name>/<path>`) opens that page in
Minutes; with no path it opens the front page. Links made with the id keep working after the workspace
is renamed. Reloading the page reopens the same page. Only the workspace's owner, or an administrator,
can rename it.

### Attach an existing repository

Choose **Attach existing repo…** in the chat bar's **+** menu, **Attach a repo…** on the front page, or
**Attach repository as a workspace** under Connections → Git repositories.

1. Enter the **Repository** address (for example `git@github.com:<org>/<repo>.git`) and the **Branch**
   (`main` by default). The repository always becomes a **new workspace**; your desk and other
   workspaces are unchanged.
2. Press **Attach**. Large repositories can take several minutes; the dialog shows progress.
3. When it is done (*Cloned … into …*), press **Open workspace**.

Access uses your saved GitHub token, or a **deploy key**: under Connections, press **Use this deploy
key**, then **Add it on GitHub →** and add the public key to the repository *with write access*. Vexa
generates the key; you never paste a private key, and the private half never leaves the server.

### Repositories on GitLab or another self-hosted server

A repository on your company's own git server attaches the same way. Two things differ from GitHub.

**The address can be nested.** GitLab keeps projects in groups and subgroups, so paste the full address:
`https://git.example.com/platform/tools/notes.git` or `git@git.example.com:platform/tools/notes.git`.
Any depth up to 22 segments (a group, 20 subgroups and the project) is accepted. On `github.com` the
address is still exactly `owner/repo`.

**The credential.** Use one of these:

- **A deploy key** (recommended). Paste the `git@…` address, press **Use this deploy key**, and add the
  public key in the project under *Settings → Repository → Deploy keys* with **Grant write
  permissions**. When your operator registered the host as GitLab, Vexa links you straight to that page.
- **An access token typed for this one call.** A GitLab personal, project or group access token with
  `read_repository` (and `write_repository` to push). Type it as `oauth2:<token>`, or as
  `<username>:<token>` for a server that wants a named account. A bare token works too when your
  operator registered the host (see below). Your **saved** token is a GitHub credential and is only
  ever sent to `github.com`, so it is never used here.

**Publishing a new repository to GitLab.** `POST /api/workspace/publish` with `host` set to a GitLab
host your operator registered creates the project there — in your own namespace, or in the group named
by `org`, nested groups included (`"org": "platform/tools"`) — and pushes the workspace. The token needs
the `api` scope. Any other host is refused with a message naming it; create the repository there yourself
and publish with its address as `remote_url`. The publish dialog in Minutes creates on GitHub.

#### For operators: register your git hosts

Tell agent-api which provider each self-hosted host runs, so a bare token is sent in the form that host
expects. Unlisted hosts keep GitHub's form, exactly as before.

| Provider | A token is sent as | Use for |
|---|---|---|
| `github` | `https://<token>@host/…` | GitHub Enterprise Server |
| `gitlab` | `https://oauth2:<token>@host/…` | GitLab (self-managed or dedicated); also enables publish-create on that host |
| `basic:<username>` | `https://<username>:<token>@host/…` | Gitea, Bitbucket Server and other servers that want a named account |

Helm (`values.yaml`):

```yaml
agentApi:
  gitProviders: "git.example.com=gitlab,code.example.org=basic:svc-vexa"
```

With `helm --set`, escape the commas (`--set-string agentApi.gitProviders='git.example.com=gitlab\,code.example.org=basic:svc-vexa'`).
Docker Compose reads the same setting as `VEXA_GIT_PROVIDERS` from `.env`. A malformed entry
stops agent-api at boot with a message naming it. The host must be a dotted name agent-api can reach;
when the server's TLS certificate comes from a company CA, add that CA to the agent-api image's trust
store, because tokens are only ever sent over `https`.

### Connect your accounts

Open **Connections** from your account menu (bottom of the rail). An agent can also ask you to connect
something, which opens the same page.

| Card | Lets your agents |
|---|---|
| **Git repositories** | use a saved GitHub token, or attach a repository |
| **Gmail** | read email and save drafts (Minutes does not send mail) |
| **Google Calendar** | read calendar events |
| **Custom secret** | use a secret, optionally against one HTTPS address you name |

- You can connect several accounts of one kind: give each a **Connection label** ("Personal",
  "Work") and press **Add another … account**.
- Google consent opens in a pop-up. Allow pop-ups for Minutes.
- A custom secret names the exact HTTPS address, the header, the value format and the one method it may
  be used with. You confirm the destination host by typing it; an unknown host is flagged.
- **Disconnect** stops use and keeps the connection; **Delete** removes it (audit history is kept).

How an operator runs the credential broker behind this page is in [Connections](/connections).

## Limits and errors

| You see | Why | What to do |
|---|---|---|
| *This invite has expired.* · *…has already been used.* · *…was withdrawn.* | invites last seven days and work once | ask for a new one |
| *This invite was sent to a different address…* | you signed in with another address | sign in with the invited address |
| *This invite link is not valid.* | the link does not match any invite | ask for a new one |
| *This invite could not be checked just now.* | the service did not answer | try again |
| an owner-only refusal from the agent | only owners add, remove or change members | ask an owner |
| *cannot remove the last owner* | a workspace needs an owner | add another owner first |
| *That page is in …, a workspace you do not have access to.* · *That link points at a workspace that is no longer here.* | a `/w/` link you cannot open; Minutes never shows your desk instead | ask for access |
| *Repository access failed. Check the repository URL and credential.* | the clone was refused | check the address, token or deploy key |
| *That is not a repository. Use https://github.com/owner/repo, …* | the address has an empty segment, `.`/`..`, a GitLab page path (`/-/…`), more than 22 segments, or more than `owner/repo` on `github.com` | paste the project's clone address |
| *Vexa can create a repository on GitHub, or on a GitLab host this deployment registered …* (`422`) | publish was asked to create a repository on another host | create it there and publish with `remote_url` |
| *GitLab on … rejected the token (HTTP 401)* · *GitLab group … was not found, or the token cannot see it* | the token lacks the `api` scope, or the group path is wrong | check the token's scopes and the `org` group path |
| *Import interrupted. Check the workspace before retrying.* | the import stopped part-way | check what arrived, then retry |
| *Allow popups for Minutes, then try again.* · *Authorization was not completed.* | Google consent did not finish | allow pop-ups and retry |
| *Connections unavailable. Please try again.* | the credential service did not answer | try again; an operator checks the broker |

The private tier is never shared. On the company workspace only the administrator manages who may
write. A connection label is at most 80 characters.

## How it works

### Flow

1. **Front page.** The terminal reads, in parallel: the workspace record, its tree, its last change, its
   remote status, and for a shared workspace its members and meetings. All go through the gateway to
   agent-api.
2. **Invite.** The agent calls its `workspace_invite` tool, which reaches
   `POST /api/workspace/invite`. agent-api checks that you own the workspace, mints an invite
   restricted to that address and valid once, and builds the link from `VEXA_UI_URL`. For an address
   with no account, it publishes a `workspace.invited` event, and the flows service sends the email.
3. **Join.** `/join` previews the invite (`GET /api/join/preview`, which grants nothing), you sign in,
   and the terminal accepts it (`POST /api/workspace/invites/accept`). agent-api checks the
   gateway-verified email against the invite and adds you to the roster.
4. **Links.** `/w/<id>` is resolved by `GET /api/workspaces/{id}` (or `by-slug`), which always answers
   `readable`, `not-yours` or `gone`.
5. **Attach.** `POST /api/workspace/import` starts an import and returns an operation id; the terminal
   polls `GET /api/workspace/import/{op}/status`. Deploy keys are `GET`/`POST
   /api/workspace/{slug}/deploy-key`; the saved token is `GET`/`POST /api/workspace/git-token` (only a
   masked value comes back).
   - The address is checked first, before any git process exists: the terminal's `repoRef.ts` and
     agent-api's `control_plane/repo_ref.py` accept the same shapes, nested GitLab paths included, and
     refuse the same ones; agent-api also refuses a host only it could reach.
   - The credential is resolved in `control_plane/workspace_credentials.py`: the workspace's deploy key
     for an `ssh` address, else a token typed for this call, else the saved token for `github.com` only.
   - A token is written into the clone, pull or push URL in exactly one place,
     `shared/token_destination.py`, and only for an `https` address. The shape of that userinfo comes
     from `shared/git_provider.py`: the token as typed when it names an account (`oauth2:…`,
     `<user>:…`), else by the operator's provider map, else GitHub's bare form. After a clone the
     stored `origin` is reset to the token-free address.
6. **Publish.** `POST /api/workspace/publish` decides where a new repository would be created before it
   reads any credential (`creation_host` in `control_plane/workspace_publish.py`): `github.com`, or a
   host registered as `gitlab`; anything else answers `422`. On GitLab it resolves the group with
   `GET /api/v4/namespaces/<group path>` and creates the project with `POST /api/v4/projects`, sending
   the token only in the `PRIVATE-TOKEN` header and refusing redirects, then pushes over the same
   token-scrubbed remote as every other push.
7. **Connections.** The terminal's `/api/connections/*` routes call the credential broker as the
   signed-in person. Agents use their own `connection_request` route, which can request a setup but
   never read a credential.

### Who writes what

| Data | Single writer | Where |
|---|---|---|
| Workspace files and roster (`policy/members.json`) | agent-api | the workspace's git repository |
| Invites (hashes only) | agent-api | `.invites/` beside the workspaces, outside every workspace |
| Workspace ids and names | agent-api | `.vexa/workspace.json` in each workspace, plus a registry that can be rebuilt from it |
| Membership index, users by email | admin-api | the identity database |
| Import status | agent-api | outside every workspace |
| Git tokens and deploy keys | agent-api's secret store, or the credential broker when configured | sealed at rest |
| Connections, consent state, audit | the credential broker | its encrypted store |

### Routes

| Browser calls (terminal) | Goes to |
|---|---|
| `GET /api/workspaces/{id}`, `/api/workspaces/by-slug/{slug}`, `/api/workspace/members`, `/api/workspaces/{slug}/git/last-change`, `/api/workspace/git-remote-status` | agent-api, through the gateway's `/agent/*` |
| `GET /api/join/preview` | agent-api `/api/workspace/invites/preview` (no user key) |
| `POST /api/workspace/invites/accept` | agent-api, through the gateway |
| `POST /api/workspace/import`, `GET /api/workspace/import/{op}/status` | agent-api, through the gateway |
| `GET`, `POST /api/workspace/{slug}/deploy-key`, `/api/workspace/git-token` | agent-api, through the gateway |
| `POST /api/workspace/publish` `{ …, host? }`, `POST /api/workspace/push`, `POST /api/workspace/pull` | agent-api, through the gateway; agent-api then calls the git host (and GitLab's `/api/v4` for a create) |
| `GET /api/connections/list`, `POST /api/connections/…` | the credential broker, as the person |
| agent tools `workspace_invite`, `workspace_membership` | agent-api `/api/workspace/invite`, membership routes |

### Configuration

`VEXA_UI_URL` on agent-api (no invite is made without it). `VEXA_GIT_PROVIDERS` on agent-api (Helm
`agentApi.gitProviders`) registers self-hosted git hosts; it is validated when agent-api starts. The terminal's connections routes read
`VEXA_CONNECTIONS_BROKER_URL`, `VEXA_CONNECTIONS_HUMAN_KEY_FILE` and `VEXA_CONNECTIONS_PUBLIC_ORIGIN`;
the broker itself is set up as in [Connections](/connections).

## Why it complies

### Architecture

| Rule | How this design meets it | Gate |
|---|---|---|
| **P2** contracts · **P6** one front door | the browser calls only the terminal; the terminal reaches agent-api through the gateway, and the broker through its contract | `gate:isolation`, `gate:exports`, `gate:domain-doors` |
| **P4** published schemas | the broker's API is the sealed `credential-broker.v1`; the agent tools are in `mcp.tools.v1` | `gate:schema`, `gate:contract-version` |
| **P15** secrets protected by default | credentials live in the broker or the sealed git secret store, never in a workspace, a log or the browser | ungated: reviewed; the broker's deny tests below |
| **P18** fail loud | each invite and link refusal is its own sentence; broker failures are typed `broker_fault`s; an interrupted import says so | ungated: reviewed |
| **P20** authorize every access | roles are checked on every membership and repository route; invites check the verified email | deny tests below |
| **P21** state from evidence | an import is done only when it reports `completed`; a connection request is not a connected account | ungated: reviewed |
| **P23** one writer per carrier | agent-api writes rosters, invites and import status; the broker writes credentials | `gate:dataflow` |
| **P14** config is a validated contract | `VEXA_GIT_PROVIDERS` is declared in agent-api's `config.v1.json`, surfaced on Helm and Compose, and parsed at boot by `shared/config.py`, which refuses a malformed entry | `gate:config-contract` |
| **P15** secrets (git tokens) | a token is put into a URL only by `token_destination.embed_token`, only over `https`, and never persisted: the clone's `origin` and the push remote are reset token-free; the GitLab API gets it in a header, never a URL; errors are scrubbed of the token, its password half and the URL form it took | ungated: reviewed; deny tests below |
| **P18** fail loud | a host publish cannot create on is a typed `UnsupportedHostError` (`422`) naming the host and the alternative; a bad provider map stops the boot; GitLab answers are translated into named refusals (taken name, rejected token, missing group, redirect) | ungated: reviewed |
| no duplication | the address rule lives in `repo_ref.py` with one twin in the terminal, held to the same cases by both test suites; the token shape lives only in `git_provider.py` | ungated: reviewed |

### Security

**Who can do what.** Owners add, remove and change members and manage the repository. Contributors
write. Readers read. Only the owner or an administrator renames a workspace. The private tier cannot be
shared, and only the administrator manages the company workspace.

**Protections.**

- Invite tokens are random, shown once, and stored only as a hash. They expire, can be withdrawn, and
  are used once under a lock, so two people cannot redeem the same invite.
- A restricted invite is checked against the email the gateway verified, not one the browser sends.
- The invite preview grants nothing and does not say whether a workspace exists.
- A repository address is a whitelist: plain path segments only, never empty, `.`, `..` or `-`, at
  most 22 deep, exactly two on `github.com`; a host only agent-api could reach is refused, nested path
  or not.
- A saved token goes only to `https://github.com/`. A token for another host is typed for one call and
  travels only over `https`. Publish sends a token to an API only on `github.com` or a host the operator
  registered as GitLab, and never follows a redirect with it.
- Deploy keys are generated server-side; the private half is sealed at rest and written to a
  permission-`0600` file only for the length of one git operation.
- Connection routes accept only the deployment's own origin and a closed set of actions. The terminal
  holds the person's broker key; agent workers hold none.
- Consent pop-ups follow only Google's authorization address or the address the setup declared, and
  report a status, never a credential, back to the page.
