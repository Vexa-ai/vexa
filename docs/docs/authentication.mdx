title: "Authentication"
description: "Mint an API key, send it on every request, scope it, and rotate it."
---

Every public request carries an API key in the **`X-API-Key`** header. The gateway resolves the key
to a user and injects identity downstream — you never pass a user id or subject yourself; the server
derives it from the key.

```bash
-H "X-API-Key: <API_KEY>"
```

## Base URL

| Deployment | API base |
|---|---|
| Self-hosted (`make all` / compose) | `http://localhost:18056` (`API_GATEWAY_HOST_PORT`) |
| Hosted | `https://api.cloud.vexa.ai` |

## Getting a key

**Don't have a key yet?** Hosted: sign in at [vexa.ai/signin](https://vexa.ai/signin) with a Google
account and copy your key from [your account page](https://vexa.ai/account) — free credit, no card
required. Self-hosted: `make all` prints a key when the stack comes up.

`make all` mints a key as part of bring-up and **prints it** (along with the service URLs) when the
stack is ready — copy it from the `make all` output and use it as your `X-API-Key`.

### Minting more keys

To mint additional keys, use the `provision-token` make target with your `ADMIN_TOKEN`. There is no
default: `make up` mints one into `deploy/compose/.env` (and replaces any value this repository ever
published for it, such as the old `dev-admin-token`), and the services refuse to boot on a published
one. Treat it like a root password — it mints a key for any user:

```bash
# from deploy/compose
make -s provision-token ADMIN_TOKEN="$(sed -n 's/^ADMIN_TOKEN=//p' .env)"
# → prints a freshly minted vxa_... API key
```

Under the hood the **admin API** mints keys. It listens on `http://localhost:18057` by default
(`ADMIN_API_PORT`) and is protected by `ADMIN_TOKEN` via the `X-Admin-API-Key` header — you can call it
directly for finer control over users and scopes:

```bash
export ADMIN=http://localhost:18057
export ADMIN_TOKEN="$(sed -n 's/^ADMIN_TOKEN=//p' .env)"   # the ADMIN_TOKEN `make up` minted into .env

# 1. create (or find) a user
curl -X POST "$ADMIN/admin/users" \
  -H "X-Admin-API-Key: $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"email":"jane@acme.com","name":"Jane","max_concurrent_bots":2}'
# → {"id":1,"email":"jane@acme.com","name":"Jane","max_concurrent_bots":2}

# 2. mint a key for that user id (JSON body preferred)
curl -X POST "$ADMIN/admin/users/1/tokens" \
  -H "X-Admin-API-Key: $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"scopes":["bot","tx"]}'
# → {"id":7,"token":"vxa_bot_...","user_id":1,"scopes":["bot","tx"]}

# query form still works: ?scopes=bot,tx or ?scope=bot
```

The returned `token` is your `X-API-Key`. **It is shown once** — store it.

## Scopes

A key carries one or more scopes. Pass them in the JSON body as `{"scopes":["bot","tx"]}`, or as
query `scope=<one>` / `scopes=<a>,<b>`. The body wins when both are present. An unknown body field
is refused with `422` — never silently dropped.

| Scope | Grants |
|---|---|
| `bot` | bot lifecycle — `POST`/`GET`/`DELETE /bots`, `/bots/status`, bot config — and the calendar connections (`/user/calendar`, `/user/calendars/*`), because an auto-join feed spawns bots |
| `tx` | the transcript and meeting-record plane — `/meetings*`, `/transcripts/*` |
| `browser` | browser-tool capabilities. **Reaches no API route today** — a browser-only key can call [`/auth/me`](/api/settings#identity) and nothing else |

`/recordings*`, `/user/webhook*`, `/user/models`, `/user/transcription`, `/agent/*` and `/mcp` accept
either `bot` or `tx`. Most keys want both: `{"scopes":["bot","tx"]}`. The three `/user/*` routes in
that list are the [Settings API](/api/settings) — model credentials, transcription backend, and
webhook delivery, stored per key owner.

Every route requires a scope. A key that holds none of the scopes a route accepts gets `403`,
whichever route it is.

Keys are prefixed by their primary scope — `vxa_bot_…`, `vxa_tx_…`, `vxa_browser_…`. A key without a
recognized scope is rejected.

## Rotating and revoking

Mint a new key, switch your clients over, then delete the old one by its token id:

```bash
curl -X DELETE "$ADMIN/admin/tokens/7" -H "X-Admin-API-Key: $ADMIN_TOKEN"   # → 204
```

Set an expiry at mint time with `expires_in=<seconds>`; expired keys are rejected automatically.

### Login-minted tokens (`terminal-login`)

When a user signs in through the terminal (OAuth or email login), the terminal mints an API token
named **`terminal-login`** to populate the auth cookie. These are **bounded per user**: after each
sign-in the terminal keeps only the newest `VEXA_TERMINAL_LOGIN_TOKEN_CAP` (default `3`) and revokes
the older ones. So when you audit a user's tokens —

```bash
curl "$ADMIN/admin/users/1/tokens" -H "X-Admin-API-Key: $ADMIN_TOKEN"
```

— the `terminal-login`-named entries are login sessions (capped, not unbounded), while any
differently-named entries are self-serve keys the user minted and are never pruned by login.

## Who may sign in to the terminal

The terminal's sign-in doors — the emailed link, Google, Microsoft and your own OIDC provider — each end by creating an
account and minting a `terminal-login` key for it, so they are gated on **who** the address is, not
only on proof that the person holds it. A sign-in is admitted only for:

- an **existing user** of this instance (upgrading locks nobody out),
- an **admin** — the claimed one, or an address in `VEXA_ADMIN_EMAILS`,
- an address on the **sign-in allow-list**: `VEXA_SIGNIN_ALLOW` on admin-api plus what the admin
  adds in the terminal under **Settings → Sign-in**. Entries are exact addresses
  (`alice@example.org`) or whole domains (`@example.com`, that domain exactly).

Anybody else is refused before an account exists. The email form answers "check your email" for
every address and mails only the admitted ones; the redeem page and the OAuth return show one
sentence that names no list. If admin-api cannot answer, new sign-ins are refused (existing sessions
keep working).

**The first administrator needs the admin claim code.** While no admin has been claimed and
`VEXA_ADMIN_EMAILS` is empty, admin-api writes a one-time claim code to its log at boot. The terminal's
claim screen asks for it; the sign-in that carries it is admitted and becomes the admin, and the code
is spent. Without it nobody new can sign in to an unclaimed instance and nobody can take the role.
Restarting admin-api issues a fresh code. `VEXA_ADMIN_EMAILS` (on admin-api) names the admins instead,
and then no code is issued. A sign-in allow-list narrows the claim further: only an address on the
list may sign in or claim the role. admin-api makes every one of these decisions; the terminal only
asks it.
An account created through `POST /admin/users` (above) counts as an existing user, so minting a key
for someone also lets them sign in.

`VEXA_SIGNIN_ALLOW=*` opens sign-in to any address. It is an operator-only setting: the admin's
Settings → Sign-in list refuses `*`, a `*` already stored there is ignored, and admin-api logs a
warning at boot whenever sign-in is open.

### The emailed link

- The link is valid for 15 minutes by default (`MAGIC_LINK_TTL_SECONDS`, capped at 60 minutes) and
  signs in **once**, whichever terminal replica redeems it. A second click shows "already used".
- An address is at most 254 characters. Requests for a link are budgeted per client address
  (`MAGIC_LINK_RATE_PER_IP`, default 20) and per email address (`MAGIC_LINK_RATE_PER_ADDRESS`,
  default 5) over `MAGIC_LINK_RATE_WINDOW_SECONDS` (default 900). Behind a reverse proxy, set
  `TERMINAL_TRUSTED_PROXIES` to the proxy's addresses so the per-client budget counts real clients;
  the Helm chart sets the in-cluster ranges when the terminal's Service is `ClusterIP`.
- The link is mailed through the deployment's relay (`VEXA_MAIL_SMTP_*`). The terminal uses
  STARTTLS whenever the relay offers it, and never sends `VEXA_MAIL_SMTP_USER`/`_PASSWORD` over an
  unencrypted connection.

### Google and Microsoft

- Google: the ID token's `email_verified` must be `true`.
- Microsoft: with `MICROSOFT_TENANT_ID` set to a tenant id, the token's tenant must be that one; with
  a multi-tenant authority, the token must carry `xms_edov: true`.
- The first OAuth sign-in to an account records the provider's stable subject on it. A later sign-in
  through the same provider with a different subject is refused, even for the same address.
- After sign-in the browser returns only to a path on this instance or a URL on its exact origin.

### Your own identity provider (OIDC)

- ADFS, Keycloak or any OpenID Connect provider, configured by issuer URL, client id and secret.
  Setup, the checklist for your IdP team, and the failure modes: [Sign-in with your own identity
  provider](/sign-in-oidc).
- The address comes from the verified ID token of the configured issuer; the account is bound to
  that identity like the Google and Microsoft ones.
- `VEXA_SIGNIN_METHODS` chooses which doors the card offers (for example only `oidc`).

### What a person sees

| Situation | What the terminal shows |
|---|---|
| Address not admitted | The email form still answers "check your email"; nothing is mailed. The redeem page and the OAuth return show one sentence that names no list. |
| The link was already used, expired, or altered | The redeem page says which (`410` or `400`) and offers a new link. |
| admin-api cannot be reached | New sign-ins are refused (`503`); existing sessions keep working. If the link's single-use record cannot be checked, the link is not spent and works again later; if the account step fails after that check, the page says the link was used and asks for a new one. |
| Another Google, Microsoft or OIDC identity for an account already bound to one | Refused with the same sentence. |
| No public URL configured (`NEXTAUTH_URL` / `TERMINAL_URL`) | The email form answers `503` and nothing is mailed. |

## How it works

1. **Ask.** The person submits an address (`POST /api/auth/request-link`) or starts OAuth
   (`/api/auth/[...nextauth]`). The terminal checks the address shape and the request budget.
2. **Admission.** The terminal's server asks admin-api `POST /internal/signin-admission`
   (`signin.v1` `SigninAdmissionRequest`). admin-api decides from its own inputs: the user rows, the
   claimed admin, `VEXA_ADMIN_EMAILS`, the `signin` setting and `VEXA_SIGNIN_ALLOW`
   (`admin_api/app/signin_allow.py` `decide`). Only a literal `admitted: true` admits.
3. **Proof.** For the link, the terminal mails a token signed with the link key (HMAC-SHA256 over the
   address, expiry and a random id). For OAuth, the provider's ID token is checked as above.
4. **Redeem once.** The redeem route verifies the signature and expiry, then asks admin-api
   `POST /internal/signin-links/redeem`, which records the link id in the service Redis with
   `SET NX` until the link expires (`vexa:signin-link:redeemed:<jti>`). Only the first request
   succeeds.
5. **Account and binding.** `findOrCreateUserToken` asks admission again, finds or creates the user
   (`POST /admin/users`) and, for OAuth, binds the provider subject
   (`PUT /internal/users/{id}/provider-subject`).
6. **Session.** The terminal mints a `terminal-login` key (`POST /admin/users/{id}/tokens`), keeps
   the newest `VEXA_TERMINAL_LOGIN_TOKEN_CAP`, and sets the httpOnly `vexa-token` and
   `vexa-user-info` cookies.

**Who writes what.** admin-api is the only writer of users, tokens, the `signin` setting, the claim
record, the redeemed-link records and the provider bindings (`users.data.provider_subjects`). The
terminal stores nothing but the two cookies.

**Configuration.** admin-api (`admin_api/config.v1.json`): `VEXA_SIGNIN_ALLOW`, `VEXA_ADMIN_EMAILS`,
`REDIS_URL`, `INTERNAL_API_SECRET`. Terminal: `TERMINAL_TRUSTED_PROXIES`, `VEXA_MAIL_SMTP_*`, the
OIDC provider's `VEXA_OIDC_*` and `VEXA_SIGNIN_METHODS` are declared in `clients/terminal/config.v1.json`; `NEXTAUTH_SECRET`, `NEXTAUTH_URL`, `MAGIC_LINK_SECRET`,
`MAGIC_LINK_TTL_SECONDS`, `MAGIC_LINK_RATE_*` and the `GOOGLE_CLIENT_*` / `MICROSOFT_*` provider keys
are read from the terminal's environment. See [Configuration](/configuration).

## Why it complies

**Architecture**

| Rule | How this design meets it | Enforced by |
|---|---|---|
| P2, P4 — couple through sealed contracts | The terminal and admin-api meet only through `signin.v1` (admission, the claim, link redemption, provider binding); its reason vocabularies are generated into both sides. | `gate:schema`, `gate:contract-version` |
| P6 — one front door | The terminal calls admin-api's internal routes through one client (`adminApi.ts`). | `gate:domain-doors` |
| P23 — one writer per carrier | admin-api alone writes users, tokens, the allow-list, the redeemed-link records and the bindings; the terminal holds no list and no ledger. | `gate:dataflow`, `gate:calm` |
| P14 — config is a validated contract | admin-api's keys and the terminal's mail, proxy, OIDC and sign-in-method keys are declared in `config.v1.json`; the terminal's NextAuth and link keys are not yet. | `gate:config-contract` (declared keys) |
| P18 — fail loud | An unreachable admin-api, a store that cannot be written or a missing public URL refuses with `503`; nothing signs in silently. | ungated: reviewed |
| P20 — default-deny | Admission, link redemption and binding all refuse unless admin-api answers yes. | ungated: reviewed; deny tests below |

**Security**

- **Who decides.** admin-api alone. Its internal routes need `INTERNAL_API_SECRET`, with no
  development-mode exception for admission, link redemption or binding.
- **What is refused.** An address not admitted; a second redemption of a link; an expired or forged
  link; an unverified provider email; another provider identity for a bound account; a redirect off
  this origin. The development login (`/api/auth/login`) answers `403` on every build other than
  development.
- **What is not revealed.** Admitted and refused addresses get the same response, in the same time.

## What can go wrong

| Status | `detail` | Meaning |
|---|---|---|
| `401` | `Missing API key` | no `X-API-Key` header |
| `401` | `Invalid API key` | unknown or revoked key |
| `403` | `Insufficient scope for this endpoint` | key lacks the scope this route needs |
