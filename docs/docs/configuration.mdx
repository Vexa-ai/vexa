Vexa is configured by environment variables, set in `deploy/compose/.env` for Docker Compose (seeded
from `.env.example` on first `make all`). Defaults below are what the stack falls back to when the
variable is unset — fine for local evaluation, **not** for anything exposed.

<Warning>
Change every secret (`ADMIN_TOKEN`, `INTERNAL_API_SECRET`, DB and storage credentials,
`VEXA_DISPATCH_SIGNING_KEY`, `NEXTAUTH_SECRET`) before putting the stack on a network. The defaults
are public.
</Warning>

## Transcription (STT)

| Variable | Default | Purpose |
|---|---|---|
| `TRANSCRIPTION_SERVICE_URL` | — | STT service URL, e.g. `http://<gpu-host>:8083`. Give it the **base URL** (canonical) or the full `…/v1/audio/transcriptions` endpoint — every consumer appends the path only when it is missing, so both shapes behave identically. Point it at the bundled service you deploy separately (`deploy/transcription`) or any OpenAI-compatible endpoint. Unset + default `transcribe_enabled=true` → `POST /bots` answers **503** naming the missing keys (not a silent empty transcript). |
| `TRANSCRIPTION_SERVICE_TOKEN` | — | STT auth token — must match the `API_TOKEN` of your `deploy/transcription` unit, or a token from `vexa.ai/account`. |
| `TRANSCRIPTION_MODEL` | `whisper-1` | STT model id sent on every transcription request (the OpenAI-compatible `model` field). **Set it when the backend validates model ids** — Groq (`whisper-large-v3-turbo`), OpenAI (`whisper-1` / `gpt-4o-transcribe`), vLLM/LiteLLM (the served name) — or every request fails `model_not_found`. Ignored by the bundled `deploy/transcription` unit, whose model is its own `MODEL_SIZE`. |
| `DEFAULT_TRANSCRIPTION_LANGUAGE` | — | The language bots transcribe in when neither the request nor the person's Settings say: one code, e.g. `de`. With the list below it must be one of them and is the fallback. Helm: `meetingApi.transcriptionLanguage`. A value meeting-api cannot use stops its boot. See [Transcription language](/how-to/transcription-language). |
| `DEFAULT_TRANSCRIPTION_ALLOWED_LANGUAGES` | — | Codes detection is restricted to, comma-separated with no spaces, e.g. `de,en`. Helm: `meetingApi.transcriptionAllowedLanguages` (a list). |
| `TRANSCRIBE_ENABLED` | `true` | Deployment-level default for a spawn's `transcribe_enabled` when `POST /bots` does not say. Resolution: **explicit request body wins** → else this env → else `true`. Set `false` for a deliberately no-STT deployment: bots spawn **capture-only** instead of answering 503. Leaving it **empty means `true`** — only an explicit `false`/`0`/`no`/`off` opts out. |
| `RECORDING_ENABLED` | `true` | Deployment-level default for a spawn's recording when `POST /bots` does not say. Same empty-means-default rule as above. |
| `BOT_ALONE_SILENCE_WINDOW_MS` | `600000` | Active-phase remote-audio silence window before the bot leaves with `completed(left_alone)`. Forwarded to spawned bots. A request's `automatic_leave.max_time_left_alone` overrides it. |
| `BOT_SPEAKER_MIN_AUDIO_SEC` | `2` | Google Meet minimum audio window before submitting to STT. Lower values reduce first-transcript latency but increase request frequency. |
| `BOT_SPEAKER_SUBMIT_INTERVAL_SEC` | `2` | Google Meet speaker-stream submission interval. |
| `BOT_SPEAKER_CONFIRM_THRESHOLD` | `2` | Consecutive matching STT results required to confirm a segment. `1` lowers latency but reduces LocalAgreement protection against corrections. |
| `BOT_SPEAKER_MAX_BUFFER_SEC` | `30` | Maximum buffered Google Meet audio before a forced submission. |
| `BOT_SPEAKER_IDLE_TIMEOUT_SEC` | `15` | Flush/reset timeout after a speaker stops producing audio. |
| `BOT_SPEAKER_MIN_FINAL_AUDIO_SEC` | `1` | A speaker turn whose whole audio is shorter than this is not sent to STT as a final window (the sub-second tail of a longer turn always is): sub-second fragments come back as phrases like "Thank you." that the hallucination filter discards. Skipped seconds are counted as `short` in the bot's `[COVERAGE]` line. |
| `BOT_STT_TIMEOUT_SEC` | `90` | Per-request STT timeout for meeting bots, in seconds (minimum `20`). A remote STT can take 15–30 s for a few seconds of audio; a shorter timeout aborts requests that would have answered. Audio is never dropped while a request is in flight. See [Troubleshooting](/troubleshooting#transcript-covers-only-part-of-the-meeting). |
| `BOT_TRANSCRIPTION_LATENCY` | unset | Unset: one pipeline, show fast and then reconfirm. A pause of 0.5–0.7 s ends an utterance, which is shown at once as a draft; per-participant tracks refresh their draft about every second, and no request carries more than 10 s. The drafts are then replaced by reconfirmed segments (see `BOT_TRANSCRIPT_RECONFIRM_SEC`). `standard` keeps the confirm-on-agreement lane. `low` keeps the fast tuning even with reconfirmation off; it then publishes first versions as final. Explicit `BOT_SPEAKER_*` knobs still win. Teams uses its own lane and is unaffected. |
| `BOT_STT_CONFIDENCE_FILTER` | unset | `strict` makes meeting bots also drop transcript segments that Whisper itself decoded with low confidence: an average log-probability under −1.0 for the window. This removes text the model invents over noise or music, such as an outro line or a lone "you". It runs after the speech gate and the always-on rule, and only on requests of 8 s or more (shorter windows score lower for real speech too). Measured on real English and Russian recordings, it removed every invented segment found in correctly detected windows and lost under 1% of real words, all short mumbled phrases. Off by default. |
| `BOT_TRANSCRIPT_RECONFIRM_SEC` | `10` | Show fast, then reconfirm (Google Meet, Zoom, calls). Every window is shown at once as a draft, greyed until confirmed. When a speaker pauses, or this many seconds of their speech accumulate, that stretch is transcribed again in one request with the speaker's earlier text as context. One confirmed segment then replaces the drafts. Under STT overload the reconfirmation waits; if it cannot run, the drafts are confirmed as they are, so no words are lost. `0` turns it off. |

The STT service is the **GPU workload, deployed separately** from this stack — see
[Deployment → Transcription](/deployment#transcription-the-separate-gpu-unit). The main stack
stays GPU-free and reaches it over the network via the two variables above.

### When the backend is wrong, you learn at configure time

A URL or token that does not work is refused where you set it, not by an empty transcript hours
later. The same live check runs at three surfaces, and all three name the same cause:

| Surface | What you see |
|---|---|
| Setup wizard — **Save & test** | Red with the endpoint's own status: `Token REJECTED by … (HTTP 401)` or `No transcriptions endpoint at … (HTTP 404)`. A green here means a bot will transcribe — the wizard verifies with the exact request a bot's first audio chunk makes. |
| Boot log + `GET /health` | The `stt` capability row reads `misconfigured` with a `probe.reason`, instead of `configured`. A failing probe warns loudly but never blocks boot. |
| `POST /bots` | `503` carrying that same reason, **before** any meeting row is written — never a bot that joins and silently transcribes nothing. |

The verdict is cached for 60s, so after fixing the value either wait a minute or call
`GET /health?force=1` to re-probe immediately.

<Note>
A `404` from the transcriptions path is treated as a **wrong URL**, not as proof of life: a real
OpenAI-compatible endpoint answers `400` or `401` to an empty request body and never `404`. Some
gateways also answer `404` for a rejected credential — the error text names both possibilities.
</Note>

<Warning>
**Never put a comment on the same line as a value in `.env`.** Write it on its own line above the
key. Compose tolerates a trailing `# comment`, but `docker run --env-file` (which Vexa Lite uses)
does **not** strip it — the comment becomes part of the value, so `TERMINAL_PORT=13000  # the UI`
sets the port to the literal string `13000  # the UI`.
</Warning>

## Optional service authority

Stock self-hosted Vexa has no external service authority and continues to admit bots exactly as
before. Operators who need an independently owned admission/active-service policy can opt into the
sealed `service-authority.v1` boundary:

| Variable | Default | Purpose |
|---|---|---|
| `VEXA_SERVICE_AUTHORITY_CONFIG` | — | Compact JSON containing a credential-free `url`, `contract_version: "service-authority.v1"`, `timeout_ms`, `response_max_age_seconds`, `failure_policy: "closed"`, and `mode: "enforce"` or `"observe"`. HTTPS is required except for loopback/in-cluster HTTP. |
| `VEXA_SERVICE_AUTHORITY_SECRET` | — | HMAC-SHA256 secret for the exact timestamped request bytes. Required only when the config is set; keep it in the deployment secret store. |
| `SERVICE_AUTHORITY_SWEEP_INTERVAL_S` | `15` | Poll cadence for discovering due active-service boundaries. Decisions remain anchored to admitted time plus whole minutes, so changing the poll cadence does not change the billable boundary. |

The request contains service identity, authoritative user ID, service mode, frozen transcription
provider, concurrency, and lifecycle timestamps. It deliberately contains no email, customer or
payment-provider identifier, price, balance, transcription endpoint URL, or credential. A
configured authority that is unavailable, malformed, stale, or bound to another request fails
closed before a new bot is spawned. During active service, its stop intent is committed before
runtime teardown and resumed after restart.

`mode: "observe"` records decisions without refusing or stopping service. It is useful for rollout,
but it is not evidence that a hard service control is enforced. A session admitted in one mode is
never reinterpreted under another mode after a deployment change.

## Operator terminal callback

An operator can send terminal service facts to one deployment-owned system endpoint. This is
separate from a user's webhook configuration: the URL is frozen at boot, cannot be supplied by an
API caller or meeting payload, and receives only `meeting.completed` and `bot.failed`.

| Variable | Default | Purpose |
|---|---|---|
| `VEXA_SYSTEM_WEBHOOK_URL` | — | Absolute operator-owned endpoint for terminal `webhook.v1` envelopes. HTTPS is required unless private HTTP is explicitly enabled. URLs with credentials, query strings or fragments are rejected. |
| `VEXA_SYSTEM_WEBHOOK_SECRET` | — | HMAC-SHA256 secret for the exact timestamped envelope bytes. Required with the URL and stored only in the deployment secret store. |
| `VEXA_SYSTEM_WEBHOOK_ALLOW_PRIVATE_HTTP` | `false` | Explicitly permits a private/in-cluster HTTP destination such as a billing service on the Compose/Kubernetes network. It does not change customer webhook SSRF protection. |
| `VEXA_SYSTEM_WEBHOOK_TIMEOUT_S` | `10` | Bounded delivery timeout, greater than zero and at most 60 seconds. |

Transient delivery failures enter a dedicated retry/dead-letter queue and retain the same
deterministic event ID. Customer webhook destinations continue through DNS/IP validation and cannot
redirect this operator callback. Leave all four values unset for the stock OSS behavior.

## Secrets & identity

| Variable | Default | Purpose |
|---|---|---|
| `ADMIN_TOKEN` | none — you must set it | Admin API key (`X-Admin-API-Key`) — mints users and tokens (meeting-api reads it as `ADMIN_TOKEN`, admin-api as `ADMIN_API_TOKEN`). meeting-api derives the key that signs every per-spawn MeetingToken from it and never signs with it directly. Never a value published in this repository: the services refuse to boot on one. |
| `INTERNAL_API_SECRET` | none — you must set it | Shared secret for service-to-service calls. |
| `REDIS_PASSWORD` | none — you must set it (compose) | The bundled Redis's default-user password; the services connect with it inside their Redis URL, and no bot or worker sees it. Compose's `redis` refuses to start without one (`make all` mints it; keep it URL-safe — `openssl rand -hex 32`); Helm generates one (`secrets.redisPassword`, or a `REDIS_PASSWORD` key in `secrets.existingSecretName`); Lite mints one per boot. |
| `REDIS_WORKLOAD_ACL` | `per-workload` | **agent-api, meeting-api.** What a spawned agent worker or meeting bot connects to Redis as. `per-workload`: a Redis user of its own — a worker its own unit's four keys (input, output, read cursor, delegation token), a bot its own meeting's two channels and the transcript stream it appends to — defined at spawn and removed when it ends. `shared`: the service connection, only for a Redis that cannot define users (some managed services); every worker and bot can then read and write every other's keys, so set it only where every person on the instance trusts every other. With your own Redis, the services' user needs `ACL SETUSER` / `ACL DELUSER` / `ACL GETUSER`, and the server needs read-only key permissions (Redis 7+ or Valkey 7.2+, which every Vexa surface ships): on an older server no agent worker user is defined and its turn is refused, because a read-write user could rewrite the privacy marks and mount audience its own commit hold reads. Any other value refuses the boot of both services. |
| `RUNTIME_API_TOKEN` | none — you must set it | **runtime, agent-api, meeting-api.** The runtime's caller credential: every runtime route except `/health` requires it as `Authorization: Bearer`, and agent-api and meeting-api present it. At least 32 bytes and never a placeholder; all three refuse to boot otherwise. No bot or agent worker is given it. `make all` mints one; Helm generates one and keeps it across upgrades (`secrets.runtimeApiToken`, or a `RUNTIME_API_TOKEN` key in `secrets.existingSecretName`); Lite mints one per boot. |
| `VEXA_GATEWAY_IDENTITY_SIGNING_KEY_FILE` | none — generated at install | **Gateway only.** A file holding the gateway's Ed25519 private key (PKCS#8 PEM). The gateway signs the identity it resolved onto every request it forwards (`X-Vexa-Identity`). No other service mounts it. |
| `VEXA_SUBJECT_TICKET_KEY_FILE` | none — generated at install (with flows) | **meeting-api, agent-api, each its own.** A file holding that service's Ed25519 private key for subject tickets (subject-ticket.v1): meeting-api signs who a meeting fact is about, agent-api a routine a person turned on and a message to a person. The gateway's flows service door verifies them. Unset, facts reach flows without a ticket and the door refuses the person-bound calls they cause. |
| `VEXA_FLOWS_MAIL_TICKET_KEY_FILE` | none — generated at install | **flows-mailbox, flows-worker.** The mail intake's own subject-ticket key, for authenticated invites and replies. Set on every flows lane, mounted only on these two. |
| `VEXA_SUBJECT_TICKET_KEYS_DIR` | none — generated at install (with flows) | **Gateway only.** The producers' public keys, `meetings.pem`, `agent.pem` and `mail.pem`. The service door forwards a flows call made for a person only with a ticket one of them verifies. Public keys only. |
| `VEXA_GATEWAY_IDENTITY_PUBLIC_KEY_FILE` | none — generated at install | **agent-api, meeting-api, credential broker.** A file holding the matching public key. They verify the gateway's signature and cannot make one: agent-api and meeting-api refuse a user header that is not signed, and the broker refuses a Connections call without the gateway's signature for that person. A private key here refuses the boot. |

The identity keypair is generated for you: compose's `identity-keys` service on first start (two
volumes, the private one mounted by the gateway alone), the Helm chart (a Secret and a ConfigMap),
and the Lite entrypoint (persisted in its state directory). To bring your own, generate it with
`openssl genpkey -algorithm ed25519 -out signing-key.pem` and
`openssl pkey -in signing-key.pem -pubout -out public-key.pem`. The subject-ticket keypairs are
generated the same way: compose's `subject-ticket-keys` service, the Helm chart's
`subject-ticket-keys.yaml` (see [Flows operations → Subject tickets](/flows/operations#subject-tickets)).

Neither has a default any more. Both services **refuse to boot** on a placeholder literal
(`changeme`, `vexa-internal-secret`, `lite-internal-secret`, `default`, `secret`, …, and for
`ADMIN_TOKEN` every value this repository ever shipped for it, such as `dev-admin-token` and
`CHANGE_ME`): a value published in this repository is not a secret, and a stack running on one comes up green while
anyone who read the repo can mint an API key for any account. Generate each with
`openssl rand -hex 32` and set the same `ADMIN_TOKEN` on every service that shares the tier.

## Bot participant name

`DEFAULT_BOT_NAME` on meeting-api names the bot, and compose, Lite and helm ship it as `Vexa`. To
rename the bot, set it in `.env` (compose/Lite) or `meetingApi.defaultBotName` (helm) and restart
meeting-api — the terminal needs no rebuild, because it omits `bot_name` when it sends a bot and
lets the deployment decide. Blank the variable and meeting-api falls back to `VexaBot-{random}`.

Two things still win over it. An explicit `bot_name` in a `POST /bots` request always takes
precedence, which is also how a calendar connection applies its own per-calendar bot name. And a
name baked into the terminal image at build time overrides the deployment: pass
`NEXT_PUBLIC_DEFAULT_BOT_NAME` as a Docker build arg (there is a commented-out line for it under the
terminal's `build.args` in compose) and rebuild the image — a rename then costs another rebuild,
which is why the runtime variable is the better knob. Direct `joinMeeting` callers read
`DEFAULT_BOT_NAME` too and fall back to `Vexa Join Layer`.

<Warning>
**Microsoft Teams only accepts letters, numbers, spaces and `- ' . _ @` in a guest's name.** A name
such as `Notetaker (recording)` is refused: Teams keeps its **Join now** button disabled, so the bot
cannot ask to join any Teams meeting. The bot stops in under half a minute, on the Teams
pre-join screen. The run ends `join_failure`, and its reason text (`data.reason`) starts with
`teams_prejoin_blocked` and quotes the rule Teams showed. Pick a name that fits the rule, for example
`Notetaker - recording`, in `DEFAULT_BOT_NAME`, in `meetingApi.defaultBotName` (Helm), in a calendar
connection's bot name, or in the `bot_name` of a `POST /bots` request. Google Meet and Zoom accept
parentheses, so a name that works there can still fail on Teams. Letters with accents and other
scripts are fine. How the check works and why it complies:
[A name Teams refuses](/troubleshooting/completion-reasons#a-name-teams-refuses-teams_prejoin_blocked).
</Warning>

## Database & storage

| Variable | Default | Purpose |
|---|---|---|
| `DB_NAME` / `DB_USER` | `vexa` / `postgres` | Postgres database and user (metadata). On an external Postgres the user also creates the session store's and the CRM's own roles, which needs `CREATEROLE`, or roles your database team creates: see [Database privileges on an external Postgres](/deployment-kubernetes#database-privileges-on-an-external-postgres). |
| `DB_PASSWORD` | none | The Postgres password. </Note>

### Claude subscription credentials (`HOST_CLAUDE_CREDENTIALS`)

Setting `HOST_CLAUDE_CREDENTIALS=~/.claude/.credentials.json` mounts your Claude Code
sign-in into the agent containers (read-only), so the agent runs on your subscription
instead of an API key. It needs the company policy `subscription_token_proxy: allow` in
`_global/POLICIES.md`: with the default `deny`, the file is mounted into no worker and a
subscription turn is refused. Whether that file stays valid depends on the host OS:

- **Linux** (and **Windows via WSL2** — run the stack and the `claude` CLI inside WSL):
  the file is Claude Code's own store; the CLI refreshes it in place. Nothing to do.
- **macOS**: the CLI's source of truth is the login **Keychain** — the file is a one-time
  export whose token expires every ~8–12 hours. Symptom: agent chat fails with
  `401 Invalid authentication credentials` while `claude` works fine in your terminal.
  Install the bundled sync daemon once:

  ```bash
  deploy/bin/claude-creds-sync/install.sh
  ```

  It registers a launchd user agent (`ai.vexa.claude-creds-sync`) that re-exports the
  Keychain into the file every 5 minutes, write-only-on-change, preserving the inode the
  containers mount. `install.sh uninstall` removes it. Details:
  `deploy/bin/claude-creds-sync/README.md`.

The credential-file mount is a single-developer convenience. For a portable setup that
survives token rotation on any OS, configure an API key or a custom endpoint in
**Settings → Models** (stored per-user/global in the database) — see the setup wizard or
the table above.

## Tool providers that are late

Identity must answer when the MCP service starts, or it refuses to start. Every tool provider —
meetings, flows, agent and CRM — that does not answer at start (or, for meetings, answers without its
tool list because an older pod is still rolling) is logged, and the service starts with the tools that
did answer. It asks each missing provider again every `VEXA_MCP_REFRESH_SECONDS` (default 30) until it
answers; its tools then join `tools/list`, under the same visibility settings as every other tool.
Readiness does not wait for a late provider: the tool list heals within one refresh interval.

## MCP tool visibility

Which tools a caller is shown in `tools/list` and may call. Unset, every tool the deployment serves
is shown to every caller, as before.

| Variable | Default | Purpose |
|---|---|---|
| `VEXA_MCP_TOOLS_ALLOW` | — (every tool) | Comma-separated tool names an ordinary caller is shown and may call. Helm: `mcp.tools.allow`. |
| `VEXA_MCP_TOOLS_DENY` | — | Comma-separated tool names nobody is shown or may call. Helm: `mcp.tools.deny`. |
| `VEXA_MCP_TOOLS_COHORT` | — (nobody) | The people shown every tool despite the allow-list: user ids, exact addresses and `@domain` entries, comma-separated and case-insensitive; `*` is everyone. The deny-list still applies to them. Helm: `mcp.tools.cohort`. |

To keep existing keys on the 0.12 surface after an upgrade, set the allow-list to the 0.12 tool list
(`core/gateway/services/mcp/tests/fixtures/tools-list-v0.12.json`, comma-joined) and name the people
who try the new tools in the cohort.

**How it works.** The MCP service reads the three settings at boot. On `tools/list` it removes every
tool the caller is not shown; the descriptors that remain are unchanged. On `tools/call` a tool the
caller is not shown is answered `Unknown tool: <name>`, the same answer as for a tool that does not
exist, and nothing is forwarded. The caller is identified by the identity the gateway stamped on the
`/mcp` request; a request without one is an ordinary caller. A name in the allow-list or deny-list
that the deployment does not serve is logged at boot.

**Why it complies.** The setting only narrows what a caller is offered. Every tool still acts through
the gateway with the caller's own credential, so key scopes and `VEXA_AGENT_ALLOW` keep deciding what
that credential may do; visibility is not an authorization boundary and does not replace them. A
hidden tool cannot be reached by naming it, and its refusal does not reveal that it exists. With the
settings unset the surface is exactly what it was.

## LLM spend cap

Agent turns are capped by what they spend on model calls, in US dollars per UTC day and per UTC month,
for the whole deployment and for each person. The caps are `_global/POLICIES.md` keys, so the admin
account changes them without a restart; `off` removes one cap.

| Key / variable | Default | Purpose |
|---|---|---|
| `llm_budget_org_daily_usd` · `llm_budget_org_monthly_usd` | `25` · `250` | The deployment's caps. |
| `llm_budget_user_daily_usd` · `llm_budget_user_monthly_usd` | `5` · `50` | Each person's caps. |
| `llm_price_input_usd_per_mtok` · `llm_price_output_usd_per_mtok` | — | What a million tokens of a model no price table names count at. Empty: the base open-weight model's market price. Never applied to a model the table prices. |
| `llm_budget_notify` | — | User ids notified in-app at 80% and 100% of a cap. |
| `credit_markup` · `credits_5h` · `credits_week` | `1.3` · — · — | With the `usage` feature on: credits per call = market cost × markup (default 1.3; a value below 1.0 or unreadable is refused and 1.3 applies); the plan's 5-hour and weekly allowances in credits ($). A full window refuses the next turn unless extra usage is on. |
| `VEXA_LLM_KILL_SWITCH` (agent-api env) | — | `1` refuses every agent turn at once. Helm: `agentApi.llmKillSwitch`. |
| `VEXA_MODEL_PRICES_URL` (agent-api env) | OpenRouter's public `/api/v1/models` | Where market prices are read, once a day. `off` never reads the network; the snapshot bundled with the release prices every call. |

**How it works.** agent-api asks the ledger before it dispatches any turn — a chat message, a routine's
run, a sensor's or an event agent's turn all go through the same dispatch. If a cap that applies is
spent, or the kill switch is on, nothing is spawned or delivered: the person reads "You have reached
your AI usage limit for today. It resets at …" in the chat, and a routine's run fails with that line.
Each turn reports what its model calls used on its result (the provider's own cost when it gives one,
as OpenRouter and the Claude CLI do; otherwise its tokens, priced at that model's market price from
OpenRouter's public price table, read at most once a day and cached in Redis, or from the snapshot
bundled with the release when the table cannot be read; a model neither names counts at the two price
keys, or, when they are empty, at the base open-weight model's market price; a call that reports
nothing is estimated from its text). The same record adds the call's tokens to the rolling-day token
view the token budgets read, so the dollar ledger and the token budgets count one set of calls. agent-api reads that from the worker's output stream,
whether or not anyone is watching the turn, and adds it to per-day and per-month counters in Redis for
the person and the deployment. The first time a cap passes 80% and 100% in its period, the crossing is
logged (`llm_budget_threshold`), listed in the admin panel and sent to the people `llm_budget_notify`
names. A harness reports a turn's usage when the turn ends, so the model proxy also prices every call it
relays, from the provider's own usage in the answer (streamed or not) and at the same price table, and
keeps it as the turn's unreported spend until the worker's report replaces it. Before each model
request the proxy checks the ledger plus that unreported spend, so a long turn is stopped at the cap
partway through (402) rather than after it ends. A turn that reports no usage (the Codex harness) is
recorded at the proxy's figure when it completes. Calls on a deployment subscription do not go through
the proxy: such a turn already running when a cap is reached finishes, and the next one is refused. A
ledger that cannot be read refuses turns rather than letting them run uncounted.

**Why it complies.** The cap bounds the cost a deployment and each person can incur, independently of
the provider's own credit limit, which stays the last line of defence. The counters hold amounts and
user ids only, never prompts or replies, and expire after their period. A refusal is a typed answer
before any model call, so a refused turn sends nothing to the provider. The kill switch is an operator
setting on agent-api and stops new model calls without touching stored data. Reading the price table is one
unauthenticated GET of a public list: no prompt, person or usage figure leaves the deployment, and
`VEXA_MODEL_PRICES_URL=off` keeps an air-gapped install off the network entirely. Meeting bots and
transcription make no calls through this path and are not affected.

## Public profiles

Behind the `public_profiles` switch, which is switched on only by name (`all,public_profiles`).

**How it works.**
- **The profile.** A person's public profile is theirs.
  - Identity is its only writer. It keeps the profile in the person's own account record.
  - Each field is published separately: name, photo, role, company, links (https only) and a short bio.
  - Nothing is public until the person publishes. Withdrawing hides the whole profile at once.
- **Links from a CRM.** An organisation's CRM contact can link to a published profile. Linking needs someone who may change the contact.
  - The contact then reads the profile's public fields live from identity each time it is shown, next to the organisation's own record.
  - Nothing from the profile is copied into the CRM.
  - When the profile is withdrawn, the contact shows only the organisation's own data.
- **The count.** Identity learns only that an organisation linked or unlinked. It keeps that as a salted hash, so the person sees how many organisations link to them and never which ones.
- **The directory.**
  - It answers a query of at least 3 letters with at most 10 published profiles, matched on public name, role and company.
  - It never reports how many matched.
  - It reaches a profile only by an opaque handle, and an unpublished handle answers as if it never existed.
  - Each person gets `VEXA_DIRECTORY_READS_PER_MINUTE` reads a minute (30 by default).
- **Company verification.** A company domain is verified by a DNS TXT record identity gives, or by the person's own verified email on that domain. It is recorded on the profile, with no payment involved.

**Why it complies.**
- Publishing is opt-in, field by field, and withdrawable at any time.
- Each organisation's CRM stays inside its own partition. No organisation's notes, fields or record ids are sent to identity or to another organisation, and a contact never stores the profile.
- The directory is built so that people cannot be enumerated.

## Gateway edge protection

The gateway carries two independent abuse layers. Both are env-driven; both default sensibly for
self-hosted and can be left untouched.

### Per-user limiter (post-auth, on by default)

A token-bucket limiter keyed by user id fires *after* the API key is resolved — it catches one token
driving too much traffic. On by default.

| Variable | Default | Purpose |
|---|---|---|
| `GATEWAY_RATE_LIMIT_DISABLED` | — | `1` / `true` / `yes` / `on` disables the per-user limiter entirely. |
| `GATEWAY_RATE_LIMIT_BURST` | `120` | Bucket size (max burst). |
| `GATEWAY_RATE_LIMIT_RPS` | `40` | Refill rate (tokens/sec). High enough for normal use; lower for stricter throttling. |

### Agent tier admission

`VEXA_AGENT_ALLOW` (gateway and agent-api, default empty) enables the agent tier (`/agent/*`) per person: empty admits everyone a key scope admits, `*` admits everyone, otherwise a comma-separated list of user ids and emails (case-insensitive; `@example.com` admits a whole domain). Anyone else gets `403 agent_tier_not_enabled` at the edge, before anything is forwarded; a worker is admitted by the person it acts for.

### Edge guard (pre-auth, off by default)

An optional fastapi-guard edge layer caps requests per **client IP** *before* the API key is validated
— so an IP flooding invalid keys, or rotating many keys from one IP to defeat the per-user limiter, is
answered with `429` at the edge and never reaches admin-api. An IP that keeps offending past a threshold
is **auto-banned for a window**; sustained abuse costs the abuser, not the operator. It is **on by default
everywhere**: the code default is `GUARD_ENABLED=true`, compose interpolates
`GUARD_ENABLED=${GUARD_ENABLED:-true}` and ships the opt-out line commented, and the Helm chart sets
`gateway.guard.enabled: true`. You opt OUT, not in.

<Note>
`GUARD_ENABLED=false` is the kill switch — set it to turn the whole edge layer off. When
behind a reverse proxy you must also set `GUARD_TRUSTED_PROXIES`, or every request keys to the proxy
IP → one global bucket shared by all clients (one abuser throttles everyone). See
[Deployment → Publishing behind a reverse proxy](/deployment#publishing-behind-a-reverse-proxy).
</Note>

| Variable | Default | Purpose |
|---|---|---|
| `GUARD_ENABLED` | `true` (code, compose and Helm) | Kill switch for the entire edge layer. |
| `GUARD_ENABLE_REDIS` | `true` | Share rate/ban state across processes via the existing `REDIS_URL` (`false` → in-memory only, per-process). |
| `GUARD_RATE_LIMIT_RPM` | `600` | Per-IP request cap per minute; `0` disables rate limiting. |
| `GUARD_RATE_LIMIT_WINDOW` | `60` | Rate-limit window in seconds. |
| `GUARD_AUTO_BAN_THRESHOLD` | `10` | Over-limit events from one IP before it is auto-banned. |
| `GUARD_AUTO_BAN_DURATION` | `3600` | Auto-ban window in seconds; after expiry the offender gets a fresh budget. |
| `GUARD_IP_WHITELIST` | — | CSV of IPs or CIDR ranges that bypass every guard check (e.g. `10.0.0.0/8`). Validated at boot: an invalid entry refuses to start with an error naming the var and the entry. |
| `GUARD_IP_BLACKLIST` | — | CSV of IPs or CIDR ranges rejected on the first request (`403`), e.g. `203.0.113.5,198.51.100.0/24`. Validated at boot like the whitelist. |
| `GUARD_BLOCKED_COUNTRIES` | — | CSV of ISO country codes to block (geo, opt-in). |
| `GUARD_BLOCK_CLOUD_PROVIDERS` | — | CSV of cloud providers to block by IP range, opt-in. Accepted values: `AWS`, `GCP`, `Azure` (case-insensitive, normalized at boot); any other name refuses to start with an error listing the accepted spellings. |
| `GUARD_TRUSTED_PROXIES` | — | CSV of trusted proxy IPs or CIDR ranges whose `X-Forwarded-For` is honored for client-IP resolution (e.g. `172.16.0.0/12`). Validated at boot. **Set this when behind a reverse proxy.** |
| `GUARD_TRUST_X_FORWARDED_PROTO` | `false` | Trust `X-Forwarded-Proto` for scheme enforcement. |
| `GUARD_REDIS_PREFIX` | `vexa:guard:` | Redis key namespace (avoids colliding with Vexa's own keys). |
| `GUARD_WS_ENABLED` | `false` | Opt-in `/ws` connect guard, run directly by fastapi-guard's own `guard_websocket`. Requires `GUARD_ENABLED=true` (boot refuses otherwise, naming both vars). Runs the same checks as the HTTP layer: ban store, IP lists, and a per-IP rate limit with its own `/ws` budget (an isolated `endpoint_path="ws"`), auto-banning through the same knob pair below. The ban store and the rate-limit window are both Redis-shared with the HTTP layer when `GUARD_ENABLE_REDIS=true`, per-process otherwise. Auto-ban violation counts are kept PER PATH: an IP's HTTP and WS over-limit events do not add up toward one threshold, though the resulting ban, once either path triggers it, is shared. **Breaking on upgrade:** a deploy that previously ran `GUARD_ENABLED=false` with `GUARD_WS_ENABLED=true` (a working WS-only setup under the old hand-rolled guard) now refuses to boot with a `ConfigError` naming both vars - set `GUARD_ENABLED=true` (or turn the WS guard off) before upgrading. |
| `GUARD_AUTO_BAN_RATE_LIMIT` | `true` | Auto-ban an IP that keeps exceeding the rate limit (ban reason `rate_limit_exceeded`) after `GUARD_AUTO_BAN_THRESHOLD` over-limit events, for `GUARD_AUTO_BAN_DURATION` seconds. One knob for both the HTTP pipeline and the `/ws` connect guard; needs the ban store (on by default). |

<Note>
With `GUARD_ENABLE_REDIS=false` AND `uvicorn --workers N>1`, the HTTP rate-limit buckets and auto-bans are also per-process: the effective limit becomes `N × GUARD_RATE_LIMIT_RPM` and bans do not propagate across workers (the `/ws` rate window now follows this same setting too, so without Redis it is per-process just like the HTTP window, and WS bans live in the same ban store as HTTP bans, so without Redis both are per-process). The same applies across multiple gateway **replicas** without Redis - each is its own process. On a Redis outage the library degrades both windows to their in-memory per-process fallback and logs an error per request rather than failing closed, so the same `N ×` ceiling applies until Redis is back.

**Safe configurations:** the shipped gateway runs a **single** uvicorn worker, so the default (`GUARD_ENABLE_REDIS=true`, one worker) enforces the limit globally. If you scale to multiple workers **or** replicas, keep `GUARD_ENABLE_REDIS=true` — Redis-backed state is what shares the buckets and bans across processes. `GUARD_ENABLE_REDIS=false` is only safe with a single worker **and** a single replica; if you must run without Redis at higher concurrency, divide `GUARD_RATE_LIMIT_RPM` by the process count to hold the aggregate cap (note this still will not propagate bans).
</Note>

The guard fails open (`fail_secure=false`): a guard-check bug or a redis outage returns the request to
the app rather than taking the gateway down. Request-body WAF scanning is intentionally off — the
gateway proxies arbitrary user text (chat, meeting `data`, transcript shares), so signature scanning
would false-positive on legitimate content.
