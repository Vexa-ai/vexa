# ADR 0041 — The edge signs the identity it resolved; a worker's delegation is a bearer like any other

**Status:** accepted · 2026-10-09, amended the same day (Ed25519, below) · for v0.13.2 ([#1784](https://github.com/Vexa-ai/vexa/pull/1784),
[#1783](https://github.com/Vexa-ai/vexa/issues/1783)) · applies P20 and P4 · completes decisions 1
and 2 of [ADR-0037](0037-the-target-architecture-one-edge-domains-over-identity-and-runtime.md)
without changing them

## Context

The gateway resolves a bearer through identity and forwards the request with `X-User-Id` and the
headers beside it (email, scopes, bot limit, workspace memberships, webhook). agent-api and
meeting-api derive everything they scope by from those headers, so the headers should carry proof of
where they came from rather than rely on the network path alone. The opt-in
`VEXA_REQUIRE_GATEWAY_IDENTITY` switch checked for a marker header; this ADR replaces it with a
signature the services verify.

A cloud worker's tools were served by a separate MCP upstream (`AGENT_MCP_URL`) that existed only in
the dogfood deployment. ADR-0037 §2 asks for one MCP server, at the gateway, authenticating every
caller, with the worker as an ordinary client of it.

## Decision

1. **The gateway signs what it stamps.** Every forward carries `X-Vexa-Identity`: an Ed25519
   signature over the claims the services read, with an issue time and a 60-second expiry, made with
   a private key only the gateway holds (`VEXA_GATEWAY_IDENTITY_SIGNING_KEY_FILE`; the sealed contract
   `core/gateway/contracts/gateway-identity.v1`). See the amendment below.
2. **The services verify at their door.** agent-api and meeting-api install `IdentityGuard` with the
   gateway's public key: a valid signature (±30 s skew, at most a 300 s lifetime) rebuilds every `x-user-*` header
   from the claims; an `x-user-*` header without one is a `401`. A request that names nobody passes
   to the routes that need nobody (health, bot and runtime callbacks), and there is no fallback
   subject. The switch is removed.
3. **One other way to name a person: the internal tier.** A service holding `INTERNAL_API_SECRET`
   (flows, agent-api calling meeting-api, the dogfood rig) presents `X-Internal-Secret` and names the
   user it acts for. That is the trust the internal tier already carried everywhere else.
4. **A delegation token is resolved by identity.** `/internal/validate` verifies `vxd_` bearers with
   `VEXA_MCP_DELEGATION_SECRET` and answers with the person, scopes `bot` + `tx`, never an admin role,
   and the dispatch's ceiling (`regime`, `workspaces`, `target`) as `delegation`. Every resolver —
   the gateway and flows — therefore authenticates a worker the same way, through the same rate
   limiter, and none of them holds the delegation key. The `AGENT_MCP_URL` branch is removed: `/mcp`
   has one upstream.
5. **The domain owns the policy on the ceiling.** The ceiling rides the signed identity
   (`x-user-regime`, `x-user-delegation-workspaces`). agent-api refuses a worker dispatched without a
   person the verbs that need one (Connections reads and drafts, a stored credential's use, a
   consent request, the person's timezone, a repository load) and a workspace outside its isolation
   set.
6. **Generated at install.** The identity keypair and the delegation key are generated by every
   deploy surface — compose's `identity-keys` one-shot and `mint-dev-env.sh`, the chart (kept across
   upgrades), the Lite entrypoint (persisted in its state directory) — and every service that needs
   one of them refuses to boot without it.

## Amendment (2026-10-09): an asymmetric signature, and the broker checks it

As first built, the signature was an HMAC over a secret the gateway, agent-api and meeting-api all
held, so every verifier could also mint an identity, and the credential broker could not be given the
key without being able to mint too — it went on trusting whichever person agent-api named. Before
v0.13.2 ships (the contract was unreleased, so v1 is amended rather than a v2 added):

- **Only the gateway can sign.** `gateway-identity.v1` is an Ed25519 signature. The gateway holds the
  private key; agent-api, meeting-api and the credential broker hold the public key
  (`VEXA_GATEWAY_IDENTITY_PUBLIC_KEY_FILE`) and can verify but not sign. The token's `v1` fixes the
  scheme and names no algorithm, a verifier refuses any key that is not an Ed25519 public key (the
  private key included), and the claims, the 60-second expiry, the ±30 s skew and the 300 s cap are
  unchanged. `VEXA_GATEWAY_IDENTITY_SECRET` is gone.
- **The broker acts for a person only on the gateway's word.** agent-api forwards the verified
  `X-Vexa-Identity` unchanged on every agent-role call; the broker verifies it and refuses the call
  when it is missing, invalid, or names anybody other than the actor in its own assertion
  (credential-broker.v1 keeps role and integrity). agent-api's keys alone — the agent key, the
  internal tier — no longer let it use a person's connections; it can only while serving a request
  the gateway signed for that person. A caller that names a person over the internal tier is refused
  Connections by agent-api before the broker is asked.
- **Keys at install.** Compose's `identity-keys` one-shot writes the pair into two volumes, the
  private one mounted by the gateway alone; the chart keeps the private key in a Secret mounted only
  by the gateway and derives the public key into a ConfigMap on every render; Lite generates the pair
  on first boot into its state directory.
- The contract moved to `core/gateway/contracts/gateway-identity.v1`, so that it no longer shares a
  name with the identity domain's `identity.v1`.

## Trade-off

**The internal tier can still name a person to agent-api and meeting-api.** Anything holding
`INTERNAL_API_SECRET` can, which is the trust that tier already carried. The boundary the signature
draws is between the gateway and everything else: a verifier, a bot's browser, an agent worker or
any other pod can check an identity and cannot make one, and the credential broker does not accept
the internal tier at all.

**Signatures are verified on every hop, at Ed25519 cost.** A verification is tens of microseconds,
well inside one forward. The signing key is one more file to keep: rotating it means replacing the
private key and restarting the services that hold the public half.

**The internal tier is broad.** It already was. The chart's default NetworkPolicy narrows who can
reach agent-api and meeting-api at all — runtime-managed pods reach meeting-api for their callbacks
and agent-api not at all, and workers are labelled so the policy can tell them from bots.

## Consequences

- A forged or unsigned identity is refused by agent-api and meeting-api; every legitimate caller has
  a path: the gateway (signed), the internal tier (flows, agent-api, the rig), or no identity at all
  (bot and runtime callbacks, the scheduler, the terminal's internal admin routes).
- Connections are reached only through the gateway: a person's own client and a worker's toolbelt
  go through it already, and the dogfood rig's agent tools now call agent-api through the gateway
  with the caller's own credential (a worker's delegation token as itself).
- A worker files friction through the gateway with its delegation token, as `/agent/friction`.
- The chart ships a default NetworkPolicy for agent-api and meeting-api and deploys the MCP service;
  Lite runs it as a program.
- Delegation revocation (a `jti` denylist) lived in the rig; identity does not hold one yet. A token
  lives at most its TTL (an hour by default).
- `gate:fact-parity` gains a `header` kind (2026-10-09): the captured text is an HTTP field name,
  compared case-insensitively (RFC 9110 §5.1), so `x-vexa-identity` and `X-Vexa-Identity` are one
  answer. Facts `identity-header` and `mcp-reentry-header` use it.
